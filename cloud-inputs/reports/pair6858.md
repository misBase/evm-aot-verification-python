### 2.2 与兄弟义务的形状差别

材料：`analysis/diff_{a,b}_68_8_vs_58.txt`（`cloud-inputs/pair58/cdiff.py` 的合取项差集）、`analysis/sha3args_a58.txt`、`analysis/opaque_b_shape.txt`。

- **gas 项**：完全相同（差集里没有 gas 和 msize 的合取项）。两个上下文的 `pair_68_58` 之间前提完全相同（237/237），只有目标第 2 部分有差别（`diff_58_a_vs_b.txt`）。

## 4. 健全性论证

1. **一步剥离的引理。** 对任意数组 A、B，地址 a、b，值 v，读地址 i、j，若 b − a = j − i（模 2^n），则 `A[i] = B[j]` ⟹ `Store(A, a, v)[i] = Store(B, b, v)[j]`。证明：`Store(A, a, v)[i] = ite(i = a, v, A[i])`，`Store(B, b, v)[j] = ite(j = b, v, B[j])`。由于 j = i + (j − i)、b = a + (j − i)，而加同一个常数在模 2^n 下是双射，所以 i = a ⟺ j = b：两边要么都读到 v，要么都落到 A[i]、B[j]。逆否命题：`Store(A,a,v)[i] ≠ Store(B,b,v)[j]` ⟹ `A[i] ≠ B[j]`。对 store 的个数做归纳，可以推广到剥掉任意多层。测试 `test_peel_step_is_implied_for_every_value` 用全自由变量让 z3 验证了这条引理。
2. **条件只靠简化器检查。** "值相同"和"地址差等于读地址差"都要求 `simplify(bv_sort_ac=True)` 之后是同一个 AST。z3 的化简保持等价，同一个 AST 在每个模型下取值相同，所以条件在所有模型下都成立。不满足时立刻停下，不做任何猜测。
3. **只是弱化。** 每个被替换的合取项 C 都蕴含替换后的 C′，其余合取项不变，所以 F ⊨ F′：F 的每个模型都是 F′ 的模型。因此 F′ UNSAT ⟹ F UNSAT。反过来不成立：store 可能正好覆盖两个链底不同的位置，这时 F UNSAT 而 F′ SAT（`test_peeling_can_lose_a_proof_only`）。所以只信 F′ 的 UNSAT；SAT 或 unknown 都回到原来未剥的路线（`test_peeled_miss_falls_back_to_the_unpeeled_query`）。这个改动不会产生 sat 答案，也不会把任何 sat 改成别的答案。
4. **只作用在顶层合取项上。** 被替换的必须是 `_conjuncts` 的顶层合取项（正极性），这样"弱化一个合取项就是弱化整个公式"才成立。处于析取或否定之下的不等式不会被替换。
5. **与其他步骤的组合。** 剥 store 作用在 `query = simplify(substitute(unified, *opaque))` 上。`unified` 来自 `unify_uf_arguments`，每次合并都有已证引理；opaque 只增加模型。所以链条是 F ⊨ unified 的重写 ⊨ opaque 化（只增加模型）⊨ 剥 store（弱化）⊨ 轻前提（去掉合取项，弱化）。每一步都只会增加模型，最后的 UNSAT 可以一路传回 F。记录下来的 `opaque_array_uf_peeled` 带着实际被反驳的查询 sexpr，可以复查。
6. **`_LIGHT_MS`。** 它只是预算。轻前提探针的健全性（去掉合取项只是弱化）与时间上限无关，见 pair58-fix 报告 §4。上限更长只可能把 unknown 变成 unsat，或者多花时间。
7. **错误剥离的防护。** 如果地址或值不匹配也照样剥，就会产生错误的 UNSAT。例如 `Store(A, f, v1)[w] ≠ Store(A, f+1, v1)[w]` 是 SAT 的，但错误地剥掉以后变成 `A[w] ≠ A[w]`，就是 UNSAT。`test_mismatched_stores_are_not_peeled_into_a_false_refutation` 覆盖了地址不匹配和值不匹配两种情况；变异测试显示，去掉任一项检查，这条测试都会失败（§6）。

## 8. 未解决的问题

1. **需要服务器全量验证**：5377 的两个 d30 上下文用 a952b9b 跑完整节点，以及原来已证块的回归。离线只覆盖了本报告列出的义务。
2. **`pair_68_33` 没有 SMT2**，§2.2 里关于它的推断没有核实。
3. **剥 store 只在 unify 路由的不透明查询里用。** 其他路由（quick*、exact*、blast*）遇到同样两条对齐的 store 链时也可能受益，但这次没有加，以免改变其他义务的路由耗时。将来如果遇到"两侧 store 链逐字节对齐、链底不同"的卡点，可以考虑把它推广成一个独立的路由。
4. **只做弱化、不带地址排除。** 带 `∧ i ≠ a_k` 的等价形式在本义务上要 35.9s（不带只要 6.5s）。如果出现"链底只在 store 覆盖的位置不同"的义务，剥后的查询会是 SAT，然后回到原路线，最多多花一个单查询预算。
5. **`_LIGHT_MS = 8000` 的成本**只在本数据上估过：探针不命中时几乎都是约 0.2s 的 SAT，在本次日志约 350 次探针中没有一次用满 2s。其他合约如果有大量"轻前提也难"的候选对，每对最多多花 6s。服务器回归时请留意 pair 阶段的总耗时。

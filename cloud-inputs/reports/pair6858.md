## 1. 结论

- **r37f 现有路由在 3600s 内证不出**（任务第 2 步不成立）：离线单独剖析，a 在 2635.2s、b 在 2769.1s 跑完全部路由，结果都是 unknown（没有用满 3600s，而是所有路由都失败了）。
- **卡在哪里**：goal split 成 7 部分，第 0、1、3、4、5 部分在 quick0 证出，第 6 部分（gas）在 quick* 证出，**卡住的是第 2 部分（内存/sha3 目标）**。卡点在胜出路由 `unify*` 里面：sha3 参数合并**成功**（1.6s，轻前提命中），但合并之后的 opaque 内存查询 `opaque_array_uf_light` 在 30s 单查询预算内超时（30.25s），完整版 `opaque_array_uf` 同样超时，之后的 case tree 用满 120s 失败。
- **根因**：pair_68_58 是唯一一条真正拷贝 calldata 的路径（`stack_18` < 2^64 且 ≤ CallDataSize）。兄弟 `pair_68_8` 的拷贝源偏移被截成 CallDataSize，拷贝内容全是 0。opaque 查询的目标是 `A[w] ≠ B[R15 + w]`，两侧内存都是**同一串 320 个字节写入**（EVM 写在 fmp + k，x86 写在 R15 + fmp + k，写入值逐个相同）叠在一个 CALLDATACOPY lambda 上。Z3 要对两条 320 层的 store 链做读写分情况，带上真实 calldata 读之后需要 113s（a）/ 126s（b），超过 30s 预算。在 68_8 上同一查询是 13.8s。
- **修法（通用，两处）**：
  1. `peel_matching_stores`：对顶层读不等式 `¬(A[i] = B[j])`，从两条 store 链顶部剥掉逐对匹配的写（地址差 ≡ j − i，值相同），换成对底层数组的读。这是**弱化**（原式蕴含新式），只有 UNSAT 能传回。在 `_retry_with_uf_unification` 的 opaque 查询之前先试剥过的版本，不成功再走原来的查询。实测 a：113s → **5.2s**，b：126s → **5.0s**，68_8：13.8s → 0.7s。
  2. 轻前提探针超时（unknown，而不是 sat）时，用调用方的预算再解一次。sha3 参数相等这条查询在云端负载下要 0.9–2.1s，正好压在 2s 上限上；在一次 4 进程并行的测试里它超时了（2.06s），导致合并失败、整个路由 unknown（1250s）。
- **离线验证**（云端 4 核，单独模式，每条 3600s，2 路并行）：修法后 **a proved 772.8s，b proved 808.2s**（修法前 unknown 2635s / 2769s）。第 2 部分由 `unify*` 证出（a 255.6s，b 237.3s），前面失败的路由约 460–516s；生产中 winner-first 统计会把 `unify*` 提前，这部分会省掉。

## 4. 健全性论证

### 4.1 peel_matching_stores

1. **单步引理**：设 A = store(X, a, v)，B = store(Y, b, u)，b − a ≡ d，j − i ≡ d（模 2^64），u ≡ v。若 A[i] ≠ B[j]：
   - 若 i = a，则 j = i + d = a + d = b，A[i] = v = u = B[j]，矛盾；
   - 所以 i ≠ a，于是 j = i + d ≠ a + d = b（加法在模 2^n 下是单射），两边的读都穿过这一层：A[i] = X[i]，B[j] = Y[j]，所以 X[i] ≠ Y[j]。
   
   对 store 链归纳，剥 n 层后 A[i] ≠ B[j] ⟹ X_n[i] ≠ Y_n[j]。
2. **只信 UNSAT**：新公式 F′ 只是把一个合取项换成了它的推论，F ⊨ F′，所以 F′ UNSAT ⟹ F UNSAT。F′ 是 SAT 或 unknown 时不得出任何结论，调用方接着走原来的 opaque 查询（测试 `test_unpeeled_query_still_runs_when_the_peeled_one_is_not_refuted`）。丢掉的 i ≠ a 只会让 F′ 更弱（测试 `test_peeled_formula_is_only_a_weakening`：F UNSAT 而 F′ SAT 的例子，剥 store 不会把它变成 UNSAT）。
3. **匹配条件是精确判定**：地址差用 `simplify` 求成字面量 0 才算匹配，值用 AST 相等或 `simplify(va == vb)` 化成 True 才算匹配。`simplify` 是等价变换，判成匹配就一定在所有解释下都匹配；判不出来只会停止剥离（少剥，不会错剥）。
4. **引理可复查**：每种数组 sort 记一条 `store_peel_k`，内容是通用实例 `store(x, a, v)[i] ≠ store(y, a + d, v)[i + d] ∧ x[i] = y[i + d]`（全是新常量），要求 Z3 判为 unsat，否则整个剥离放弃（返回 None）。这和 `skolemize_array_disequalities` 记外延性引理的做法一样。
5. **只作用在顶层合取项**：binder 下面的读不等式不碰。lambda 作为底层数组时，`simplify(Select(lambda, i))` 是 beta 归约，等价。
6. 剥过的查询之后照样经过轻前提（只去掉合取项，pair58-fix §4.1）和 opaque 常量（只增加模型），两者的论证不变。

### 4.2 轻前提探针的重试

只改了同一条查询的时间预算：查询本身（去掉 heavy 合取项之后的 `light ∧ goal`）和接受规则（只认 "unsat"）都没有变。重试只在第一次是 unknown 时发生；sat 不重试（`test_sat_light_probe_is_not_retried`），所以 sat 的情况不会多花时间。重试预算 `retry_ms = min(budget_ms, 剩余 deadline)`，也就是调用方本来就会给这个候选对的单查询预算（unify 里 30s，sweep 里 2s，此时 `retry_ms == light_ms`，不会重试）。

代价：每个"轻前提超时"的候选对最多多一个单查询预算。修法后的剖析里（§1 的 a、b 两条），`unify*` 内的轻前提不命中 78 次共 16.9s，没有出现长时间的重试。

## 9. 未解决的问题

1. **需要服务器全量验证**：本地只单独跑了两条 pair_68_58 和 r37d 的 16 条慢 pair。r37f + 本修法跑 5377 的两个上下文，需要在服务器上确认。生产中 winner-first 会把 `unify*` 提前，第 2 部分前面约 460–516s 的失败阶段预计会省掉。

4. 轻前提重试会让"轻前提超时"的候选对多花一个单查询预算。本数据里这种候选对很少（每条 pair 0–1 个），但在别的块上如果大量出现，可以给重试单独设上限。

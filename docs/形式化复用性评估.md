# 验证框架对其他 EVM AOT/JIT 编译器的可迁移性

> 调研日期：2026-08-18
> 用途：论文 Discussion / Threats to Validity 章节素材。回答审稿人必问的
> "Does this framework generalize beyond your specific compiler?"
> 所有仓库元数据（license / star / 最后推送 / 归档状态）均为调研当日通过 GitHub API 实测。

---

## 0. 简答

**方法论层面：可以，且是设计使然。**
Translation validation 的定义就是编译器无关的——它证明的是"这一次编译的输出等价于输入"，
不触碰编译器实现。本框架的可观察等价定义、验证架构、Uint256 参考模型都只依赖 EVM 规范，
换任何目标都成立。

**实现层面：不可直接迁移，且这不是工程惰性，而是方法本身的可扩展性代价。**
让程序级验证从"理论可行"变成"秒级可解"的每一项技术，都依赖对目标编译器 codegen 的白盒假设。
一旦目标后端不满足这些假设，方法仍然正确，但求解规模从秒级跌到 unknown——SMT 上的退化是悬崖式的，
不是渐进的。

**因此可迁移性不是二元的，而由一个可判定的目标性质决定：codegen 的句法规整性（syntactic regularity）。**
这个判据与源语言、目标 ISA 都无关，只与后端的组织方式有关。据此：

- 模板式 codegen 编译器（go-hpc-evm、**Monad**）→ 可迁移，代价可预测
- LLVM/MLIR 系（revmc、evm_mlir）→ 方法成立但不可扩展
- 无机器码产物（evmone、DTVM 当前形态）→ 命题不成立

可供论文直接引用的表述：

> Our framework is *methodologically* compiler-agnostic but *pragmatically*
> profile-parameterized. The equivalence criterion, the observable-behavior
> definition, and the reference semantics transfer to any EVM-to-native compiler
> without modification. What does not transfer is the set of structural assumptions
> that make whole-program SMT queries tractable — fixed base-register partitioning
> of the target memory, a statically known runtime-context layout, and a finite,
> enumerable set of code-generation shapes. We argue that these assumptions are not
> incidental to our implementation but characterize a *class* of compilers: those
> whose back end is a template-style emitter rather than an optimizing IR pipeline.
> For this class, migration cost is dominated by re-instantiating a target profile;
> outside it, the method remains sound but loses tractability.

## 1. 方法论层面：什么是真正可迁移的

以下四项只依赖 EVM 规范和"可观察行为"的定义，与目标编译器无关。它们构成本工作的方法论内核。

### 1.1 离线验证架构与保守 fallback

合约默认解释执行，验证通过才切原生；`unsat` → AOT / `sat` → fallback / `timeout` → fallback。
未验证的原生代码永不影响共识。

这个部署模式对任何"解释器 + 编译器"双轨的区块链客户端都成立，且这些客户端天然满足前提——
revmc 是 revm 的旁路加速器，Monad 同时维护高度优化的解释器（`--vm_mode Dual` 即双轨对拍），
DTVM 有解释器模式。**这是本工作最容易被其他系统采纳的部分，也是最该在论文里强调的架构贡献**，
因为它把"验证不完备"（timeout）转化成了一个安全的工程默认值，而不是一个未解决的正确性问题。

### 1.2 五维可观察等价定义

return data / memory / gas / storage / status code。这是 EVM 语义层的定义，与后端实现无关。

其中 **gas 作为一等等价维度是区块链 translation validation 特有的**：
通用编译器 TV（Alive2 对 LLVM peephole、CompCert 的 simulation diagram）不把资源消耗
视为可观察行为，因为在通用语言里它不影响程序语义。在区块链上它影响共识——
gas 记账偏差会导致节点分叉，其后果与计算结果错误同级。

这一点值得在 Related Work 里明确对比，它是本工作相对 Alive2 范式的实质差异，
而非"应用到新领域"这种弱主张。

### 1.3 Uint256 参考模型

256-bit 算术与位运算的数学规范（29 个操作），以及它与实现表示之间的桥接方法。
规范侧完全可迁移；桥接侧绑定具体表示（见 §2.4）。

### 1.4 路径级符号执行与状态合并

CFG 构建、worklist 符号执行、汇合点合并、path-condition 守卫的 ITE 合并。
标准技术，概念上无迁移障碍。

### 1.5 一个支持性观察：UF 抽象边界与编译收益边界重合

MegaETH 的公开研究指出：revm 约 **50% 的执行时间花在 host/system opcode**
（keccak256、sload、sstore）上，这些已是原生实现、编译无法加速，
因此端到端加速上限约 2×。

这个数字反过来支撑本文的建模取舍：**编译器能加速的部分，恰好就是本框架能真正证明的部分
（目标机器码中可见的算术与控制流）；只能用 uninterpreted function 黑盒建模的 host 部分，
本就不在编译收益里。** 即 UF 的抽象边界与编译器的作用边界基本重合——
"host 用 UF 建模"这个看似的 soundness 妥协，放弃的恰是编译器根本没有改动的那一半语义。

这一点与目标编译器无关，因此属于方法论层。建议主动写进 Discussion，
作为对"是否用 UF 掩盖了一半语义"这一预期质疑的正面回应。

## 2. 实现层面：什么不可迁移，以及为什么这是必然的

### 2.1 三根 tractability 支柱及其白盒依赖

论文 §6 把这三项称为 "critical to making program-level verification tractable"。
它们各自依赖一条对目标编译器的白盒假设：

| 优化 | 作用 | 隐含的白盒假设 |
|---|---|---|
| **基址寄存器内存分区** | 按 R13/R14/R15 把 x86 内存拆成三个不相交 Z3 Array，杜绝跨域 Store chain 污染 | 基址寄存器角色在整个程序中固定，不被寄存器分配器重排 |
| **运行时上下文侧信道** | 高频字段（status code、sp、gas）镜像成独立 BitVec，避开深层 Select 链 | 运行时结构体布局与字段偏移编译期已知且稳定 |
| **`shape_id` 引理缓存** | 复杂 x86 slice 离线证一次、按形状复用（如 MUL 的 34 条指令） | 每个 source op 对应的 codegen 形状集合有限且可枚举 |

### 2.2 为什么失去这些不是"慢一点"而是"不可解"

这是本节要向审稿人说清的核心。SMT 求解在这类问题上的行为不是渐进的：

- 去掉内存分区，两侧内存合并成单一 Array，跨域 Store chain 使每次 Select 都要穿越
  无关的写入历史。表达式规模的增长是乘性的，不是加性的。
- 去掉侧信道，读一次 status code 要展开整条 store 链。本框架实测中，
  仅 `_handle_jcc` 里的 simplify 剪枝就承担了 97.7% 的静态判死；移除后吞吐下降一个数量级。
- 去掉形状缓存，MUL 这类操作必须在每个出现点全展开 —— 论文已实测这直接导致 solver timeout。

也就是说：这些不是常数因子优化，而是让问题落在可解区内的**结构性前提**。
方法的正确性不依赖它们，方法的可用性完全依赖它们。

**论文措辞建议**：不要写成"我们做了一些优化"，而应写成
"we identify three structural properties of template-style back ends that admit a
tractable encoding, and show that whole-program equivalence checking is practical
exactly when these properties hold."
——把优化提升为对目标类的刻画，泛化性主张才站得住。

### 2.3 "black box" 主张需要收敛

论文 §1 写 "treating the compiler as a black box and making verification independent of
compiler internals"，§5 开篇重申 black-box。但正文至少四处依赖白盒知识：

| 位置 | 白盒依赖 |
|---|---|
| §5.1 State correspondence | "Three registers carry fixed roles: R13→CallEngine, R14→stack base, R15→memory base" |
| §6.4 Memory Model | 按基址寄存器把 x86 内存分区成三个不相交 Z3 Array |
| §6.3 Composable Lemma | L1 "parses structured parameters from machine code"；summary 按 `shape_id` 缓存 |
| §5 输入端 | source 是编译器导出的 EVM IR，不是摘要承诺的 EVM bytecode |

审稿人只要读到 §5.1 就会质疑 §1 的措辞。**建议主动改为分层表述**：

> 对后端 codegen 是黑盒（不读编译器源码，只消费其产物）；
> 对运行时 ABI 与寄存器约定是灰盒（需要一张显式的 target profile 作为配置输入）。

这个改法反而**增强**泛化性论证：它把白盒依赖从"藏在方法里的假设"变成"一个可替换的显式参数"。
本仓库的 `x86_64/aot_profile.py` 中的 `X86AOTProfile` dataclass 已经是这个东西的雏形，
把它提升为论文的一等抽象（而不是实现细节），generality 就有了着力点。

### 2.4 第四处、也是最根本的一处：输入端锚点

论文 §5 的 source 是 go-hpc-evm 导出的 `CompilerEVMResult{ControlFrames: []*Block}`。
这个 IR 已经替验证器做掉了 CFG 恢复与块级对齐，而 pairing 机制（call site mapping、
path pairing、loop pairing）全部建立在这个锚点上。

后果有两重：

1. **论文实际验证的是 backend（IR → x86），前端 bytecode → IR 未被覆盖。** 摘要说
   "the compiled x86-64 code is semantically equivalent to the original EVM bytecode"
   属于 overclaim，应改为 IR，或明确说明前端在信任基（TCB）内。
2. **迁移时这个红利消失。** §5.2 写 "our framework rejects contracts with dynamic jumps;
   the Solidity compiler rarely emits them outside of handwritten inline assembly" ——
   这句话在有 IR 前端兜底时勉强成立，**直接吃 bytecode 时不成立**：Solidity 的 internal
   function 返回就是压返回地址后 `JUMP`，是标准动态跳转。也就是说迁移到直接消费 bytecode 的
   编译器时，适用性限制会**收紧**而不是放宽。这一条必须写进 limitation。

### 2.5 表示层绑定：Uint256 桥接

论文 §3 的标题是 "bridging the reference model to the Go AOT compiler's 4×64-bit limb
implementation"。规范侧可迁移，但 limb 分解、carry/borrow 链、holiman 分段算法的镜像
全部绑定"uint256 表示为 4 个 64-bit 内存 limb"这一具体选择。

Monad 把 uint256 存在**单个 256-bit AVX 寄存器**里（见 §5.4）。这既说明桥接层确实绑定表示，
也说明另一种表示可能**更简单**（BitVec(256) 直接对应，无需 limb 展开）。
论文应把 §3 拆成"规范"与"表示桥接"两部分，前者作为可复用资产陈述。

## 3. 可迁移性判据：codegen 的句法规整性

### 3.1 什么是"模板式 codegen"

这个概念是全文的枢纽，需要精确定义，否则 §3.2 的判据会退化成事后归纳。

> **定义。** 一个后端是**模板式的**（template-style / macro-expansion code generation），
> 当且仅当：每个源操作对应一段预先写定的目标指令序列，序列的选择仅由少量编译期可判定的参数
> （操作数是否为常量、常量取何特殊值、操作数当前所处的位置类别）决定；
> 编译器的工作是"选模板 + 填参数"，而非"构造通用 IR 再施加全局优化"。

对立面是**优化 IR 管线**（LLVM / MLIR）：源操作先降级到与源语言无关的通用 IR，
之后经过内联、常量传播、CSE、向量化、寄存器分配等 pass，
最终指令序列是全局优化的结果，**无法从单个源操作局部推断**。

这个区分不是风格问题。它决定了"给定一个源操作，其目标代码形状的集合是否有限且可枚举"——
而这正是 §2.1 三根 tractability 支柱共同的前提。

下面用 Monad 的真实源码给出三个可观察特征。

#### 特征 1：指令模板是源码里的字面常量表

`category/vm/compiler/ir/x86/emitter.cpp:176`：

```cpp
#define GENERAL_BIN_INSTR(i0, i1)                    \
    general_bin_instr<                               \
        {&x86::Assembler::i0, &x86::Assembler::i1,   \
         &x86::Assembler::i1, &x86::Assembler::i1},  \
        /* ……共 5 组，对应 5 种操作数位置组合…… */>
```

调用点（`Emitter::add`）：

```cpp
GENERAL_BIN_INSTR(add, adc)(dst, dst_loc, src, src_loc, /* skip 谓词 */);
```

展开后是 **5 组 × 4 个 asmjit 汇编器方法指针**的编译期常量数组：
4 个对应 uint256 的四个 64-bit limb（第 0 个用 `add` 建立进位，后三个用 `adc` 传播），
5 组对应操作数位置组合。

**指令模板在这里是字面意义上的一张编译期常量表**——没有搜索、没有代价模型、没有 pass 顺序。
这是模板式后端最直接的判定证据：模板的基数可以数出来。

#### 特征 2：形状由少量编译期可判定参数决定

`Emitter::add()` 的完整形状分支：

```cpp
if (pre_dst->literal()) {
    if (pre_src->literal())                          // 双常量 → 编译期折叠
        return stack_.alloc_literal({x + y});
    else if (pre_dst->literal()->value == 0)         // 0 + a → 恒等
        return pre_src;
}
else if (pre_src->literal() && pre_src->literal()->value == 0)  // a + 0 → 恒等
    return pre_dst;
// 否则：发射 add/adc 链
```

`Emitter::and_()` 同构，多两支：`a & 全1 ⇒ a`、`a & 0 ⇒ 0`。

即 ADD 的形状空间是 {双常量折叠, 左零恒等, 右零恒等, 通用 add/adc 链}，AND 是六支。
此外模板还带一个 per-limb 的跳过谓词（`[](size_t i, uint64_t x){ return i == 0 && x == 0; }`），
对特定 limb 上的常量做进一步特化——仍然是有限枚举。

**这里有一个对论文很有力的观察**：本框架论文 §6.3 把 `shape_id` 定义为
"determined by compile-time constant-zero combinations"，
而 Monad 这个由完全独立团队开发的编译器，其形状参数化方式与该定义**几乎逐字对应**。

这不是巧合。模板式后端负担不起全局优化，常量特化几乎是它唯一能做的优化，
因此形状必然沿"哪些操作数是编译期常量、取何特殊值"这一维度展开。
**换言之，`shape_id` 这个抽象不是对 go-hpc-evm 的特化设计，而是刻画了模板式后端的共性结构。**
这一点应当写进论文——它把 §6.3 从一个实现技巧提升为对一类编译器的观察。

#### 特征 3：位置感知的模板选择，但位置类别有限

`Emitter::and_()` 用的是另一个宏：

```cpp
AVX_OR_GENERAL_BIN_INSTR(and_, vpand)(dst, left, left_loc, right, right_loc, /* skip */);
```

两个操作数都在 AVX 寄存器时发射**单条 `vpand`**（一条指令处理全部 256 位），
否则退回 GPR 上的四条 `and` 链。这就是 Monad 文档所称
"operand-aware instruction selection" 的真身——但候选集是源码里写死的两条路径，
不是优化器搜索的结果，且位置类别只有四种（`Literal` / `AvxReg` / `GeneralReg` / `StackOffset`）。

对比 LLVM 后端：同一个 `and` 源操作的最终指令序列取决于内联深度、
周围代码的寄存器压力、向量化 pass 是否触发——不可从局部推断，形状空间不封闭。

#### 对 SMT 编码的直接后果

模板式不等于"和 go-hpc-evm 一样"。Monad 的模板选择了不同的表示，后果是可预测的：

| EVM 操作 | go-hpc-evm | Monad | 对 Z3 编码的影响 |
|---|---|---|---|
| AND / OR / XOR | 四条 GPR limb 指令 | **单条 `vpand` / `vpor` / `vpxor`** | Monad **更简单**：直接对应一个 `BitVec(256)` 操作，无需 limb 分解与重组 |
| ADD / SUB | add/adc 链（4 limb） | add/adc 链（4 limb，`GENERAL_BIN_INSTR(add, adc)`） | **同构**：现有的 carry 链建模可直接复用 |

差异的物理原因：AVX2 没有跨 lane 的进位传播，所以按位运算能整体向量化、加减法不能。
这是**表示层**的差异，不触及判据 R2——形状仍然有限可枚举，只是模板内容不同。
这也再次说明 §2.5 的判断：Uint256 桥接层绑定的是表示选择，而非方法本身。

#### 一处需要新增建模的机制

`discharge_deferred_comparison()` —— **延迟比较**：比较结果先留在 EFLAGS 中，
直到真正需要一个 0/1 值时才物化。这要求符号状态里增加一个"待决比较"分量，
是本框架当前没有的。

它并不违反模板式的定义（discharge 点在源码中显式且可枚举），
但说明即便在同一类编译器内部，仍存在需要逐个识别的机制差异——
这正是 §6 所说"不可迁移的是领域知识而非代码"的一个具体例证。

### 3.2 三条判据

综合 §1、§2 与 §3.1，可迁移性不取决于源语言（都是 EVM）、也不取决于目标 ISA（都是 x86-64），
而取决于后端的组织方式。提出三条可判定的判据：

**(R1) 状态位置映射的静态可确定性**
EVM 抽象状态（栈槽、内存、运行时上下文字段）到目标机器位置（寄存器/固定偏移）的映射，
在编译期静态可确定，且在程序执行过程中不被优化器重排。
→ 决定 state correspondence 能否写成有限的映射表，以及内存分区与侧信道能否成立。

**(R2) codegen 形状的有限可枚举性**
每个 source 操作对应的目标指令序列取自一个有限、可枚举的模板集合，
形状仅由编译期可判定的少量参数（如常量零组合）决定，不随调用上下文变化。
→ 决定 slice parser 与 `shape_id` 引理缓存能否成立。

**(R3) 块级对齐锚点的存在性**
存在一个与源程序基本块结构对应的中间表示（编译器内部即可，不必导出），
使两侧 CFG 能建立块级对应关系。
→ 决定 pairing 机制（call site / path / loop）能否成立。

三条同时满足 → 迁移代价被约束为"重新实例化一个 target profile"；
任一条不满足 → 方法仍然 sound，但对应的那根支柱失效，规模退化到不可解。

**这个判据是论文可以主张的一项抽象贡献**：它把"我们的方法能不能用到别的编译器上"
从一个逐案例的经验问题，变成一个对目标后端的可检查性质。它也解释了为什么
"编译到 x86-64" 这个共同点不足以保证可迁移——revmc 和 Monad 目标 ISA 相同，
可迁移性却截然不同。

### 判据在各目标上的取值

| 目标 | R1 状态映射静态 | R2 形状有限 | R3 块级锚点 | 结论 |
|---|---|---|---|---|
| go-hpc-evm（本文目标） | ✅ R13/R14/R15 固定 | ✅ `compileEVMxxx` 模板 | ✅ `ControlFrames` | 全满足 |
| **Monad** | ⚠️ 虚拟栈，但位置空间极小且编译期确定 | ✅ `Emitter::xxx` 模板 | ✅ `BasicBlocksIR` | **全满足（R1 需扩展映射）** |
| revmc / evm_mlir | ❌ LLVM 寄存器分配 | ❌ 内联+常量传播使形状爆炸 | ❌ 无 | 三条全失 |
| Nethermind IL-EVM | ➖ 目标是 MSIL 栈机，不适用 | ✅ 逐 opcode 发射 | ✅ 单方法内块结构 | 命题变形（见 §4） |
| evmone / DTVM 当前形态 | — | — | — | 无机器码产物，命题不成立 |

## 4. 逐目标结论

### 4.1 revmc（paradigmxyz，Apache-2.0，活跃）

EVM bytecode → LLVM IR → LLVM 后端。三条判据全失：

- R1 失效：LLVM 的寄存器分配不保证固定基址寄存器角色 → 内存分区退化为单一 Array
- R2 失效：内联、常量传播、跨 opcode CSE 使 codegen 形状随上下文变化 → 引理缓存命中率崩塌
- R3 失效：优化后机器码与 EVM opcode 的对应关系被打散，无块级锚点

输入端有一个反向的好消息：revmc 直接吃 bytecode，不依赖私有 IR 格式，验证范围反而**扩大**
（覆盖前端，摘要措辞终于名副其实）。但代价是 §2.4 的动态跳转问题全面暴露。

**更合理的定位**：在 revmc 的 **EVM → LLVM IR 翻译层**做 TV（Alive2 风格）。
那才是它未经验证的自研部分，LLVM 后端本身有更成熟的验证生态（Alive2）。
代价是放弃"跨越大语义 gap"这个卖点——这是 positioning 取舍，不是技术障碍。
论文可以把这一点作为 future work 写出来，显示对边界有清醒认识。

### 4.2 evmone（ipsilon，Apache-2.0，活跃）

纯解释器，baseline + advanced 两种执行引擎，**无机器码产物**，"IR ↔ 机器码"命题不成立。
基于它的 AOT 分支 `megaeth-labs/evmone-compiler` 已于 2025-02-09 归档，且自述非 evmone 团队维护。

但存在一个非平凡的命题重定向：**验证 advanced 模式的块级预计算 ≡ baseline 的逐指令记账**。
advanced 的核心优化就是"每块一次性预计算 gas 成本与栈需求"，恰好落在本框架五维里的
gas 与 stack-underflow status 两维上。这个命题真实、有共识安全价值，且比 AOT 验证容易得多
（两侧都是 EVM 语义，无跨 ISA gap）。

代价：§2 的三根支柱全部用不上，§1.3 的 Uint256 桥接也用不上，等于只借了方法论骨架。
**对论文而言这是廉价的 generality evidence，不构成 contribution。**

### 4.3 DTVM（DTVMStack，NOASSERTION，活跃）

README 中 EVM 前端仍是路线图；组织内实际落地的 EVM 兼容路线是 `DTVM_SolSDK`（Solidity → WASM），
且同时维护 `DTVMStack/evmc` 与 `DTVMStack/evmone` 的 fork——说明其 EVM 兼容当前依赖 evmone 解释器
而非自研编译。

结构上有一个对本方法**有利**的性质：dMIR 作为统一确定性 IR，扮演了 go-hpc-evm 那个 EVM IR 的角色，
天然提供 R3 锚点。但有两个本方法完全未处理的新问题：

1. **多后端**（FLAT / FLAS / singlepass / LLVM 15）：一个 source 对应 N 个 target，每个都要独立建模
2. **分层热切换**（FLAS = Function Level Adaptive hot-Switching）：同一次执行会在运行中跨层切换，
   引入 on-stack replacement 的状态一致性问题——这是 JIT 验证文献中的独立难题，
   本框架的"一 source × 一 target 静态等价"模型处理不了

此外验证目标会变成 WASM 语义 refinement（多一层 trap 语义 + EVM gas → WASM fuel 的映射）。

### 4.4 Monad（category-labs，GPL-3.0，活跃）—— 泛化性的存在性证明

**这是本次调研对论文最有价值的发现。** 详见 §5。

论证要点：Monad 是一个由完全独立的团队、用不同语言（C++ vs Go）、不同汇编后端（asmjit vs 自研）、
不同 uint256 表示（AVX 寄存器 vs 内存 limb）开发的生产级 EVM 原生编译器，
却**同时满足 R1/R2/R3 三条判据**。

这说明 §3 提出的判据刻画的是一个**真实存在的编译器类**，而不是对 go-hpc-evm 的事后过拟合。
对论文的泛化性主张而言，这比补做一个 `-O0` 的 demo 有力得多——
它是一个独立的存在性证据，且可以在不写一行代码的情况下作为 Discussion 材料使用。

### 4.5 Nethermind IL-EVM（MIT，实验线）

EVM bytecode → **.NET MSIL**，整个合约编译成单个方法而非 PC 驱动的 dispatch loop。
目标不是机器码，命题变形为"EVM 栈机 ↔ CLR 栈机"：语义 gap 显著小于跨 ISA，
且 MSIL 有 ECMA-335 正式语义可依。代价是要建 CLR 语义，且 §2 的支柱不适用（无寄存器/内存布局可言）。
属于中等难度、方法论上有新意的备选，但偏离本文"跨越大语义 gap"的主线。

## 5. Monad 编译器：支撑 §4.4 的调研细节

### 5.1 项目与源码组织

- 仓库 `category-labs/monad`，C++（含 Rust 组件），★1215，GPL-3.0，调研当日仍在 push
- 编译器位于 `category/vm/`，其 README 自述 "This project is an untested work in progress"，
  是未公开的 `monad-jit` 项目的 C++ 重写
- 编译管线：`EVM bytecode → Intercode → BasicBlocksIR → Emitter(asmjit) → Nativecode`
- **不经任何可移植 IR**，asmjit 直接发射 x86-64

| 路径 | 规模 | 作用 |
|---|---|---|
| `category/vm/compiler.hpp` | — | 顶层：`compile` / `cached_compile` / `async_compile`（TBB 并发） |
| `category/vm/compiler/ir/basic_blocks.hpp` | 18 KB | 基本块 IR（R3 锚点） |
| `category/vm/compiler/ir/x86/emitter.cpp` | 298 KB | 逐 opcode 发射器（R2） |
| `category/vm/compiler/ir/x86/virtual_stack.{hpp,cpp}` | 55 KB | 虚拟栈 / 位置分配（R1） |
| `category/vm/runtime/` | ~30 文件 | 运行时上下文、host bridge、storage、memory、call/create |
| `category/vm/interpreter/` | — | 高度优化的解释器（差分对照基准） |

### 5.2 R3：`BasicBlocksIR` 是 `CompilerEVMResult` 的同构对应物

```cpp
struct Block {
    std::vector<Instruction> instrs;   // 非终结指令序列
    Terminator terminator;             // FallThrough/JumpI/Jump/Return/Stop/Revert/SelfDestruct/InvalidInstruction
    block_id fallthrough_dest;
    byte_offset offset;                // 原始 bytecode 偏移
    bool is_valid() const;
    std::tuple<int32_t,int32_t,int32_t> stack_deltas() const;
};

class BasicBlocksIR {
    std::vector<Block> const &blocks() const;
    std::unordered_map<byte_offset, block_id> const &jump_dests() const;
    bool is_valid() const;
};
```

三点意义：

1. 与本框架依赖的块级锚点结构一致，且**带 `byte_offset` 可回溯原始 bytecode**——
   意味着可同时验证 bytecode ↔ IR 与 IR ↔ x86 两段，正好补上 §2.4 指出的前端 gap。
2. 它由 bytecode 直接构造（`BasicBlocksIR(uint8_t const*, code_size_t)`），
   不依赖编译器导出私有格式——验证器可独立重建同一 IR，锚点不需要编译器配合。
3. `is_valid()` 与 `stack_deltas()` 提供现成的良构性谓词与栈高度增量；
   `Terminator` 枚举与本框架终结指令集合几乎一一对应。

### 5.3 R2：`Emitter` 是逐 opcode 模板发射器

```cpp
void push(uint256_t const &);  void pop();  void dup(uint8_t);  void swap(uint8_t);
void add(); void sub(); void mul(int64_t remaining_base_gas); void byte(); void signextend();
void shl(); void shr(); void sar(); void clz();
void and_(); void or_(); void xor_(); void eq(); void iszero(); void not_();
void lt(); void gt(); void slt(); void sgt();
void mload(); void mstore(); void mstore8(); void calldataload();
void gas(int64_t remaining_base_gas);  /* 及全部环境类 opcode */
```

形态与 `impl_amd64.go` 的 `compileEVMxxx` 完全同构 —— 形状可枚举，
slice parser / summary matcher / `shape_id` 缓存范式继续成立。
**模板的具体结构、形状参数化方式与指令表证据见 §3.1**，那里以 `add()` 与 `and_()` 为例做了完整拆解。

注意 `mul` 与 `gas` 携带 `remaining_base_gas` 参数，说明 gas 状态参与指令选择，建模时须一并考虑。

### 5.4 R1：虚拟栈——满足但需扩展映射

```cpp
constexpr uint8_t AVX_REG_COUNT = 16;
constexpr uint8_t GENERAL_REG_COUNT = 3;

struct Literal    { uint256_t value; };                     // 编译期常量
struct StackOffset{ int32_t offset; PrevLoc moved_from; };  // 内存栈槽
struct AvxReg     { uint8_t reg; };                         // 256-bit AVX 寄存器
struct GeneralReg { uint8_t reg; };                         // 64-bit 通用寄存器
```

EVM 栈元素在四种位置间流动，由引用计数的 `StackElem` 管理。相对 go-hpc-evm 的固定地址映射，
这是 R1 上的**弱化但未失效**：

- 位置空间极小（**仅 3 个通用寄存器** + 16 AVX），且分配在编译期完成、可随 IR 导出
- 搬运是显式方法（`mov_stack_index_to_avx_reg` / `..._to_general_reg` / `..._to_stack_offset`），
  spill 点可枚举
- 对比 LLVM 的通用寄存器分配器，这更接近"编译期确定的位置表"而非"需要反推的分配结果"

一个值得写进论文的观察：**uint256 存在单个 256-bit AVX 寄存器里，在 SMT 编码上比 4×64 limb 更简单**
（直接对应 `BitVec(256)`，无需 limb 展开与 carry 链镜像）。
这说明 §3 的 Uint256 桥接层绑定的是"表示选择"而非"方法"，且另一种表示可能降低编码复杂度——
支持把 §3 拆分为"规范"与"表示桥接"两层来陈述。

### 5.5 运行时上下文：profile 机制可直接照搬

```cpp
enum class StatusCode : uint64_t { /* ... */ };
struct Result   { uint8_t offset[32]; uint8_t size[32]; StatusCode status; };
struct Context {
    evmc_host_interface const *host;  evmc_host_context *context;
    int64_t gas_remaining;  int64_t gas_refund;
    Environment env;  Result result;  Memory memory;
    exit_stack_ptr_t exit_stack_ptr;  bool is_stack_unwinding_active;
    constexpr void deduct_gas(int64_t gas) noexcept {
        gas_remaining -= gas;
        if (/* 不足 */) exit(StatusCode::OutOfGas);
    }
};
```

`runtime::Context` 与 `CallEngine` 角色一致；本框架的 `X86AOTProfile.offsets` 机制换一张偏移表即可，
侧信道优化同样成立。memory 扩展成本公式在源码里明写（`(c*c)/512 + 3*c`，c = word count），
可与本框架的 gas 建模直接对照。host 调用走 **EVMC 标准接口**而非私有 ABI，
比 go-hpc-evm 的 func_index 桥接更规范。

### 5.6 一个真实的、值得攻的验证命题

`emitter.hpp` 中：

```cpp
void gas_decrement_static_work(int64_t);
void gas_decrement_unbounded_work(int64_t);
// Arbitrary work threshold for when to emit gas check.
// Needs to be big enough to make the gas check insignificant,
// and small enough to avoid exploitation of the optimization.
```

Monad 把 per-instruction gas 记账折叠成块入口的一次性检查（配合 `terminator_static_gas`），
但**gas check 的发射时机由一个自认 "arbitrary" 的启发式阈值决定**，
注释本身承认它是在"性能可忽略"与"不被攻击者利用"之间取的经验值。

若阈值判断有误，OOG 的**触发时机**会与解释器发散——最终状态可能相同，
但 gas 与 status code 两维可观察行为不同。这正好落在本框架五维等价的强项上，
且是现有测试难以覆盖的类型（需要构造恰好跨越阈值的 gas 边界）。

作为对照，Code4rena 2025-09 对 Monad 的审计已明确把
"differences in execution output between interpreted and JIT-compiled EVM bytecode"
列为关注项——需求是公开承认的。

### 5.7 现成的验证接口

对论文的意义在于：说明本方法所需的输入在一个独立系统上是可得的，不依赖对目标编译器的侵入式改造。

| 设施 | 说明 |
|---|---|
| `MONAD_COMPILER_ASM_DIR=<dir>` | 按合约地址 dump 生成的汇编到文件 —— 直接产出 x86 侧输入 |

## 6. 为什么不做

技术上并非不可行（Monad 即反例）。不做的理由是三条现实取舍，论文可以坦率写出：

1. **不可迁移的其实是领域知识，不是代码。** 本工作最贵的资产不是那 23.5k 行 Python，
   而是对目标 codegen 的一批具体结论——SIGNEXTEND 的 overflow 分支真实缺陷、
   除法路径的分段建模、限定 lemma 的守卫条件。这些全是逐行比对编译器输出攒出来的，
   换目标即归零。工程量可估，知识重建不可估。
2. **纵向的 soundness 缺口优先于横向覆盖。** 当前仍存在：前端 bytecode → IR 未验证（§2.4）、
   call site 顺序匹配假设、部分 x86 summary 只有 matcher 而无 per-hit proof。
   在这些闭合前铺开第二个目标，会让论文的正确性主张更难辩护而非更强。
3. **求解规模已是主要瓶颈。** 生产规模合约的验证已需数小时量级，瓶颈在符号执行阶段的
   表达式膨胀。迁移到结构假设更弱的目标只会让这条曲线更陡。

论文里建议这样表述：不做不是因为方法受限于单一编译器，而是因为**在方法论已被 §3 判据刻画清楚的前提下，
第二个实例带来的边际科学价值低于闭合现有 soundness 缺口**。

| erigontech/silkworm | 用 evmone，无自研 codegen | Apache-2.0，★319，pushed 2025-05-21 |
| geth Go JIT VM（历史） | EVM bytecode → `jit_optimiser` 段融合 → **super-instruction 序列** → 解释执行 | 已删除。**常被误认为出机器码，实际是超指令解释器** |
| geth `vm_jit.go`（历史） | cgo 调 `libevmjit` → 即上面 ethereum/evmjit 那条 LLVM 线 | 已删除；build tag `evmjit`，非默认 |

> geth 的两条历史 JIT 线常被混为一谈，引用时需区分。前者的废弃教训值得写进 Introduction：
> 段融合无法同时保住正确性（gas 记账、tracing、jumpdest 分析）**又**比收紧后的解释器更快——
> 说明"编译后 gas 语义是否保持"是历史上真实拖垮过一个 EVM 编译器的问题，支持 §1.2 把 gas 列为一等等价维。

### 读表要点

**同为"EVM bytecode → x86-64 机器码"，revmc 与 Monad 的可迁移性截然相反**——
差别只在中间那一段是 LLVM 优化管线还是模板发射器。这是 §3 判据存在的直接理由：
管线两端相同不足以判断可迁移性，必须看中间。审稿人的直觉很可能是"都编译到 x86-64，应该差不多"，
这个对比是最直接的反驳。

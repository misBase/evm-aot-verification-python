# 后续可优化的点记录

## 栈域改为 64 位粒度 Array

- 优化方向：把 `STACK` 域从当前的 `Array[BitVec64, BitVec8]` 单独改为 `Array[BitVec64, BitVec64]`，按 64 位 limb 建模。
- 判断：这是当前最直接的内存模型优化点，预期收益最大、风险最低。
- 原因：
  - 栈域的真实访问模式高度规则，绝大多数都是 8 字节对齐的 limb 读写，以及 4 x 64-bit 组成的 256-bit 栈值读写。
  - 当前 stack-check、Go 函数语义、ADD/MUL 等核心算术路径，本来就主要以 64-bit limb 为单位工作。
  - 相比 `CALLENGINE` 域和 `EVM` 域，`STACK` 域更少出现零散 byte 级更新，因此更适合先做粗粒度化。
- 预期收益：
  - 明显减少 `load_64bit()` / `store_64bit()` 展开成 8 次 `Select/Store` 的 AST 体积。
  - 降低栈一致性检查和多 limb 算术程序验证时的求解压力。
  - 有机会继续减少 `Select(Store(...))` 链长度。
- 风险边界：
  - 只能先改 `STACK` 域，不建议把整个 x86 memory 统一切到 64 位粒度。
  - 需要确认是否存在对 `STACK` 域的 byte / 2-byte / 4-byte 非对齐访问；如果存在，需要保留兼容路径或额外的拼接/拆分逻辑。
  - `CALLENGINE` 域仍然包含 `status_code` 这类 byte 字段，`EVM` 域也承担 byte-level 可观察语义，因此它们不适合跟着一起改。
- 建议顺序：
  - 先只改 `STACK` 域。
  - 保持 `CALLENGINE` / `EVM` 仍为 byte-addressed。
  - 补一组回归测试，重点覆盖：
    - 固定栈槽 64-bit 读写
    - 256-bit 栈值读写
    - stack equivalence
    - Go function semantics 中对栈的访问

## 多核并行验证

- 现状：当前程序级验证基本是单进程顺序执行；EVM/x86 公式构建、CFG worklist 探索，以及 `RefinementChecker` 中多次 `solver.check()` 都是串行流程。
- 判断：优先做粗粒度并行，收益更稳定；单个 Z3 query 开线程可以尝试，但不应作为主要提速路径。
- 可选方向：
  - 多测试 / 多合约并行：引入 `pytest-xdist` 或外层 `ProcessPoolExecutor`，把不同 program pair 分发到多个进程。
  - Z3 内部线程：给 `SolverFor("QF_AUFBV")` 设置 `threads=N` 做 benchmark；对数组 + 位向量公式不保证线性加速，可能无收益甚至变慢。
  - obligation 并行：把 return-data 条件、长度、memory、storage、transient storage、stack slot 等独立检查拆成多个进程并行跑。
- 风险边界：
  - 不要在线程间共享同一个 `Solver` / Z3 context；每个 worker 应创建自己的 solver。
  - `set_option()` 是 Z3 全局设置，并行时要避免 verbose/proof 等全局参数互相污染。
  - 若拆分 obligation，需要保留当前 overall timeout 语义，避免每个子检查各自吃满完整预算。
- 建议顺序：
  - 先做多测试 / 多合约级别并行。
  - 再加可配置的 `solver_threads` 并压测典型慢例。
  - 最后再考虑重构 `RefinementChecker` 做 obligation 级并行。

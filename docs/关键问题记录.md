# 关键问题记录
本文档记录了在项目开发过程中遇到的关键问题及其解决方案，旨在为后续的开发、论文等提供参考和指导。

## 1. x86 CFG 在 `ret` 后断开（缺少 Go 往返边）
- 问题：AOT 机器码在 `ret` 处会先跳回 Go 运行时，再从 `exitContext.returnAddress` 恢复到下一段机器码；原 CFG 未建模该往返，导致 `ret` 后续块断开、边数量偏少。
- 根因：执行器把 `ret` 当作直接终止；未识别 `compileCallGoFunction` 指令模式，也未显式建 `ret -> GO_HOST -> returnAddress` 动态边。
- 解决方式：在 `ret` 分支增加 `CallGoFunction` 模式识别（基于 `R13 + status_code/return_address` 写入），命中后动态创建 `CALL/RETURN` 边，并按 `returnAddress` 继续执行；同时为每个站点创建独立 `GO_HOST_n` 节点。
- 结果：`ret` 后控制流可连续，`muti_block*.dot` 能看到 `GO_HOST` 与对应 `call/return` 边，关键跳转边（如 `0x328 -> 0x364`）可在足够执行深度下正确出现。

## 2. 合流点合并优化（X86TopologicalStrategy + merge_buffers）

- **背景**：符号执行默认采用 DFS 策略，路径数随条件分支指数爆炸。对具有菱形控制流的 x86 程序，条件跳转的两条路径最终汇聚到同一基本块，若分别执行会重复计算后续指令的语义，导致 Z3 表达式规模翻倍增长。
- **方案**：在 `X86SymbolicExecutor` 中引入合流点合并优化（`enable_merge=True`），分三部分：
  1. **静态合流点检测**（`_compute_static_merge_points`）：在初始化阶段用拓扑序过滤回边，只统计前向入边数 ≥ 2 的基本块作为合流点，避免循环头被误识别。
  2. **拓扑顺序搜索**（`X86TopologicalStrategy`）：按拓扑序驱动 worklist，保证一个合流点的所有前驱都先于合流点被执行，使 `merge_buffers` 能在主循环内自然收齐。
  3. **状态合并**（`_merge_at_confluence`）：在合流点将多条路径状态用 `If(path_cond, val_A, val_B)` 合并为单一符号状态，后续只需执行一次。
- **两个修复的 bug**：
  - **flush 丢状态**（问题 4）：`_flush_merge_buffers` 处理 flush 产生的后继状态时，非合流点非终止的中间态原来被直接丢弃（欠近似）。修复：新增 `_flush_execute_state` 辅助方法，对此类状态递归继续执行，结果重新派发到 `merge_buffers` 或 `final_states`。
  - **回边导致主循环阻塞**（问题 3）：原 `_compute_static_merge_points` 把回边也计入入边数，循环头的等待计数永远不被满足，主循环跳过该合流点，后续路径全部丢失。修复：`_compute_static_merge_points` 接受 `topo_order` 参数，跳过 `topo_order[src] >= topo_order[dst]` 的回边，`__init__` 中先计算拓扑序再计算合流点。
- **结果**：合并优化可将路径数从指数量级压缩到线性量级（每个合流点只产生一条合并路径），显著降低 Z3 约束复杂度；含循环的 CFG 执行不再阻塞，flush 阶段的中间态不再丢失。

## 3. 跳转目标解析上移到 Go IR 层（避免机器码跳转表干扰 CFG）

- **背景/动机**：如果在机器码阶段再解析跳转目标，往往需要生成 jump table，CFG 构造时容易把跳转表解析成循环或伪分支，造成结构膨胀与误判。
近期提交依据（/Users/june/Work/go/src/github.com/bcds/go-hpc-evm）：
- `05fe32d`（2026-03-12）：`CompileEVM` 改为调用 `resolveSymbolicJumps`，并注明“在返回前解析所有可支持跳转目标为静态形式”，表明跳转解析在 Go IR 阶段完成。
- `a8a7cb9`（2026-03-12）：增强符号跳转分析（`const_set`/条件处理），提升 Go 层可解析目标的覆盖率。
- `f6199da`（2026-03-13）：符号解析改为路径敏感 worklist，收集 `resolvedJumps` 并在 `applySymbolicResolutions` 中写回 `ImmediateSet`，仅在解析仍不可得时才报动态跳转错误。
- **记录结论**：当前机器码编译是在跳转目标解析之后进行的；JUMP/JUMPI 的目标在 Go IR 层已解析并写入 `ImmediateSet`，避免机器码生成 jump table，从而减少对 CFG 构造的干扰（尤其是跳转表被误解析为循环的风险）。

## 4. Host Func Index 固定为 ABI 常量表

- **背景/动机**：AOT 编译器将 EVM 的 host 操作（如 SHA3、SLOAD、SSTORE、CALL 等）编译为 x86 机器码中的 Go bridge 块，通过 `mov dword [r13+0xe8], <func_index>` 嵌入函数索引，`ret` 回 Go 运行时后由 `evmExitContext.goFunctionCallIndex` 查表分发。原实现中 func_index 依赖 Go `map` 迭代顺序分配（`CompileEVM` 中遍历 `e.hosts.Hosts`），导致：
  1. 不同合约的同一 host 函数可能获得不同 index，Python 侧无法建立通用映射。
  2. Go `map` 迭代顺序不确定，同一合约重复编译可能产生不同 index，验证结果不可复现。
  3. Python 侧需要"按合约手动配置 `host_functions` 映射"，增加使用负担且易出错。

- **Go 侧改动**（go-hpc-evm `c87c1d7`，2026-04-15）：
  - 新增 `HostSpec{ID int64, Name string}` 结构和 `builtinHostSpecs` 固定目录（1..19）。
  - `CompileEVM` 改为遍历 `DefaultHostSpecs()` 而非 `e.hosts.Hosts` map，确保 func_index 编译时确定。
  - 固定表：`1=sha3, 2=call, 3=callCode, 4=delegateCall, 5=staticCall, 6=create, 7=create2, 8=selfDestruct, 9=sload, 10=sstore, 11=balance, 12=selfBalance, 13=extCodeSize, 14=extCodeCopy, 15=extCodeHash, 16=blockHash, 17=log, 18=tload, 19=tstore`。

- **Python 侧改动**：
  - `x86_64/aot_profile.py`：`GO_HPC_EVM_PROFILE.host_functions` 从空字典改为上述固定映射；新增 `resolve_host_function_name(func_index)` 和 `resolve_builtin_function_name(func_index)` 统一解析入口。
  - `x86_64/go_function_semantics.py`：分发逻辑改用 `resolve_host_function_name()`，错误信息更新为"not defined by the active go-hpc-evm host ABI table"。
  - `verification/call_site_mapping.py`：同理改用统一解析入口，错误信息对齐。
  - 测试：所有 host 函数测试从合成 index（如 `{0: "sload"}`）改为真实固定 index（如 `{9: "sload"}`），确保与实际 AOT 产出一致。

- **记录结论**：host func index 现为固定 ABI 常量，Go/Python 两侧共享同一映射表。形式化验证不再需要按合约手动配置 `host_functions`，验证结果可复现。该固定表应作为 go-hpc-evm 的 ABI 约束维护，新增 host 函数时须同步更新两侧。

## 5. callEngine 字段 side-channel（Z3 穿透 Store 链导致验证极慢）

- **问题**：x86 语义执行器对 `[R13+offset]` 的写入只更新 `x86_memory` 字节级 Array；后续读取（如 `ret` 处读 status_code、读 stack_pointer）需要通过 `load_byte` / `load_64bit` 穿透整个 Store 链（所有已执行过的字节级写入）才能还原出值。Z3 对符号基址（R13 是符号变量）的 Array 别名分析代价极高，导致 `ret` 处的 return 条件公式体积爆炸，验证时间从秒级变为分钟级甚至超时（`test_verify_add_program_pair` 在此前慢数十倍）。

- **根因**：Z3 的 Array theory 在处理 `Select(Store(...Store(arr, addr_n, v_n)..., addr_1, v_1), query_addr)` 时，若 `query_addr` 与各 `addr_i` 的大小关系不能被静态判定（符号地址），必须逐层展开 Store 做别名分析，复杂度随 Store 链深度线性增长，在含大量 callEngine 写入的完整程序中代价极高。

- **解决方式**：为 `SMTState` 新增一组显式 BitVec 字段作为 side-channel（`callengine_status_code`、`callengine_stack_pointer_limbs`、`callengine_stack_byte_offset`、`callengine_return_address` 等）。在 `x86_instruction_to_z3` 中，识别到 `mov [R13+KNOWN_OFFSET], value` 时，除写入 `x86_memory` 外，同步调用 `_maybe_update_callengine_field()` 写入对应 side-channel 字段；读取时 `_maybe_read_callengine_field()` 直接返回 side-channel 值，绕过 `x86_memory`。`ret` 处的 status_code 和 sp 读取改为直接读 side-channel 常量（ADD 程序中为 `BitVecVal(2, 8)` 和 `BitVecVal(-4, 64)`），彻底消除对 Store 链的穿透。

- **结果**：`ret` 处的 return 条件公式从深度嵌套的 Array Select 表达式变为对常量的简单比较，Z3 求解负担大幅降低。`test_verify_add_program_pair` 验证速度显著提升（秒级）。side-channel 的正确性依赖"所有写 `[R13+offset]` 的指令都命中 `_CALLENGINE_FIELD_MAP`"这一不变式，当前覆盖 `mov`、`add`、`shl`、`shr` 四类写内存指令。

## 6. x86 内存拆分为三域（callengine / stack / evm）

- **问题**：旧版 `X86MemoryState` 只有一个全局 `Memory: Array[BV64, BV8]`，三种物理上完全不重叠的内存区域——通过 R13 访问的 callEngine 结构体、通过 R14 访问的 EVM 栈窗口、通过 R15 访问的 EVM 256-bit memory——共享同一 Z3 Array。在 Z3 中，共享同一数组时，任意写操作都会在后续所有读操作的 Store 链中累积。对 SHA3/SLOAD/CALL 等操作，Go 函数调用前后会连续读写三种域，导致 SHA3 语义中 `evm_mem` 包含了 callEngine 和栈域的 Store 噪声，与 EVM IR 侧的纯 `evm_memory` Array 无法等价（`test_verify_muti_block_*` 失败的根本原因）。

- **根因**：单一 Array 对 Z3 是"有记忆的"——写入 `[R13+0x28]`（sp 字段）和写入 `[R15+offset]`（EVM memory）落在同一个 Array 里，Z3 的 `Select` 无法直接排除地址不重叠的可能性（地址是符号的），必须展开所有 Store 做别名分析，导致 SHA3 / MSTORE / CALL 场景下公式膨胀。

- **解决方式**：将 `X86MemoryState` 拆分为三个独立 Z3 Array：
  - `call_engine_mem`：仅接受 base_reg=R13 的访存
  - `stack_mem`：仅接受 base_reg=R14 的访存
  - `evm_mem`：仅接受 base_reg=R15 的访存

  所有 `load_*/store_*` 强制传入 keyword-only 的 `domain: MemoryDomain` 参数，无默认值；`_classify_domain(base_reg)` 在语义层静态路由。无法路由的访存（base_reg ∉ {R13,R14,R15}）抛 `MemoryDomainError`，测试桩可设 `unrouted_memory_domain` 兜底到 STACK 域。SHA3/CREATE/CALL 等 host 函数只读写 `evm_mem`，彻底消除三域之间的 Store 链交叉。

  同时引入 `PointerTag` 枚举跟踪寄存器的 provenance（CALLDATA_PTR / CODE_PTR / RETURNDATA_PTR / EVM_PTR / STACK_PTR），用于将 `[reg+offset]` 形式的间接访存（base_reg 不是 R13/R14/R15，而是从 callEngine 字段加载的指针）路由到正确域。

- **结果**：SHA3 语义从全局 `x86_memory.Memory` 改为只读 `x86_memory.evm_mem`，与 EVM IR 侧的 `evm_memory` 对齐，在结构上消除了之前三域混写导致两侧 SHA3 读不同 Array 的问题。`test_verify_muti_block_*` 目前标记为 `@pytest.mark.skip(reason="Not impl well")`，尚未验证三域拆分后能否通过完整验证。

## 7. returndata / code / calldata 的符号化建模

- **问题**：旧版 `SMTState` 没有独立的 `return_data`、`code`、`calldata_ptr`（code_ptr / input_ptr）字段，相关内容全部混写在全局 `x86_memory.Memory` 中。CALL / CALLCODE / DELEGATECALL / STATICCALL 等指令执行后产生的 return data 无处存放；CALLDATACOPY / CODECOPY 在做字节搬运时也是操作全局内存，与三域拆分后的语义不兼容。

- **解决方式**：
  - `SMTState` 新增 `return_data: Array[BV64, BV8]` 和 `code: Array[BV64, BV8]` 字段，以及六个 callEngine side-channel 字段（`callengine_input_pointer`、`callengine_input_size_bytes`、`callengine_code_pointer`、`callengine_code_size_bytes`、`callengine_return_data_pointer`、`callengine_return_data_size_bytes`）。
  - `aot_profile.py` 补全对应的 callEngine 偏移（`input_pointer=0x90`、`input_size=0x98`、`code_pointer=0xA0`、`code_size=0xA8`、`return_data_pointer=0xB0`、`return_data_size=0xB8`）。
  - `GoFunctionSemantics` 新增 `_update_return_data_source()` 辅助方法：CALL/CALLCODE/DELEGATECALL/STATICCALL 执行后用 `Lambda` 表达式更新 `mstate.return_data`，同步写回 callEngine side-channel 中的 return_data_pointer 和 return_data_size。
  - `PointerTag` 追踪从 callEngine 加载的指针（EVM_PTR / STACK_PTR / CALLDATA_PTR / CODE_PTR / RETURNDATA_PTR），使 `[reg+offset]` 形式的间接访存能路由到正确域（如 CALLDATACOPY 用 input_ptr 写 evm_mem）。
  - Go 函数调用后调用 `_clear_caller_saved_pointer_tags()` 清空 caller-saved 寄存器的 tag，避免跨调用的 tag 错误传播。

- **结果**：return data / code / calldata 拥有独立的符号化 Array，访存路由按 provenance 而非仅靠 base_reg 决定，为后续 RETURNDATACOPY / CODECOPY / CALLDATACOPY 的形式化建模提供了正确的状态载体。

## 8. 终止路径 Observation 直接检查（避免先合并完整终态 Array）

- **问题**：旧版 program-level 等价性检查会先把所有终止路径的完整 `SMTState` 合并成一个总状态，再从总状态中提取返回值、内存、storage 等 observable。这个合并会对大对象（尤其是 `Array[BV64, BV8]` 的 memory、`Array[BV256, BV256]` 的 storage/transient storage、x86 寄存器集合）构造大量 `If(path_cond, array_path_i, array_path_j)`。一旦某条路径内部已经包含复杂 byte-level `Select/Store/ITE`，外层 Array 合并会把公式再包一层路径 ITE，导致 Z3 需要同时处理“路径选择 + Array extensionality + bit-vector arithmetic”的组合爆炸。

- **典型触发场景**：`CALLDATALOAD` 在符号 offset 下，本身就会产生 32 个字节级 `Select(calldata, offset+i)` 和越界补零 ITE。如果该值继续参与后续 memory / return-data 计算，再在 CFG 终态层把 x86 多条 terminal path 的完整 memory / storage / register state 合并起来，Z3 看到的就不是“某条路径上的局部 observable”，而是“路径 ITE 包起来的一整套终态 Array”。这会把原本的 byte-level 难题放大成路径级 Array 合并难题。

- **根因**：对程序等价性而言，真正需要比较的是每条终止路径对外可观察结果，而不是整份机器终态。旧做法相当于先构造：

  ```text
  merged_state = If(cond_0, state_0, If(cond_1, state_1, ...))
  check observable(merged_state)
  ```

  这会强迫 Z3 构造并化简完整终态的 Array ITE。实际上，只要每个输入都落在某条 EVM 终止路径和某条 x86 终止路径上，并且在二者路径条件交集下 observable 相等，就足以证明等价：

  ```text
  coverage:  Or(evm_cond_i) == true, Or(x86_cond_j) == true
  pairwise:  for all i,j. evm_cond_i && x86_cond_j => obs_evm_i == obs_x86_j
  ```

- **解决方式**：引入“终止路径 observation”作为正式检查对象，为 program-level equivalence check 提供一条不合并完整终态的检查路径。

  1. `EquivalenceChecker.check_equivalence_paths()` 新增 path-observation 检查流程：
     - 先检查 EVM/x86 terminal path 条件是否覆盖全部输入；
     - 对 EVM path 与 x86 path 做两两交集；
     - 对交集 UNSAT 的 path pair 直接跳过；
     - 对 SAT 或 UNKNOWN 的 pair，带着 `path_condition = evm_cond && x86_cond` 调用原来的 return-data / memory / storage / transient-storage 检查；
     - UNKNOWN feasibility 不剪枝，按可能可达处理，保证不因 solver 不确定而欠近似。

  2. `ProgramEquivalenceChecker` 保留旧 merged-result 路径作为默认行为，同时提供 path-observation mode：
     - 默认 `path_observations=False`，继续调用两边 program 的 `to_z3()` merged-result API；
     - 显式 `path_observations=True` 时调用两边 program 的 path API；
     - path-observation 主 等价性检查直接使用 `PathObservation` 列表；
     - path-observation 下 `stack_check=None` 时完全不构造 merged state；
     - 只有 debug 用的 `stack_check` 打开时，才请求 `merge_state=True` 作为 fallback。

  3. `EVMProgram` / `X86Program` 增加正式 `to_z3_paths()` API：
     - 返回 `PathSemantics(global_states, observations, merged_state)`；
     - EVM 侧负责执行 EVM CFG 并提取 `offset/length/memory/storage/transient_storage`；
     - x86 侧负责 instruction/block 识别、CFG execution、sequential/no-CFG fallback，并提取对应 observable；
     - `merged_state` 仅在调用方显式要求时生成。

  4. 新增中立结构 `common/path_observation.py`：
     - `PathObservation` 固定字段：`condition, offset, length, memory, base_addr, has_return_data, storage, transient_storage`；
     - `PathSemantics` 表示一次 path-sensitive execution 的结果；
     - `PathObservation` 保持 dict-like `.get()` / `[]` 兼容，避免 `EquivalenceChecker` 大规模重写。

- **正确性直觉**：旧的 merged-state 检查和新的 path-observation 检查在路径覆盖完整时是等价的。对任意输入，EVM 执行会满足至少一个 `evm_cond_i`，x86 执行会满足至少一个 `x86_cond_j`；这个输入因此落在某个交集 `evm_cond_i && x86_cond_j` 中。若所有可行交集下 observable 都相等，则该输入下两边 observable 相等。反过来，若某个可行交集存在 observable 不等，`check_equivalence_paths()` 会在对应 pair 的带条件检查中找到反例。不可行交集跳过是安全的，因为没有输入能同时满足两边路径条件。

- **复杂度变化**：
  - 旧做法：先构造完整终态合并，Array ITE 数量随 terminal path 数增加，后续每个 observable 读取都可能穿透合并后的 memory / storage / register 表达式。
  - 新做法：最坏检查 `m * n` 个 EVM/x86 path pair，但每个 query 只比较一对未合并 terminal observation；不可行 pair 先用轻量 feasibility check 剪掉。
  - 对多路径程序，公式体积从“先构造一个巨大的 merged Array state”变成“按 path pair 局部证明”，通常更适合 Z3 的 incremental 小 query。

- **实测效果**（2026-05-19，单轮 wall-time 对照，`timeout_ms=30000`）：
  - 小程序场景收益不明显，部分还会略慢：`add_raw_stack` 从 `0.031s` 变为 `0.050s`，`mstore_return` 从 `0.057s` 变为 `0.061s`，`three_block_return` 从 `0.101s` 变为 `0.105s`。这些场景路径数少，或者仍启用了 stack check，需要请求 `merged_state` fallback，因此 path-pair 检查的固定开销盖过了省下的合并成本。
  - 简单分支场景有小幅收益：`jumpi_2block_ok_fixed1` 从 `0.233s` 降到 `0.220s`，约 `1.06x`。
  - 固定 ABI size 的真实程序收益更明显：`test_verify_perf_erc20_lite_program_pair` 在 `calldata_size_bytes=68` 时，从旧 merged check 的 `2.623s` 降到 path-observation check 的 `2.002s`，约 `1.31x`。该场景有 `6` 条 EVM terminal path、`7` 条 x86 terminal path，只有 `7/42` 个 path pair 可行，新流程能跳过大量不可行交集，避免先构造完整 merged Array 终态。
  - 全符号 calldata size 仍然不可用：去掉 `calldata_size_bytes=68` 后，两种模式都超时。path-observation check wall time 约 `207.9s`，旧 merged check 约 `232.8s`，虽然略快但仍返回 `TIMEOUT`。这说明当前优化只削掉了外层终态合并的放大项，没有解决全符号 calldata / `CALLDATALOAD` 的核心 SMT 难题。

- **局限性**：
  - 该优化解决的是“外层 CFG 终态合并导致的 Array/ITE 放大”，并不消除 `CALLDATALOAD` 在符号 offset 下的内层 byte-level `Select + ITE` 本质复杂度。它能避免路径合并把 CALLDATALOAD 变得更慢，但不能让全符号 `CALLDATALOAD` 自动变快。
  - 新流程的最坏复杂度是 `m * n` 个 path pair。若两侧 terminal path 很多且 feasibility check 不能剪掉足够多不可行 pair，小 query 的数量也会成为瓶颈。
  - 对单路径或路径很少的程序，新流程可能只有额外调度成本，没有明显公式缩减；这类场景可以考虑后续做 adaptive 选择：多路径且不需要 stack check 时优先 path observation，否则保留 merged check。
  - `stack_check` 打开时仍需要 `merged_state` fallback，此时不能完全避免终态合并成本。

- **记录结论**：program-level 等价性检查现在拥有“terminal path observation”作为可选检查对象，默认仍保留旧的 merged-result 行为以降低回归风险。该优化可以把验证目标从“大 Array 终态合并后的全局等式”改写为“覆盖完整的 path pair 局部等式”，在保持健全性的同时降低 CFG 多路径场景下的 Z3 公式膨胀风险。它是有价值的结构性优化，但不是全符号 calldata / `CALLDATALOAD` 性能问题的主解法；后续主要性能突破应转向 calldata 建模本身，例如 word-level calldata、byte-select 规范化、或对 ABI selector/size 的路径条件做更强归约。

## 9. `CALLDATALOAD` summary 放宽动态 low offset，并在 apply 阶段加安全 guard

- **问题**：`CALLDATALOAD` 的 x86 summary 用来把 go-hpc-evm amd64 输出中的一整片 `compileEVMCALLDATALOAD` 机器码折叠成共享语义 `common.calldata.calldataload_word(...)`。旧 matcher 要求 offset 的低 64-bit limb 必须在 discovery 阶段就是静态常量；如果 low limb 表现为寄存器或栈位置，即使当前符号状态下它实际可化简为 ABI 常量（如 `4 + 32`、`4 + 64`），也会直接拒绝 summary。真实样本中这种“链式编译出来的 ABI offset”常出现在 block 中段 summary 起点，导致可安全折叠的 `CALLDATALOAD` slice 不能命中 summary，回到大段逐指令语义，增加 path-observation / storage 证明压力。

- **根因**：matcher 阶段只看 x86 slice 的静态形状，不携带执行到该 block-middle 起点时的寄存器/栈符号状态。`RegisterLimbLocation(RAX)` 这类 low limb 在 discovery 阶段不是常量，但在 apply 阶段可能已经由前缀指令写成具体值。若 discovery 阶段一刀切拒绝，会损失可证明安全的 summary 命中；若无条件接受，又可能把真正符号 offset 或接近 `2^64` 的 offset 错误折叠，和 x64 slice 中 `offset + 32` 的 64-bit 回绕行为产生未证明差异。

- **解决方式**：将“是否允许动态 low offset”的判定拆成两阶段：
  1. **discovery 阶段放宽 matcher**：`_requires_concrete_low_offset(low_loc)` 对 `ConstLimbLocation` 仍做静态安全检查；若常量大于 `UINT64_MAX - 32`，立即拒绝，因为 x64 的 `offset + 32` 会回绕。若 low limb 不是常量，不再直接拒绝，而是返回 `True`，在 `CallDataLoadSummary.require_concrete_offset` 上记录“apply 时必须化简为安全常量”。
  2. **apply 阶段运行时 guard**：`apply_calldataload_summary()` 先用 `offset_expr_from_locations()` 从四个 limb 重建 256-bit offset。若 `require_concrete_offset=True`，必须满足：
     - `simplify(offset_bv)` 后是 Z3 bit-vector 常量；
     - 常量值 `<= UINT64_MAX - 32`，保证 x64 slice 的 `offset + 32` 不会 64-bit 回绕。

  通过 guard 后，代码把 offset 规范化成 `BitVecVal(concrete_value, 256)`，再调用共享 `calldataload_word(...)`；不通过则抛 `CallDataLoadSummaryMatchError`，fail closed。这里的“运行时”指验证器应用 summary 的符号执行时刻，不是 EVM 链上运行时。

- **健全性（soundness）边界**：
  - summary 只在 offset 能在当前状态下化简为安全常量时使用；真正符号 offset 不会被该动态-low-offset summary 偷偷抽象掉。
  - `UINT64_MAX - 32` guard 对齐 x64 slice 的实现细节：机器码会先做 64-bit `offset + 32` 再判断 fast/partial path。超过该上界时，机器码分支可能受回绕影响，而共享 Go/EVM `getData(input, offset, 32)` 语义不建模这种回绕，因此必须拒绝。
  - apply 阶段抛错是可诊断的 fail-closed；当前执行器没有在 apply 失败后自动恢复逐指令执行，因此这不是“静默 fallback”，而是避免不安全 summary 继续参与证明。
  - 该机制仍处在 `TRUSTED_SUMMARY_CONFIG` 信任边界内：matcher + guard 只说明 slice 形状和 offset 前提适合折叠，不能替代未来应补的局部 proof artifact。

- **结果**：`CALLDATALOAD` summary 能覆盖更多真实 AOT 形状，尤其是 ABI 参数 offset 经前缀指令计算后存放在寄存器/栈位置的 block-middle summary。单测 `test_matcher_guards_dynamic_low_offsets_for_wrap_soundness` 记录了 `muti_block_08.hex` 中这类动态 low offset：summary discovery 可发现这些候选，但它们都带 `require_concrete_offset=True`，必须在 apply 阶段通过 concrete + non-wrapping guard 才能使用。

- **记录结论**：这是一次“扩大可匹配形状，但把正确性条件推迟到有状态时检查”的优化。它解决的是 matcher 过早拒绝安全动态 low offset 的覆盖率问题，不是放宽 `CALLDATALOAD` 语义本身；所有不确定情况仍按 fail-closed 处理。

## 10. `CALLDATALOAD` ABI word 抽象模式（去除参数 word 的 calldata-size 依赖）

- **问题**：完整字节级 `CALLDATALOAD` 语义会把返回 word 展开成 32 个字节：

  ```text
  Concat(
    If(offset + 0 < CallDataSize, CallData[offset + 0], 0),
    ...
    If(offset + 31 < CallDataSize, CallData[offset + 31], 0),
  )
  ```

  对 ABI 参数读取（如 `CALLDATALOAD(4)`、`CALLDATALOAD(36)`、`CALLDATALOAD(68)`）来说，这些字节级 `CallDataSize` guard 会继续进入 storage key/value、mapping key、return memory 等表达式。Storage 等价检查随后不得不围绕 `CallDataSize` 做分区或处理大量 ITE，导致 `muti_block` 这类真实样本的 storage/等价性查询极慢。

- **根因**：程序等价性通常只需要证明 EVM IR 侧和 x86 侧对同一个 calldata word 产生同样 observable；对 ABI 参数 word 而言，具体的“短 calldata 时逐字节补零”细节并不总是后续证明的关键。把每个 ABI word 展成 32 个 byte-level guard，会把一个本可视为输入 word 的值变成一棵依赖 `CallDataSize` 的大表达式，并把 size 分支传播到 storage 公式深处。Selector 读取则不同：dispatcher 分支依赖 calldata 前 4 字节，必须保持字节精确。

- **解决方式**：在共享 helper `common.calldata.calldataload_word(..., abstract=True)` 中增加 word-level 抽象模式。该 helper 被 EVM IR 侧和 x86 `CALLDATALOAD` summary 侧共同调用，因此只要两侧传入同样的 `calldata / offset / abstract` 参数，就会生成同一个抽象 term。

  建模时先把 offset 的低 64 位 `simplify`，尝试判断是否为 concrete offset，然后按构造期信息分三类：

  1. **concrete offset < 4：selector 区域，不抽象**
     - `should_abstract=False`，继续走字节级精确读取。
     - 这保留 dispatcher 依赖的 `CallData[0..3]` 和必要的 calldata-size guard。
     - “offset < 4” 是 Python 构造 Z3 AST 时的选择条件，不会额外作为 path condition 注入 solver。

  2. **concrete offset >= 4：ABI 参数 word，抽象成不含 size 的 UF**
     - 返回 `calldataload_word(CallData, 0, offset_64)`，即第二个参数故意填 `BitVecVal(0, 64)`，不传真实 `CallDataSize`。
     - 这把 ABI 参数建模为独立的 256-bit word-level 输入，避免 storage key/value 残留 `CallDataSize` 依赖。
     - 该分支是主要性能优化点：它不是把非抽象字节级分支里的 guard 化简掉，而是让 ABI 参数读取根本不进入字节级展开。

  3. **symbolic offset：抽象但保留整体越界 guard**
     - 返回 `If(CallDataSize <= offset_64, 0, calldataload_word(CallData, CallDataSize, offset_64))`。
     - 因为 offset 不是 concrete，无法判断它是否是 ABI 参数位置；同时真实语义要求 `offset >= calldatasize` 时整体返回 0，所以保留这一层 guard。

- **非抽象分支的顺带优化**：当不能抽象、但 offset 是 concrete 时，字节级模型直接生成：

  ```text
  If(concrete_offset + i < CallDataSize, Select(CallData, concrete_offset + i), 0)
  ```

  不再先构造 `effective_start = If(CallDataSize < offset, CallDataSize, offset)` 和 `remaining = CallDataSize - effective_start` 这组符号算术。该分支仍然含有 `CallDataSize`，只是表达式更短；真正去掉 size 依赖的是上面的 concrete ABI offset 抽象分支。

- **健全性（soundness）边界**：
  - concrete ABI offset 的抽象是 over-approximation：真实短 calldata 会产生零填充 word，抽象后该 word 可以是任意 256-bit 值。若在更大的输入空间上证明 EVM/x86 等价性成立，则对真实 calldata 子集也成立。
  - 该论证依赖 EVM IR 侧和 x86 summary 侧使用同一个共享 helper、同名 UF、同实参；如果一侧抽象、一侧不抽象，或一侧把 `CallDataSize` 放进 UF 而另一侧不放，等价证明会失去结构对齐。
  - selector 不抽象是必要限制；否则可能把 dispatcher 路径条件也变成任意 word，破坏路径覆盖和分支可行性判断。
  - symbolic offset 仍保留 size guard，是对无法识别 ABI 参数位置时的保守处理。

- **组合证明中的证明义务**：
  - ABI word UF 抽象不是要证明 `calldataload_word(CallData, 0, offset)` 等于真实逐字节补零语义；它是 over-approximation。需要说明真实 calldata 产生的 word 属于任意 256-bit word 的子集，因此在更大抽象输入域上证明 EVM/x86 等价，蕴含真实 calldata 输入上的等价。
  - 该抽象成立依赖两侧共享同一 helper、同名 UF、同实参；selector 区域保持字节精确；symbolic offset 保留必要越界 guard；`abstract_calldataload_words` 在 state copy / merge 后保持一致。
  - x86 `CALLDATALOAD` summary 是另一类义务：它把一段机器码 slice 替换成 `calldataload_word(...)`，因此需要局部 lemma 证明 recognized slice 在 matcher/guard 前提下实现共享语义。当前这部分仍属于 `TRUSTED_SUMMARY_CONFIG` 信任边界。
  - 局部 lemma 至少应覆盖：high-limb overflow / offset 越界的 zero path、fast path 的 qword load + bswap + stack store、partial path 的逐字节 copy + zero padding、`offset + 32` non-wrapping guard、目标 stack slot 和 clobber 声明。

- **开关传播**：
  - `SMTState.abstract_calldataload_words` 默认 `False`，不影响既有精确模型。
  - `SMTState.copy_verification_options_to()` 在 state copy / x86 merge 时复制 `abstract_calldataload_words` 和 `assume_calldata_offset_no_overflow`，保证 fork/merge 后所有路径继续使用一致的建模旋钮，避免同一验证中出现部分路径抽象、部分路径不抽象的 UF 不对齐。
  - `SMTState.create_initial_state(..., calldata_size_max_bytes=...)` 可额外加入 `ULE(CallDataSize, max)` 假设。`muti_block` 测试使用 `GO_AMD64_MAX_SLICE_LEN = (1 << 63) - 1`，对应 Go amd64 slice 长度上界；该上界作为验证 precondition 进入覆盖和 等价性检查，排除 Go 运行时不可能出现的 calldata 长度。

- **与第 9 节 summary guard 的关系**：
  - 第 9 节解决的是 x86 侧“这段机器码能不能安全折叠成 `CALLDATALOAD` summary”，发生在 `x86_64/summaries/calldataload.py` 的 discovery/apply 阶段。
  - 本节解决的是“已经要建模 `CALLDATALOAD` 后，`calldataload_word()` 生成什么 Z3 表达式”，发生在 `common/calldata.py` 的共享语义 helper 内。
  - 前者提高 summary 命中覆盖率，后者降低命中后以及 EVM IR 侧共同生成的 calldata word 表达式复杂度；两者配合使用，但不是同一层优化。

- **记录结论**：`CALLDATALOAD` 抽象模式把具体 ABI 参数读取从 32-byte 精确展开替换为共享 word-level UF，核心收益是阻断 `CallDataSize` guard 向 storage key/value 传播。它保留 selector 字节精确性，并对 symbolic offset 保留必要越界 guard；因此这是一个有边界的 over-approximation，而不是全局去掉 calldata-size 语义。当前实现对 ABI word 抽象给出的是 over-approximation 健全性论证；对 x86 summary 正确性仍依赖 `TRUSTED_SUMMARY_CONFIG`，未来应由 proof artifact / local lemma 补齐。

## 11. PathCoverageCertificate（路径覆盖 by-construction 证书）

- **问题**：path-observation 等价性检查不再先合并完整终态，而是比较一组 terminal path observations。该检查 sound 的前提是两侧 terminal path 条件覆盖所有允许输入。旧实现只能用 SMT 查询：

  ```text
  Not(Or(path_condition_0, path_condition_1, ...))
  ```

  若该查询 UNSAT，说明不存在未覆盖输入。但真实程序的 path condition 往往包含 selector 分支、x86 flag 表达式、merge 产生的 ITE、calldata/storage 相关条件，覆盖查询本身可能 timeout/unknown。更重要的是，x86 executor 如果因为 depth limit、外部跳转、worklist 未排空等原因没有探索完所有后继，旧流程缺少一个明确的结构化信号来说明“路径枚举本身可能不完整”。

- **根因**：路径覆盖有两类信息来源：
  1. **语义条件层面**：`Or(path_conditions)` 是否覆盖输入域，可由 SMT 查询判断。
  2. **执行器结构层面**：符号执行是否确实遍历了所有建模控制流后继，可由 executor 自身记录。

  旧流程只使用第 1 类信息，导致覆盖检查既贵，又不容易区分“SMT 解不动”和“executor 探索不完整”。对于 x86 CFG 这种显式枚举控制流后继的执行器，很多情况下覆盖性可以由构造过程直接给出，而不必每次再让 Z3 反推。

- **解决方式**：引入 `PathCoverageCertificate`，作为 `PathSemantics` 的一部分随 terminal observations 一起返回：

  ```text
  complete: bool
  reason: str
  source: str
  details: tuple[(key, value), ...]
  ```

  证书有两种核心状态：
  - `PathCoverageCertificate.by_construction(...)`：执行器确认已经探索完所有建模后继，覆盖性可由构造过程给出。
  - `PathCoverageCertificate.unknown(...)` 或 `complete=False`：没有证书，或探索过程中出现可能漏路径的情况。

- **x86 executor 如何生成证书**：
  - `X86SymbolicExecutor.path_coverage_certificate()` 汇总执行统计和不完整原因。
  - 若没有不完整原因，返回 `complete=True`，reason 为 `x86 CFG executor explored all modeled successors`。
  - 若发现任何可能漏路径的迹象，返回 `complete=False`，并把原因写入 `reason`。当前 fail-closed 标记包括：
    - depth pruning / flush depth limit；
    - work-list 未排空；
    - merge buffer 未排空；
    - state 没有 CFG node；
    - 无法解析的 jmp / conditional target；
    - jmp 或 conditional target 跳出本地 CFG；
    - conditional fallthrough 离开本地 CFG；
    - GO bridge ret 无静态返回目标或返回目标在本地 CFG 外。

- **checker 如何消费证书**：
  - `EquivalenceChecker.check_equivalence_paths()` 在检查 EVM/x86 path pair 前，先调用 `_check_path_coverage()`。
  - 若传入的 coverage certificate `complete=True`，直接认为该侧 terminal paths 覆盖完整，跳过 SMT 覆盖查询，verbose 下打印 `by-construction`。
  - 若 certificate 缺失或 `complete=False`，不会放行；checker 回退到旧 SMT 查询 `Not(Or(*conditions))`。
  - 回退 SMT 查询只有 UNSAT 才算覆盖成功；SAT 报未覆盖反例，UNKNOWN/TIMEOUT 仍然失败。这保持 fail-closed。

- **coverage precondition 的串接**：
  - path-observation 模式会收集执行过程中累积的 assumptions，例如 calldata size 上界、`CALLDATALOAD` offset no-overflow 假设。
  - 覆盖检查应在这些 assumptions 约束的输入域内进行，而不是无条件全输入域。
  - 因此 `ProgramEquivalenceChecker` 额外构造 `coverage_precondition = And(True, *path_assumptions)`，并传给 `_check_path_coverage()`；回退 SMT 时检查的是：

    ```text
    coverage_precondition && Not(Or(path_conditions))
    ```

  - 这样不会因为被 precondition 排除的输入而误报“路径未覆盖”。

- **健全性（soundness）边界**：
  - 证书只证明“执行器探索了所有未被证不可达的建模控制流后继”，不证明每条 x86 指令语义正确，也不证明 host-call / summary / UF 抽象正确。
  - 对 `CALLDATALOAD` summary、ABI word UF、SHA3 UF 等抽象，仍需要各自的 trusted boundary、over-approx 健全性论证或未来的局部 proof artifact。
  - `complete=True` 跳过的只是 terminal path coverage SMT 查询，不跳过后续 path pair observable equivalence、storage/memory/return-data 等等价检查。
  - `complete=False` 时回退 SMT，而不是直接接受证书；如果 SMT 也无法证明覆盖，则整个 等价性检查失败。

- **结果**：在 CFG executor 能确认自己完整探索的场景下，terminal path coverage 检查从一个可能昂贵的 SMT 查询变成 0 秒的 by-construction 判断；在探索不完整或不确定时，又能带原因回退到原 SMT 覆盖检查。该优化同时提升性能和可诊断性，尤其适合 path-observation 模式下 terminal path 数多、path condition 大的真实程序。

- **记录结论**：`PathCoverageCertificate` 是路径枚举完整性的证书，不是语义正确性证书。它把“是否探索完所有建模后继”从隐式假设变成显式、可记录、fail-closed 的输入：完整时省掉覆盖 SMT 查询，不完整时给出原因并回退原检查。

## 12. Storage 等价检查增强（结构快路径 + 分治 SMT）

- **问题**：storage 等价性检查本质是在证明两侧最终 storage array 完全相等，即不存在某个 key 使得：

  ```text
  Select(evm_storage, key) != Select(x86_storage, key)
  ```

  真实路径中的 storage 表达式通常包含多层 `Store(...)`、path merge 产生的 `If(...)`、`CALLDATALOAD` 带来的 calldata-size guard、mapping key 的 256-bit 表达式以及 array theory。直接把完整 mismatch 查询交给 Z3，容易在 `muti_block` 这类多路径样本上 timeout。

- **解决方式**：在 `verification/equivalence_storage.py` 的 `_check_storage_equivalence_with_solver()` 中，把 storage 等价检查改成“先结构化证明，失败再回退完整 SMT”的流水线：
  - **path-value substitution**：从 path condition 中提取小而确定的事实，例如 `CallData[0] == c`、`CallDataSize == n`、`CallValue64 == c`，代入 storage 表达式，使由 selector/size 条件包住的大 ITE 塌缩。
  - **no-op Store 快路径**：识别并证明 `Store(base, key, Select(base, key))` 这类实际不改变 storage 的写入。
  - **Select(Store(...)) 链化简**：对 `Select(Store(base, k, v), idx)` 做语法级化简；若能判断 `k == idx` 则返回 `v`，若能判断 `k != idx` 则剥掉该层 `Store`。
  - **256-bit value chunk 证明**：把大位宽等价拆成高/低块，必要时继续拆到较小 bit chunk，降低单个 SMT 查询难度。
  - **calldata-size 分区**：当 storage 表达式仍依赖 symbolic `CallDataSize` 时，按具体 size 分区，把 `CallDataSize` substitute 成常量后分别证明；exact 分区可并行执行。若 store-chain 长度差异提示需要逐 size 检查，且剩余 exact 分区已经被并行批量证明，或后续 `[size, exact_limit)` 区间被证明不可行，则设置 `skip_remaining_exact_partitions` 跳过剩余 exact 分区；tail 分区仍单独处理。
  - **不可行路径 rescue**：若主 storage 查询 unknown，单独问 path condition 自身是否 UNSAT；若路径不可行，则 storage 等价 vacuously true。

- **顶层编排与 tuning**：
  - 顶层先做 path-value rewrite，再试结构 fast path；随后区分“storage 表达式真的提到 `CallDataSize`”和“只有 path condition 提到 `CallDataSize`”。
  - 如果 rewrite 后 storage 本身已经不依赖 `CallDataSize`，就不进入 calldata-size partition，因为 split 只会重复同一个 array mismatch 查询；此时直接落到完整 non-partitioned 查询。
  - storage exact calldata-size partition 的 timeout 上限调到 `60000ms` 级别，属于“给单个 size 分区更多时间换可判定性”的权衡；quick check / rescue / tail partition 仍有各自较小的 capped timeout。

- **和 `CALLDATALOAD` 抽象模式的关系**：
  - 第 10 节的 ABI word 抽象是在源头减少 `CallDataSize` guard 进入 storage key/value。
  - 本节是在下游处理已经形成的复杂 storage 公式：如果仍然有 ITE、Store 链或 size 依赖，就用结构快路径和 size 分治尽量证掉。
  - 因此二者是配合关系：`CALLDATALOAD` 抽象减少复杂公式生成，storage 增强负责消化残留复杂公式。

- **健全性（soundness）边界**：
  - 所有 fast path 都是 fail-closed：只有结构上确定成立或 SMT 返回 UNSAT 才算证明成功；SAT/UNKNOWN 不会被当作成功。
  - path-value rewrite 在仍保留原 path condition 的前提下是等价改写；对更激进的 condition rewrite，只信任 UNSAT 结果，失败则回退原始查询。
  - no-op Store 必须证明写入值等于原位置 `Select`；chunk 证明必须覆盖完整 256-bit 值；calldata-size 分区必须覆盖被建模的 size 域。
  - 不可行路径 rescue 的依据是 `path_condition` 自身 UNSAT，此时该 path pair 下任意 observable 等价都成立。

- **记录结论**：该增强没有改变 storage 等价定义，只是把一个巨大的 array mismatch 查询拆成多个健全的小证明步骤。它优先利用路径事实、Store 链结构、位宽分块和 calldata-size 分区降低 Z3 压力；任何不确定情况都会回退完整 SMT 或失败，因此属于性能/可判定性优化，而不是放宽 等价性条件。

## 13. 路径对 union fallback（EVM path 对 x86 path 集合的 return/memory 证明）

- **问题**：path-observation 模式默认逐个检查 `evm_i ∧ x86_j` path pair。已有 feasibility precheck 会先问 `evm_i ∧ x86_j` 是否 UNSAT，若不可行则跳过该 pair。但某些实际不可行的交集包含复杂 x86 path condition、merge 来源的 `Or/If`、flag 表达式或 calldata 条件，solver 可能无法证明 UNSAT，于是仍进入昂贵的 pairwise return/memory 检查。

- **解决方式**：当某个 pair 的 return/memory 检查失败或 unknown 时，固定当前 EVM terminal path `evm_i`，改问一个集合级 bad query：

  ```text
  evm_condition_i
  && Or_j(x86_condition_j && bad_return_or_memory_j)
  ```

  若该查询 UNSAT，说明在 `evm_i` 下不存在任何 x86 terminal path 产生错误 return/memory。实现会分别证明三类 bad 不存在：return-data presence 不一致、return length 不一致、返回 memory 逐字节不一致。

- **和 feasibility precheck 的区别**：
  - feasibility precheck 是 pair-level 剪枝：证明 `evm_i ∧ x86_j` 不可行后，跳过这个 pair 的全部检查。
  - union fallback 是 EVM-path-level 聚合证明：不再纠结某个 `evm_i ∧ x86_j` 是否可行，而是证明“在 `evm_i` 下，x86 路径全集里没有任何 return/memory 坏情况”。
  - 两者互补：precheck 剪掉容易证明不可行的 pair；union fallback 处理 pairwise 不好证明时的 return/memory 聚合证明。

- **健全性（soundness）边界**：
  - 该 fallback 只覆盖 return/memory，不覆盖 storage 或 transient storage。成功后只是把当前 `evm_i` 加入 `aggregate_memory_verified_evm_paths`，后续同一 EVM path 的 pair 仍会调用 `_check_path_pair_storage_transient()` 逐对检查 storage/transient。
  - 只有 union bad query 返回 UNSAT 才算成功；SAT、UNKNOWN、timeout、EVM return length 非 concrete、或 return length 超过 unroll limit，都会 fail-closed，回到普通 pairwise 失败路径。
  - 该证明依赖前置 path coverage：x86 terminal paths 必须覆盖允许输入域，否则 “x86 路径全集没有 bad” 不能代表所有 x86 执行。

- **记录结论**：union fallback 不是跳过 path pair 验证，而是把固定 EVM path 的 return/memory 检查从多个 pairwise 查询改写成一个“x86 path 集合中不存在坏返回结果”的 UNSAT 证明。它不触碰 storage/transient storage，也不替代 path coverage；因此是一个局部、fail-closed 的 return/memory 性能优化。

## 14. Return-data memory 等价检查分块与 Store 链 Select 缓存

- **问题**：当 return-data length 是 concrete 且不超过 `memory_unroll_byte_limit` 时，旧版 concrete-length memory 检查会逐字节证明：

  ```text
  Select(evm_memory, evm_offset + i)
  != Select(x86_memory, x86_base_addr + x86_offset + i)
  ```

  对 32/64/256 字节返回值，这会产生大量重复 solver 查询。每个查询都需要 reset solver、重新添加 path condition / return-data 前提，并让 Z3 重新处理相似的 Array `Select(Store(...))` 链，固定开销和 array theory 推理成本都会被按字节放大。

- **优化 1：chunked memory check，减少 solver 调用次数**
  - 在 `MemoryContentChecks` 中新增 chunked memory check，在逐字节 fallback 之前，先按 `32 / 16 / 8 / 4` 字节尝试证明连续 memory chunk 等价。
  - 对每个 chunk，用 `_memory_chunk_expr()` 把连续 byte 拼成一个 bit-vector：

    ```text
    Concat(byte_0, byte_1, ..., byte_n)
    ```

    然后查询 `evm_chunk != x86_chunk` 是否 UNSAT。若 UNSAT，则整个 chunk 覆盖的 byte 都被加入 `chunk_verified_indices`。
  - 后续逐字节 loop 遇到已验证 byte 会直接跳过，因此 chunk 成功不会重复证明同一段 memory。
  - 性能收益来自减少 solver query 数量：例如 256 字节返回值，最理想情况下从最多 256 次 byte 查询降到 8 次 32-byte chunk 查询；路径条件、return-data 前提和 array 推理的固定成本被整块摊销。
  - chunk 查询只在 full path condition 下得到 SAT 时报告 counterexample；在 storage-independent 弱条件下 SAT 不当作反例，UNKNOWN 则回退逐字节检查。

- **优化 2：Store 链 Select 预解析，缩小查询公式**
  - 新增 Store 链缓存和 `memory_select_expr()`，针对深层数组表达式：

    ```text
    Select(Store(Store(... Store(base, key, value) ...), index)
    ```

    在 Python 侧缓存 Store 链分解结果，避免每个 byte / chunk 反复拆同一个 memory AST。
  - 读取时按 newest-to-oldest 走 Store 链：
    - 若 `key == index` 可证，直接返回该 Store 写入的 `value`；
    - 若 `key != index` 可证，说明该层 Store 不影响当前读取，继续向更早 Store 穿透；
    - 若既不能证明相等也不能证明不相交，立即放弃快速路径，返回完整 `Select(memory, index)` 交给 Z3。
  - 性能收益来自缩小 Z3 输入公式：很多 concrete offset 的 `Select(Store(...))` 可以在 Python 侧解析成具体 byte 表达式，两侧都解析成功时 `simplify(evm_byte != x86_byte)` 往往直接折叠成 `False`，chunk/byte 查询会变得非常轻。
  - 缓存 key 使用 `memory.hash()` 分桶，并在复用前用 `z3_eq(cached_memory, memory)` 确认 AST 结构相同，避免 hash collision 或不同 memory 表达式误复用。

- **健全性（soundness）边界**：
  - chunked check 只有在 mismatch 查询返回 UNSAT 时才把 byte 标记为已证明；SAT/UNKNOWN 不会被当作成功，未覆盖 byte 仍回到逐字节检查。
  - Store 链预解析必须保留 Z3 的 latest-write-wins 语义。若存在较新的 symbolic Store 可能 alias 当前 `index`，不能越过它去读取更早的 exact Store；因此实现遇到“不确定 alias”时 fail-closed，返回原始 `Select(memory, index)`。
  - 旧 review 中复现过的反例是：

    ```text
    memory = Store(Store(base, 0, 0xaa), k, 0xbb)
    Select(memory, 0) = If(k == 0, 0xbb, 0xaa)
    ```

    如果缓存直接返回旧值 `0xaa`，会漏掉 `k == 0` 时的真实差异。当前实现从最新 Store 向内走链，并在无法证明 `k != 0` 时放弃快捷解析，避免该 soundness 漏洞。

- **退化保护**：
  - `memory_chunk_timeout_ms` 进入 `equivalence_tuning.py`，避免 chunk 路径隐藏硬编码 timeout。
  - `memory_chunk_fallback_streak_limit` 限制连续 chunk 失败次数；连续若干 chunk 都无法证明时提前放弃剩余 chunk 尝试，直接进入逐字节 fallback，避免难解场景下额外叠加大量 chunk 查询。

- **记录结论**：该优化没有改变 return-data memory 等价定义，而是把证明流程改成“先用大块 UNSAT 覆盖常见连续返回值，再对剩余 byte 保守回退”。主要收益来自两点：chunked check 减少 solver 调用次数，Store 链 Select 缓存减少单个查询公式体积。所有不确定情况都 fail-closed 回到原始 `Select` 或逐字节检查，因此属于性能优化而不是语义放宽。

## 15. MUL summary per-hit proof（命中即证明，证明通过才折叠）

- **问题**：x86 summary 框架把 matcher 命中的机器码 slice 折叠成抽象语义（MUL summary 直接对 stack 写 `p.mul_semantics(q)`），但信任只来自 matcher 的结构检查，没有针对每次命中的证明。端到端 glue 证明只在测试时间对固化的代表性 fixture 跑过；如果寄存器分配产出一个 matcher 接受、但语义错误的新形态（matcher 的接受集合对寄存器取值是参数化的，fixture 只是该参数空间的有限采样），会被静默信任。一个具体反例构造：`_MulParser` 原本不检查角色寄存器互不重叠，若 res1 与 tmp1 落在同一物理寄存器，后写 tmp1 的 `mov` 会覆盖 z0，parser 仍接受、summary 仍宣称 z0 正确——unsound。

- **审阅中发现的配套缺口**：测试里原有的 glue 证明本身也抓不住这类坏 slice——
  1. checkpoint obligation 用 `dict[Register, expected]`，若两个角色映射到同一寄存器，dict 字面量会静默坍缩，丢失一个 proof obligation；
  2. 尾段只做 `offset -> src_reg` 的结构映射检查，不证明 store 发生时该寄存器仍持有 `z0/z1/z2/z3`；结果寄存器在 checkpoint 之后被后续段覆盖时不会被发现。

- **解决方式**：把 glue 证明从测试提升为生产模块 `x86_64/summaries/mul_proof.py`，并接入 discover 阶段——matcher 命中后、summary 进入 runtime 索引前，对命中的真实 slice 现场跑证明，通过才 yield（“verified-hit summary”）：
  1. **证明内容**（`prove_mul_slice_refines_summary`）：R14 取具体基址、stack 域换自由符号 Array、p/q limb 为任意 64-bit 符号值，按 checkpoint 逐段 raw 符号执行（`insn.to_z3`，不经 summary，避免自证），证明每段输出寄存器 == 分支化 limb 算法的中间值；checkpoint 证过的寄存器用规范表达式替换继续（小步归纳），公式不随 slice 长度累积。
  2. **针对缺口 1**：obligation 改为 `(role, reg, expected)` 列表，同一 checkpoint 内同一寄存器出现两次直接 reject。
  3. **针对缺口 2（关键升级）**：尾段从结构映射检查升级为语义检查——断言尾段恰好 4 条 R14-base 8-byte stack store 且 offset 与 `result_stack_offsets` 一致后，**符号执行这 4 条 store，证明最终 stack 内存上的值逐 limb 等于 `z0/z1/z2/z3`**。结果寄存器被覆盖、wiring 错误、store 顺序异常都会在这里暴露。
  4. **fail-closed 语义**：证明失败（含 solver unknown/timeout）一律 raise `MulProofError`（消息固定格式 `entry=0x..., label=..., reason=..., solver_result=...`）。匹配失败是覆盖率问题可回退 raw 执行；证明失败说明 matcher 接受了语义可疑的 slice，是 soundness bug 信号，因此 **fallback 模式同样报错**，不静默回退。
  5. **缓存**：按 semantic key（slice 字节序列 + p/q limb locations + result offsets + clobbers 的 tuple）做进程内缓存。成功是语义事实，跨 timeout 复用；失败可能由 timeout 预算导致，失败缓存 key 额外带 `timeout_ms`，命中时异常带 `from_cache` 标记。discover 在主线程 `to_z3` 中一次性发生（path-pair 并行不重跑 discover），无需加锁。
  6. **纵深防御**：`_MulParser` 增加 `param/tmp1-3/res1-4` 角色寄存器 pairwise distinct guard（Go `allocateRegisters(..., 8)` 本就返回 8 个不同寄存器）。
  7. **配置与统计**：`X86SummaryConfig` 新增 `prove_mul_hits`（默认 True）与 `mul_proof_timeout_ms`（默认 10s）；`enabled()` 改 keyword-only 分离，避免新参数被当作 summary kind。`last_summary_stats["mul"]["proof"]` 记录 `proven / cache_hits / failed_cache_hits`。
  8. **单一来源**：composition 测试的 glue 实现改为 import 生产模块（测试证明的就是生产折叠前实际运行的同一份代码）；composition/primitive/frame lemma 与 42 个固化 fixture 保留为回归与 lemma 分解文档。

- **代价**：单次 glue 证明实测 10–40ms（按 checkpoint 切成约 10 个小 QF_BV query，每个都是 64-bit 乘加等式，bit-blasting 秒解）；同形态命中走缓存近零成本。相对整体验证预算（perf_erc20_lite 全符号约 20 min）可忽略。

- **健全性（soundness）边界**：
  - per-hit proof 证明的是“该 slice 在本项目的 x86 指令语义模型下实现 uint256 乘法”；Capstone 反汇编与 `to_z3` 指令建模仍是 trusted base。
  - “手写分支化 limb 算法 == `Uint256.mul_semantics`”是与具体 slice 无关的纯数学 composition lemma，由 composition 测试覆盖，不需要 per-hit 重跑。
  - 常量零分支（`ConstLimbLocation(0)`）的前提——编译器把 q limb 标成 constant zero 是否正确——属于第 2 段（EVM MUL == summary 的 single-ins 等价性）的绑定义务，不在本证明范围内。
  - **CALLDATALOAD summary 的同类缺口仍未关闭**（第 9/10 节的 `TRUSTED_SUMMARY_CONFIG` 信任边界），可仿照 mul_proof 模式补 per-hit proof。

- **记录结论**：MUL summary 从 “trusted summary（匹配即信任）”升级为 “fail-closed verified-hit summary（命中即证明，证明通过才折叠）”，以每次命中几十毫秒的代价关闭了 matcher 参数空间未采样形态的 soundness 缺口。新增 summary kind 时应默认带 per-hit 证明。

## 16. DIV/MOD 分段镜像 holiman uint256 + 借位链桥接 assumption（含两条 soundness 守护）

- **问题**：`common/arithmetic.py` 的 `div_semantics`/`mod_semantics` 原本写作 `If(b==0, 0, UDiv(a,b))` / `If(b==0, 0, URem(a,b))`，数学上忠实于 EVM DIV/MOD。但 等价性公式会让 Z3 bit-blast 256-bit 除法（实测 192-bit 起就 `unknown`），导致 DIV/MOD 单指令等价性长期 `xfail`。此前曾出现的 PASS 属于“epilogue 越界 jmp 丢弃路径后退化公式 trivially UNSAT”的假绿（见 memory `project_single_ins_epilogue_fix.md`），并非真正证出 256-bit 除法等价。

- **根因**：两侧都建裸 `bvurem/bvudiv` 时，Z3 既要对大除法 bit-blast，又要自己桥接 x86 codegen 的借位链路径条件（`a==b` / `a<b` 用 `sub/sbb` 表达）与 EVM 侧 4-limb 直接相等（`eq_semantics`）这两种结构不同的 AST，双重负担叠加超时。

- **解决方式**：
  1. **分段镜像 holiman**：`div_semantics`/`mod_semantics` 改为逐分支翻译 `github.com/holiman/uint256 v1.3.2` 的 `Int.Div`/`Int.Mod`：
     - DIV：`y==0 ∨ y>x → 0`；`x==y → 1`；`x.IsUint64() → x0/y0`（64-bit 快路径）；`else → UF`。
     - MOD：`y==0 ∨ x==y → 0`；`x<y → x`；`x.IsUint64() → x0%y0`；`else → UF`。
     快路径用 limb 比较 + 64-bit 运算展开（Z3 秒解，且与 x86 codegen 逐路径结构对齐）；大数 Knuth 长除法折成未解释函数。`_div_rem_64bit` 直接镜像 x86 `mov rdx,0; mov rax,x0; div y0` 的 `div r64` 产物 AST，使两侧逐字一致、无需 Z3 推理 `bvudiv` 性质即可对齐。
  2. **大数路径折同一 UF**：模块级声明 `_HOLIMAN_UDIV_UF`（商）/`_HOLIMAN_UDIVREM_UF`（余）。x86 侧（经 builtin bridge）与 EVM 参照都调用同一 holiman `udivrem`，折同一 UF 即保证 `x86 ≡ EVM`（**不证 ≡ 数学真值**）——两侧 operand 顺序一致（EVM/x86 都 `a = first pop = dividend`），UF 应用结构相同，该分支的 等价性方程退化为 `UF(a,b) == UF(a,b)`（UNSAT）。
  3. **借位链桥接 assumption（纯提速 hint）**：新增 `eq_borrow_chain_assumption(a,b)` = `eq_semantics(a,b) == eq_as_borrow_chain(a,b)`，其中 `eq_as_borrow_chain(a,b) = ¬(a<b) ∧ ¬(b<a)`。在 EVM 侧（`evm_ir/semantics.py` DIV/MOD）与 x86 侧（`x86_64/go_function_semantics.py` `_handle_builtin_div/_mod`）的 DIV/MOD 通过 `state.add_assumption(...)` 注入，让 solver 无需自己做 256-bit 借位↔limb 相等的慢桥接即可对齐 x86，而参照模型本身保持忠实。与 CALLDATALOAD 那种“限制输入空间”的假设不同，这是一条恒真式（由 composition lemma 证明），soundness 中性。
  4. **测试侧单一来源**：`tests/support/instruction_equivalence.py` 新增 `_collect_state_assumptions`，统一从 `state.assumptions` 收集去重后喂 solver，与合约验证主路径 `verification.program_verifier._collect_assumptions` 同款逻辑。
  5. **单指令测试转正**：DIV/MOD 用例从 `xfail(strict=True)` 改为 terminal-paths 逐路径比较（`x86_compare_terminal_paths=True`、`expected_stack_height=1`、`solver_timeout_ms=30_000`），各路径都不再需要 bit-blast 256-bit 除法即可 UNSAT。

- **健全性（soundness）边界**（本节重点；两条守护是 code review 中发现并修复的）：
  - **大数 UF 不证 ≡ 数学真值**：`x86 ≡ IR` 的论证依赖两侧折叠到同一 UF 且 operand 顺序一致，已文档化（memory `mod_div_holiman_segmented.md`）。项目验证目标是 `x86 ≡ EVM IR 语义`（CLAUDE.md），非 `≡ 数学 EVM`，故可接受。该 gap 应随 holiman codegen 演进维护。
  - **比较原语是单点信任（守护 1）**：分段分支条件（`gt/lt/eq/iszero_semantics`）与桥接 assumption **全部**构建在同一组 `Uint256` limb 比较原语上；composition lemma（`tests/composition/test_eq_borrow_chain_composition.py`）用这些原语在等式两侧，只证**内部自洽**，证不出“自洽但系统性错误”（如 limb 显著性整体搞反）。补独立 ground-truth 交叉验证：`tests/unit/test_uint256.py::TestUint256ComparisonGroundTruth` 把 `lt/gt/eq/iszero/slt/sgt` 对 z3 原生 `ULT/UGT/==/</>` 做**全符号**反证（`¬claim` UNSAT），把比较层锚定到独立数学真值，堵住该单点失效。
  - **path-local assumption 必须逐路径 guard（守护 2）**：terminal-paths 模式下，各 x86 路径的 assumptions 是 path-local 的。若像主路径那样无条件全局 `solver.add`，某条路径的“限制输入空间”assumption（如 CALLDATALOAD 的 `hi-192==0`）会越界约束 sibling 路径、把其真实 mismatch 藏成假绿（memory `failure_path_assumption_global_leak.md`）。修复：`_path_observation_mismatches` 用 `And(condition, *path_assumptions, Or(*path_mismatches))` 把每条路径的 assumption 合进**该路径**前置条件（等价 `condition ∧ assumptions ⇒ 检查`），对齐生产 `x86_64/program.py:_path_observation`。当前注入的 `eq_borrow_chain_assumption` 是恒真且无条件注入每条路径，本就无害；该守护是为未来非恒真、path-conditional assumption 预埋的 fail-closed 保险。回归测试 `tests/unit/test_instruction_equivalence_path_assumptions.py`。
  - **assumption 是 hard `solver.add` 非 tracked assumption**：`eq_borrow_chain_assumption` 经 `_collect_state_assumptions` 以 `solver.add` 无条件加入，信任完全来自 composition lemma。该 lemma 测试是信任锚，**禁止 skip**（当前无 skip-guard 标记，属已知次要缺口）。
  - **两个独立 UF 无 `q·b+r==a` 一致性约束**：DIV 折 `_HOLIMAN_UDIV_UF`、MOD 折 `_HOLIMAN_UDIVREM_UF`，二者独立、无公理关联。当前 per-opcode 各自两侧同 UF，`x86 ≡ IR` 仍成立；若一个被验证程序对同一 `(a,b)` 同时含 DIV 与 MOD 且 observable 依赖两者结果，模型可能给出数学不一致的 `(q,r)` 而 per-opcode 等价性检查仍各自 pass——当前无此场景，属潜在 gap（命名 `udiv`/`udivrem` 也与“holiman 单次 udivrem 同出商余”的实际语义不符，是可读性陷阱）。

- **结果**：DIV/MOD 单指令等价性从长期 `xfail` 转为稳定 pass（逐路径 UNSAT，隔离最慢约 6s，timeout 30s 留足余量）；composition lemma、ground-truth 交叉验证、path-guard 回归测试全绿。

- **记录结论**：这是一次“分段建模提速 + 两条 soundness 守护”的组合改动。提速来自镜像 codegen 分支结构 + 借位链桥接 hint；soundness 来自把单点信任（比较原语对原生 ULT 的交叉验证）和 assumption 越界风险（path-local guard 对齐生产范式）显式补证/对齐。UF 大数路径不证 ≡ math 是已知边界，应随 holiman uint256 / codegen 演进同步维护；DIV/MOD 两个独立 UF 的一致性约束是后续可补强的点。

## 17. SDIV/SMOD 除法节点桥接（congruence 提速）与组合证明的分工

> 承接 #16。#16 解决的是 **DIV/MOD 分段建模 + 相等借位链桥接**（`eq_borrow_chain_assumption`，对齐 holiman 分段里的 `eq/iszero` 判断结构）。本节解决的是 **SDIV/SMOD 里"除法节点本身"两侧 AST 不一致**这一新问题，核心机制是 `verified_div_bridges`（`common/div_bridge.py`），与 #15 的 MUL 组合证明属于**两类不同的验证哲学**，此处把分工讲清。

- **问题**：`common/arithmetic.py` 的 `sdiv_semantics`/`smod_semantics` 镜像 holiman `Int.SDiv`/`Int.SMod`——对 `|a|`/`|b|` 复用已转正的 unsigned `div_semantics`/`mod_semantics`，按符号分类树拼回结果（算法本身 sound，**参照对象就是 holiman，非黄皮书裸 `bvsdiv`**）。但 等价性检查是 **EVM 侧公式 vs x86 侧公式**比较，同一个无符号除法在两侧**落成不同 decl / 不同实参 AST**：EVM 侧快路径多为 `bvudiv`（实参是 `_abs256` 的 limb 借位链取负），x86 侧 simplify 成 `bvudiv_i`（实参是反汇编 `div r64` + SUBQ/SBBQ limb 链），大数路径两侧共享 `holiman_udiv`/`holiman_udivrem` UF。两侧 decl 名 / 实参 AST 不同 ⟹ Z3 的 congruence closure 不命中 ⟹ 退回 **bit-blast 256-bit 除法 → unknown**。

- **原理（congruence 是关键）**：
  1. **congruence 公理** = “同一个函数 + 相同输入 ⟹ 相同输出”，对任意函数恒成立，且**不依赖函数内部语义**——判断两个 `f(...)` 相等时除法**不必展开**。这正是它“免费”的根源：要判断 `f(A)==f(B)`，只需证 `A==B`（congruence 自动给出结论），而**不用**像 bit-blast 那样去算 `f` 内部。
  2. `verified_div_bridges`（`common/div_bridge.py`，**生产 + 测试共享**）的工作：按 `DIV_BRIDGE_CATEGORIES` 把同语义不同名的除法归类（`bvudiv`/`bvudiv_i` → `udiv`；`bvurem`/`bvurem_i` → `urem`；`holiman_*` 各自一类），两侧各恰好一个节点才配对；用**独立 QF_AUFBV solver** 先证“实参在 constraint 下恒等”（`constraint ∧ args_differ` 为 `unsat`），再注入 `evm_div == x86_div` 一条等式当 assumption，让主 solver 跳过 bit-blast。
  3. **注入的只是“整棵除法子树的值相等”，不碰 holiman 分段 ITE 内部结构**。内部的 `iszero/eq/IsUint64` 判断由**其他** hint 各自对齐：`eq_borrow_chain_assumption`（相等/借位链，见 #16）、`x86_div64_quotient_fits_assumption`（`div r64` 快路径商高位为 0 的恒真 ground 实例）、`_abs256` 用 limb 减法刻意对齐 x86 取负 AST。`verified_div_bridges` 只负责最后一锤：实参既已对齐，除法输出即相等。
  4. **量化依据（本次实测，QF_BV 强制 bit-blast 路径）**：构造两侧 abs 变换等价、但 AST 不同的 256-bit 除法，证 `evm_div == x86_div`。**无 bridge**：连 64-bit 都 bit-blast 卡死（进程跑 5min+ 第一行结果都未输出）；**有 bridge**（注入等式后由 congruence 秒判）：约 0.0001–0.0002s。差距 6 个数量级以上，本质是“解不出 vs 秒解”，印证“192-bit 起 unknown”的既有记录。

- **解决方式（落地点）**：
  1. `common/div_bridge.py`：`collect_div_subexprs` + `verified_div_bridges`，**fail-closed**——配对歧义、实参个数不一致、验证非 `unsat`（含 unknown/timeout）一律不注入。
  2. **生产 + 测试同源**：生产路径 `verification/equivalence_context.py:158`（`add_verified_div_bridges`）与单指令测试支持 `tests/support/instruction_equivalence.py:944` 调同一 `common.div_bridge`，合约级验证与单指令等价性同源受益。
  3. `common/arithmetic.py`：`sdiv_semantics`/`smod_semantics`（holiman 符号分段）+ `sdiv_speedup_assumptions`/`smod_speedup_assumptions`（把恒真 hint 挂在 `|a|`/`|b|` 上——SDIV/SMOD 内部对**绝对值**跑 unsigned div/mod，hint 须挂在绝对值上才对子路径生效）；`x86_div64_quotient_fits_assumption` 新增。`evm_ir/semantics.py` 的 SDIV/SMOD 分支注入对应 speedup assumptions。
  4. 单指令测试 SDIV/SMOD 走 terminal-paths 逐路径比较，稳定 PASS（实测 baseline：SDIV+SMOD 共约 25.6s）。

- **与组合证明（MUL per-hit proof，#15）的差异**（本节重点）：

  | 维度 | `verified_div_bridges`（除法桥接，本节） | MUL 组合证明（#15） |
  |---|---|---|
  | 本质 | 求解器**提速 hint** | **信任替换** + 独立合法性证明 |
  | 改变被证命题吗 | 否——两侧真实语义都在 solver，仅旁注一条等式 | 是——x86 侧整段机器码被 summary 顶替 |
  | 证据是否必需 | 否——去掉只是变慢/unknown，**不影响 soundness** | 是——去掉则 summary 凭空替换，等价性检查失去意义 |
  | 作用在信任链哪段 | 等价性检查 **横线**（两侧公式比较） | x86 侧**竖线**（机器码 → 公式） |
  | 为何这么轻 / 重 | 借 congruence 把除法当黑箱，只需证**实参相等**（便宜） | 难点在算法本身（partial-product 累加网络），congruence 借不到，必须逐 checkpoint glue proof |

  - **共同点**：两者都 **fail-closed、都 soundness-preserving**（桥接非 `unsat` 不注入；MUL 证明失败/unknown 一律 raise）。
  - **一句话**：**除法借到了 congruence 这个“免费午餐”（同函数同输入 ⟹ 同输出），乘法借不到，只能硬证。** 区别的根因是“同函数+不同输入”（除法，可桥接）还是“两套不同计算过程”（MUL 真实指令链 vs `mul_semantics`，必须逐段证）。

- **健全性（soundness）边界**：
  - 桥接 **fail-closed**：仅在独立 solver 证得“实参必相等”（`unsat`）时注入；任何歧义/unknown/timeout 不注入，**绝不在未证实参恒等时加 `==`**（否则越界约束、藏住真实 counterexample → 假绿）。
  - 注入的 `evm_div == x86_div` 是 **congruence 后承**（同函数同输入），不引入新约束，soundness 中性——它只是把主 solver 本可推出、但因实参 AST 形状差异而不愿自证的结论提前喂入。
  - 大数路径 `holiman_*` UF 仍是 `x86 ≡ EVM`（不证 ≡ 数学真值）；DIV/MOD 两个独立 UF 无 `q·b+r==a` 一致性约束的潜在 gap 沿用 #16 记录，此处不重复展开。

- **结果**：SDIV/SMOD 单指令等价性稳定 PASS（逐路径 UNSAT）。

- **记录结论**：等价性检查里“同一个函数两侧 AST 不一致导致 bit-blast 超时”是反复出现的模式。**优先判断准则**：除法/取余 等价性检查慢 → 先看两侧 decl/实参 AST 能否对齐、能否用 congruence 桥接（轻量提速 hint，不改被证命题）；**只有当难点在算法本身、congruence 借不到时**，才上 summary + 组合证明（信任替换，#15 范式）。两类机制定位不同、代价不同，不应混用。

## 18. 符号 bound 循环的归纳式验证落地（cutpoint 锁步归纳，CErc20 string 循环 PROVED）

- **问题**：真实合约（Compound、Safe）含符号 bound 循环——典型如动态 string 的存储读循环，trip count = ceil(len/32) 而 len 是符号值。符号执行在回边处每轮 fork，有界展开永远无法封闭；提高 `max_depth` 只是多展开几轮、推迟失败。此前对这类循环"不假绿但也证不过"（path coverage 检查必然 SAT）。

- **方案**：按 docs/循环处理增强方案.md 实现循环头 cutpoint 上的锁步归纳（translation validation + CompCert simulation diagram）：havoc 出任意第 n 轮到达循环头的状态，证明一轮循环体后耦合关系 R 保持（②b 回边 / ②c 出口）、分支决策两侧一致（②a）、体内终止路径可观测量等价（②d）——符号 bound 被归纳吞掉，不调 max_depth。落地为 `verification/loop_pairing.py`（支配分析 + 配对 + §6 守卫）、`verification/loop_induction.py`（归纳引擎）、`x86_64/loop_templates.py`（codegen 拷贝循环模板）、`common/store_forwarding.py`（求解器工程，见下）。

- **实现中解决的关键子问题**（每条都是踩过的坑或抓过的 bug）：
  1. **merged 模式假绿风险（P0 前置）**：EVM 侧 depth 剪枝原先静默跳过、`to_z3` merged 模式丢路径后合并语义只代表幸存路径——不只是覆盖缺口而是可能假绿。修复：EVM 侧补 `path_coverage_certificate()`（对齐 x86），两侧 `to_z3` result 携带证书，`program_verifier` merged 模式证书缺失/incomplete 一律失败。
  2. **"目标地址在前"≠循环**：CErc20 按块序回跳 256 处，支配分析（回边 = u→h 且 h 支配 u）确认真循环回边仅 18 条（9 头）；其余是 Solidity 内部函数调用/返回伪回边。另 `irreducible` 在真实合约恒 True 且无害（`immediate_set` 返回边过近似造成调用-返回假环），只作信息暴露——漏网可执行环由 depth 证书在执行层兜底。
  3. **Tier1/Tier2 判别器 = TAG 序言**：x86 循环头以 makeStaticUseGas 模式开头（`mov rax,[r13+0x70]; cmp; jb`，容忍 nop）⇔ EVM 级循环。CErc20 恰好 9 个 TAG 头与 EVM 9 循环 latch 轮廓完全吻合；其余 39 条 codegen 拷贝循环模板匹配 39/39。引理未证明时守卫如实失败（fail-closed，非缺陷）。
  4. **cutpoint havoc 的 entry-specific 清单**：栈基字节偏移 `[r13+0x30]` 必须符号化（具体 0 违反 TAG 栈下溢检查 → 可行路径全进 underflow stub → 40 条残路径全带假约束 → ②(b) 全空洞 unsat 的**假 proved**，被非空洞守卫抓住——教训：全部 unsat ≠ 证明成立，必须确认配对路径可共现）；memory / memory_size / memory_gas 同理 havoc。OOG/栈错误终止路径按 no-OOG envelope 排除并逐条显式记入结论；归纳步 SAT 只输出 inconclusive，绝不报反例。
  5. **窗口基址 bug：`[r13+0x28]` 是 bridge 传参暂存非窗口状态**（SLOAD 站点 ret 前写 8），混入读栈地址后偏 32 字节，slot 目标化简后恒 `False`。规范约定：cutpoint 在块入口，窗口基址 = side-channel `stack_base + byte_offset`；不用 R14 寄存器（host 调用后可能陈旧）。**"目标化简成 False"是 R 定义错误的高效定位信号**，比 unknown 有信息量得多。
  6. **②(a) unknown → 后缀切片**：决策项位于路径条件合取尾部；切片对失配证明（子集 unsat ⇒ 全集 unsat）和 R 证明（弱前提证得 ⇒ 强前提成立）都单调健全，按 1/4/16/full 递增尝试，最难失配对 slice4 上 24s 解出。
  7. **②(c) unknown → store-forwarding 归一化器**：x86 每个 64-bit 写展开 8 字节 Store，段执行后读数嵌数百层链，Z3 只对数值地址转发。`forward_selects`（同基+常量偏移判别名，异基 fail-closed 放弃）+ `unshift_store_chain`（Store 链从 r15 绝对地址下推到 offset 空间消 Lambda，memory 目标变纯数组等式秒解）+ goal 统一 forward+simplify（对齐良好的目标坍缩成 True）。**坑：线性化前必须 simplify 地址**——`(8-4)*8` 未折叠常量、`Extract(Concat(0,a)+Concat(0,b))` 溢出形态会造成假异基（症状：零转发）。
  8. **性能 → 可行性预过滤**：关 reachability 的段执行 80 条 x86 路径中 76 条 base 下 UNSAT（证明不可达，与 reachability 剪枝同一健全性），预过滤剔除后配对矩阵 80×2 → 4×2，**29min → 8min41s**。

- **结果**：CErc20 0x739（Compound string 存储循环）↔ x86 0x107a2 的归纳步完整证明——4 对非空洞路径对上 ②(b)×2/②(c)×2 真 unsat，80 条 ②(a) 全过，envelope 排除显式记录。验收测试 `tests/integration/test_loop_induction_cerc20.py`（约 9 分钟，需显式 `RUN_LOOP_INDUCTION_ACCEPTANCE=1` opt-in，默认 skip 以免拖垮常规 pytest/CI）；合成循环正/负例见 `tests/unit/test_loop_induction.py`。遗留：①(Base)/③(出口) 与降级管线自动串联、Tier 2 七条引理离线证明、深度类枚举自动化。

- **记录结论**：归纳查询 unknown 的排查次序——① 先查**空洞**（joint-sat 可共现性；目标化简是否给 False，后者指向 R 定义错误而非求解难度）；② 失配/R 证明先试**后缀切片**（单调健全，免费）；③ Store 链目标先过 **forward_selects + simplify**（等价变换）；④ 跨地址空间的数组比较优先**代数下推**（unshift）消 Lambda 而非硬解；⑤ 路径爆炸先做 base 下**可行性预过滤**。与 #17 准则同源：优先寻找让两侧 AST 对齐/坍缩的等价变换，最后才靠求解器硬算。

## 19. IR 与解释执行的错误优先级差异（接受，不处理）

- IR 按 block（`compileEVMTag` 块级序言）、Go 解释器按 op（逐 opcode），错误检查顺序天然不同。典型差异：`stack 不足 ∧ gas < block.StaticGas` 时，解释器返回 `STACK_UNDERFLOW`，AOT/IR 返回 `OUT_OF_GAS`。
- 本项目验证目标是 **IR↔AOT 一致性**，而非 IR↔解释器；此差异属预期，**接受、不处理**。

## 20. host-gas 上界是**手工同步项**：编译器一变，这里必须跟着手改

- **性质**：`state/host_gas.HOST_GAS_UPPER_BOUNDS` 的数值是从某一版 go-hpc-evm 的 gas 实现里**人工抄出来**的，不是自动派生、也没有可执行 oracle 去校验。它作为 `ULE(H, bound)` 注入路径约束参与剪枝，所以**上游 gas 实现一改，这份表就必须手动跟着改**——这是常态维护义务，不是待修的缺陷。

- **不同步的后果**：拿新版编译器的产物（IR JSON + hex）去验证而上界还是旧版的，一旦新版真实 host cost 变大（例如硬分叉调高 `ColdSloadCostEIP2929`），`ULE(H, 2100)` 会把真实可达的轨迹排除在验证域外——**静默缩域后照常返回 VERIFIED**。方向是假绿，不会报错，也没有任何测试看得见。这就是必须手工盯住的理由。

- **没有自动提醒，只能靠流程**：曾有一条 revision pin（`tests/support/go_revision.py` + `test_bounds_are_pinned_to_audited_go_revision`），在本地 go-hpc-evm HEAD 偏离基线时变红。**已删除**，因为它绑错了对象且信噪比为负：

  1. **对象错**：比的是本地工作区 HEAD，而决定健全性的是**产出被验产物的那个编译器版本**。fixture 是签入仓库的二进制产物，本地 HEAD 怎么变都不影响它们；反过来产物来自 CI 或他人机器时，检查照过。
  2. **假阳性淹没真信号**：上游是活跃开发的仓库，在那边切分支、拉 commit、做任何无关工作都会让它变红，而"HEAD 变了 ⟹ 上界失效"这个蕴含很弱。
  3. **消红的最省事做法恰好是它要阻止的动作**：把 `AUDITED_GO_HPC_EVM_COMMIT` 改成新 hash——即"没复核就更新基线"。
  4. **多数环境根本不跑**：CI 不会把私有 Go 仓库 checkout 到 `$GOPATH`，`current_go_hpc_evm_commit()` 返回 `None` 直接 skip；`main.py` 与库调用方也不执行 pytest。

  根因是产物不带 provenance——IR JSON 与 hex 都不记录自己由哪个编译器版本产出，任何在 Python 侧硬编码的 revision 都只能绑住开发机状态。基线 commit 现在纯作为**文档事实**记在 `tests/data/README.md`（供复核时知道上次照的哪一版），不再有测试比对它。

- **同步流程**（上游 gas 实现或编译器版本一变就走一遍）：
  1. 按 `HOST_GAS_UPPER_BOUNDS` 每条注释里记的函数与行号，回 `evm/host.go` / `evm/aot/*` 逐条复核数值（**不要看 `evm/gas_table.go`**，那是解释器的表、AOT 从不调用，两边数值一致纯属巧合）；
  2. 复核分层：从新 fixture 的 IR `static_gas` 减去 PUSH 份额，确认哪部分归 static / 可见 fee、哪部分才是 host 动态；
  3. 若某 opcode 新增了写不出小常量上界的依赖，把它从表里移走——`HOST_GAS_UNBOUNDED_KINDS` 会自动接住（照扣 UF、不剪枝），`test_unbounded_set_is_derived_not_hardcoded` 会提示更新期望集；
  4. `GOARCH=amd64` 重新生成 `tests/data/gas_*`；
  5. 最后才更新 `tests/data/README.md` 里记的基线 commit——**它是复核完成的标记，不是复核的替代**。

- **影响范围**：只波及会发射上界的 `FIXED_BUDGET` / `FULL`。`GasCheck.OFF` 不开 host UF、因而不产生上界（`emit_host_gas_bound` 在 `host_gas_uf_enabled` 为假时不被调用），不受影响。

- **若要减轻手工负担**（按代价递增，均未实施）：让产物携带编译器 revision（IR JSON 加一个字段）并在 `verify_program_pair` 入口比对；上界随产物下发而非在 Python 侧硬编码。注意这两条都指向同一件事——**让被验产物自证版本**；在此之前任何 Python 侧的版本绑定都只是绑开发机状态，这也是上面那条 revision pin 被删的原因。

- **记录结论**：这是"assume 与被验对象脱节"的一般形态——**只要某个 assume 的正确性依赖外部实现的版本，它就是一个手工同步项，必须在文档里写明同步流程；而要让它可自动校验，唯一的出路是让被验产物自证版本**，在此之前任何 Python 侧的 revision 绑定都只绑住了开发机状态。与 #16 的桥接 assumption 同类，但那一条的前提可在同一次求解内证伪，这一条不能，只能靠流程。

# 关键问题记录
本文档记录了在项目开发过程中遇到的关键问题及其解决方案，旨在为后续的开发、论文等提供参考和指导。

## 1. x86 CFG 在 `ret` 后断开（缺少 Go 往返边）
- 问题：AOT 机器码在 `ret` 处会先跳回 Go 运行时，再从 `exitContext.returnAddress` 恢复到下一段机器码；原 CFG 未建模该往返，导致 `ret` 后续块断开、边数量偏少。
- 根因：执行器把 `ret` 当作直接终止；未识别 `compileCallGoFunction` 指令模式，也未显式建 `ret -> GO_HOST -> returnAddress` 动态边。
- 解决方式：在 `ret` 分支增加 `CallGoFunction` 模式识别（基于 `R13 + status_code/return_address` 写入），命中后动态创建 `CALL/RETURN` 边，并按 `returnAddress` 继续执行；同时为每个站点创建独立 `GO_HOST_n` 节点。
- 结果：`ret` 后控制流可连续，`muti_block*.dot` 能看到 `GO_HOST` 与对应 `call/return` 边，关键跳转边（如 `0x328 -> 0x364`）可在足够执行深度下正确出现。

## 2. 合流点合并优化（X86TopologicalStrategy + merge_buffers）

- **背景**：符号执行默认采用 DFS 策略，路径数随条件分支指数爆炸。对具有菱形控制流的 x86 程序，条件跳转的两条路径最终汇聚到同一基本块，若分别执行会重复计算后续指令的语义，导致 Z3 表达式规模翻倍增长。
- **方案**：在 `X86SymbolicExecutor` 中引入合流点合并优化（`enable_merge=True`），分三部分：
  1. **静态合流点检测**（`_compute_static_merge_points`）：在初始化阶段用拓扑序过滤回边，只统计前向入边数 ≥ 2 的基本块作为合流点，避免循环头被误识别。
  2. **拓扑顺序搜索**（`X86TopologicalStrategy`）：按拓扑序驱动 worklist，保证一个合流点的所有前驱都先于合流点被执行，使 `merge_buffers` 能在主循环内自然收齐。
  3. **状态合并**（`_merge_at_confluence`）：在合流点将多条路径状态用 `If(path_cond, val_A, val_B)` 合并为单一符号状态，后续只需执行一次。
- **两个修复的 bug**：
  - **flush 丢状态**（问题 4）：`_flush_merge_buffers` 处理 flush 产生的后继状态时，非合流点非终止的中间态原来被直接丢弃（欠近似）。修复：新增 `_flush_execute_state` 辅助方法，对此类状态递归继续执行，结果重新派发到 `merge_buffers` 或 `final_states`。
  - **回边导致主循环阻塞**（问题 3）：原 `_compute_static_merge_points` 把回边也计入入边数，循环头的等待计数永远不被满足，主循环跳过该合流点，后续路径全部丢失。修复：`_compute_static_merge_points` 接受 `topo_order` 参数，跳过 `topo_order[src] >= topo_order[dst]` 的回边，`__init__` 中先计算拓扑序再计算合流点。
- **结果**：合并优化可将路径数从指数量级压缩到线性量级（每个合流点只产生一条合并路径），显著降低 Z3 约束复杂度；含循环的 CFG 执行不再阻塞，flush 阶段的中间态不再丢失。

## 3. 跳转目标解析上移到 Go IR 层（避免机器码跳转表干扰 CFG）

- **背景/动机**：如果在机器码阶段再解析跳转目标，往往需要生成 jump table，CFG 构造时容易把跳转表解析成循环或伪分支，造成结构膨胀与误判。
近期提交依据（/Users/june/Work/go/src/github.com/bcds/go-hpc-evm）：
- `05fe32d`（2026-03-12）：`CompileEVM` 改为调用 `resolveSymbolicJumps`，并注明“在返回前解析所有可支持跳转目标为静态形式”，表明跳转解析在 Go IR 阶段完成。
- `a8a7cb9`（2026-03-12）：增强符号跳转分析（`const_set`/条件处理），提升 Go 层可解析目标的覆盖率。
- `f6199da`（2026-03-13）：符号解析改为路径敏感 worklist，收集 `resolvedJumps` 并在 `applySymbolicResolutions` 中写回 `ImmediateSet`，仅在解析仍不可得时才报动态跳转错误。
- **记录结论**：当前机器码编译是在跳转目标解析之后进行的；JUMP/JUMPI 的目标在 Go IR 层已解析并写入 `ImmediateSet`，避免机器码生成 jump table，从而减少对 CFG 构造的干扰（尤其是跳转表被误解析为循环的风险）。

## 4. Host Func Index 固定为 ABI 常量表

- **背景/动机**：AOT 编译器将 EVM 的 host 操作（如 SHA3、SLOAD、SSTORE、CALL 等）编译为 x86 机器码中的 Go bridge 块，通过 `mov dword [r13+0xe8], <func_index>` 嵌入函数索引，`ret` 回 Go 运行时后由 `evmExitContext.goFunctionCallIndex` 查表分发。原实现中 func_index 依赖 Go `map` 迭代顺序分配（`CompileEVM` 中遍历 `e.hosts.Hosts`），导致：
  1. 不同合约的同一 host 函数可能获得不同 index，Python 侧无法建立通用映射。
  2. Go `map` 迭代顺序不确定，同一合约重复编译可能产生不同 index，验证结果不可复现。
  3. Python 侧需要"按合约手动配置 `host_functions` 映射"，增加使用负担且易出错。

- **Go 侧改动**（go-hpc-evm `c87c1d7`，2026-04-15）：
  - 新增 `HostSpec{ID int64, Name string}` 结构和 `builtinHostSpecs` 固定目录（1..19）。
  - `CompileEVM` 改为遍历 `DefaultHostSpecs()` 而非 `e.hosts.Hosts` map，确保 func_index 编译时确定。
  - 固定表：`1=sha3, 2=call, 3=callCode, 4=delegateCall, 5=staticCall, 6=create, 7=create2, 8=selfDestruct, 9=sload, 10=sstore, 11=balance, 12=selfBalance, 13=extCodeSize, 14=extCodeCopy, 15=extCodeHash, 16=blockHash, 17=log, 18=tload, 19=tstore`。

- **Python 侧改动**：
  - `x86_64/aot_profile.py`：`GO_HPC_EVM_PROFILE.host_functions` 从空字典改为上述固定映射；新增 `resolve_host_function_name(func_index)` 和 `resolve_builtin_function_name(func_index)` 统一解析入口。
  - `x86_64/go_function_semantics.py`：分发逻辑改用 `resolve_host_function_name()`，错误信息更新为"not defined by the active go-hpc-evm host ABI table"。
  - `verification/call_site_mapping.py`：同理改用统一解析入口，错误信息对齐。
  - 测试：所有 host 函数测试从合成 index（如 `{0: "sload"}`）改为真实固定 index（如 `{9: "sload"}`），确保与实际 AOT 产出一致。

- **记录结论**：host func index 现为固定 ABI 常量，Go/Python 两侧共享同一映射表。形式化验证不再需要按合约手动配置 `host_functions`，验证结果可复现。该固定表应作为 go-hpc-evm 的 ABI 约束维护，新增 host 函数时须同步更新两侧。

## 5. callEngine 字段 side-channel（Z3 穿透 Store 链导致验证极慢）

- **问题**：x86 语义执行器对 `[R13+offset]` 的写入只更新 `x86_memory` 字节级 Array；后续读取（如 `ret` 处读 status_code、读 stack_pointer）需要通过 `load_byte` / `load_64bit` 穿透整个 Store 链（所有已执行过的字节级写入）才能还原出值。Z3 对符号基址（R13 是符号变量）的 Array 别名分析代价极高，导致 `ret` 处的 return 条件公式体积爆炸，验证时间从秒级变为分钟级甚至超时（`test_verify_add_program_pair` 在此前慢数十倍）。

- **根因**：Z3 的 Array theory 在处理 `Select(Store(...Store(arr, addr_n, v_n)..., addr_1, v_1), query_addr)` 时，若 `query_addr` 与各 `addr_i` 的大小关系不能被静态判定（符号地址），必须逐层展开 Store 做别名分析，复杂度随 Store 链深度线性增长，在含大量 callEngine 写入的完整程序中代价极高。

- **解决方式**：为 `SMTState` 新增一组显式 BitVec 字段作为 side-channel（`callengine_status_code`、`callengine_stack_pointer_limbs`、`callengine_stack_byte_offset`、`callengine_return_address` 等）。在 `x86_instruction_to_z3` 中，识别到 `mov [R13+KNOWN_OFFSET], value` 时，除写入 `x86_memory` 外，同步调用 `_maybe_update_callengine_field()` 写入对应 side-channel 字段；读取时 `_maybe_read_callengine_field()` 直接返回 side-channel 值，绕过 `x86_memory`。`ret` 处的 status_code 和 sp 读取改为直接读 side-channel 常量（ADD 程序中为 `BitVecVal(2, 8)` 和 `BitVecVal(-4, 64)`），彻底消除对 Store 链的穿透。

- **结果**：`ret` 处的 return 条件公式从深度嵌套的 Array Select 表达式变为对常量的简单比较，Z3 求解负担大幅降低。`test_verify_add_program_pair` 验证速度显著提升（秒级）。side-channel 的正确性依赖"所有写 `[R13+offset]` 的指令都命中 `_CALLENGINE_FIELD_MAP`"这一不变式，当前覆盖 `mov`、`add`、`shl`、`shr` 四类写内存指令。

## 6. x86 内存拆分为三域（callengine / stack / evm）

- **问题**：旧版 `X86MemoryState` 只有一个全局 `Memory: Array[BV64, BV8]`，三种物理上完全不重叠的内存区域——通过 R13 访问的 callEngine 结构体、通过 R14 访问的 EVM 栈窗口、通过 R15 访问的 EVM 256-bit memory——共享同一 Z3 Array。在 Z3 中，共享同一数组时，任意写操作都会在后续所有读操作的 Store 链中累积。对 SHA3/SLOAD/CALL 等操作，Go 函数调用前后会连续读写三种域，导致 SHA3 语义中 `evm_mem` 包含了 callEngine 和栈域的 Store 噪声，与 EVM IR 侧的纯 `evm_memory` Array 无法等价（`test_verify_muti_block_*` 失败的根本原因）。

- **根因**：单一 Array 对 Z3 是"有记忆的"——写入 `[R13+0x28]`（sp 字段）和写入 `[R15+offset]`（EVM memory）落在同一个 Array 里，Z3 的 `Select` 无法直接排除地址不重叠的可能性（地址是符号的），必须展开所有 Store 做别名分析，导致 SHA3 / MSTORE / CALL 场景下公式膨胀。

- **解决方式**：将 `X86MemoryState` 拆分为三个独立 Z3 Array：
  - `call_engine_mem`：仅接受 base_reg=R13 的访存
  - `stack_mem`：仅接受 base_reg=R14 的访存
  - `evm_mem`：仅接受 base_reg=R15 的访存

  所有 `load_*/store_*` 强制传入 keyword-only 的 `domain: MemoryDomain` 参数，无默认值；`_classify_domain(base_reg)` 在语义层静态路由。无法路由的访存（base_reg ∉ {R13,R14,R15}）抛 `MemoryDomainError`，测试桩可设 `unrouted_memory_domain` 兜底到 STACK 域。SHA3/CREATE/CALL 等 host 函数只读写 `evm_mem`，彻底消除三域之间的 Store 链交叉。

  同时引入 `PointerTag` 枚举跟踪寄存器的 provenance（CALLDATA_PTR / CODE_PTR / RETURNDATA_PTR / EVM_PTR / STACK_PTR），用于将 `[reg+offset]` 形式的间接访存（base_reg 不是 R13/R14/R15，而是从 callEngine 字段加载的指针）路由到正确域。

- **结果**：SHA3 语义从全局 `x86_memory.Memory` 改为只读 `x86_memory.evm_mem`，与 EVM IR 侧的 `evm_memory` 对齐，在结构上消除了之前三域混写导致两侧 SHA3 读不同 Array 的问题。`test_verify_muti_block_*` 目前标记为 `@pytest.mark.skip(reason="Not impl well")`，尚未验证三域拆分后能否通过完整验证。

## 7. returndata / code / calldata 的符号化建模

- **问题**：旧版 `SMTState` 没有独立的 `return_data`、`code`、`calldata_ptr`（code_ptr / input_ptr）字段，相关内容全部混写在全局 `x86_memory.Memory` 中。CALL / CALLCODE / DELEGATECALL / STATICCALL 等指令执行后产生的 return data 无处存放；CALLDATACOPY / CODECOPY 在做字节搬运时也是操作全局内存，与三域拆分后的语义不兼容。

- **解决方式**：
  - `SMTState` 新增 `return_data: Array[BV64, BV8]` 和 `code: Array[BV64, BV8]` 字段，以及六个 callEngine side-channel 字段（`callengine_input_pointer`、`callengine_input_size_bytes`、`callengine_code_pointer`、`callengine_code_size_bytes`、`callengine_return_data_pointer`、`callengine_return_data_size_bytes`）。
  - `aot_profile.py` 补全对应的 callEngine 偏移（`input_pointer=0x90`、`input_size=0x98`、`code_pointer=0xA0`、`code_size=0xA8`、`return_data_pointer=0xB0`、`return_data_size=0xB8`）。
  - `GoFunctionSemantics` 新增 `_update_return_data_source()` 辅助方法：CALL/CALLCODE/DELEGATECALL/STATICCALL 执行后用 `Lambda` 表达式更新 `mstate.return_data`，同步写回 callEngine side-channel 中的 return_data_pointer 和 return_data_size。
  - `PointerTag` 追踪从 callEngine 加载的指针（EVM_PTR / STACK_PTR / CALLDATA_PTR / CODE_PTR / RETURNDATA_PTR），使 `[reg+offset]` 形式的间接访存能路由到正确域（如 CALLDATACOPY 用 input_ptr 写 evm_mem）。
  - Go 函数调用后调用 `_clear_caller_saved_pointer_tags()` 清空 caller-saved 寄存器的 tag，避免跨调用的 tag 错误传播。

- **结果**：return data / code / calldata 拥有独立的符号化 Array，访存路由按 provenance 而非仅靠 base_reg 决定，为后续 RETURNDATACOPY / CODECOPY / CALLDATACOPY 的形式化建模提供了正确的状态载体。

## 8. 终止路径 Observation 直接检查（避免先合并完整终态 Array）

- **问题**：旧版 program-level refinement 会先把所有终止路径的完整 `SMTState` 合并成一个总状态，再从总状态中提取返回值、内存、storage 等 observable。这个合并会对大对象（尤其是 `Array[BV64, BV8]` 的 memory、`Array[BV256, BV256]` 的 storage/transient storage、x86 寄存器集合）构造大量 `If(path_cond, array_path_i, array_path_j)`。一旦某条路径内部已经包含复杂 byte-level `Select/Store/ITE`，外层 Array 合并会把公式再包一层路径 ITE，导致 Z3 需要同时处理“路径选择 + Array extensionality + bit-vector arithmetic”的组合爆炸。

- **典型触发场景**：`CALLDATALOAD` 在符号 offset 下，本身就会产生 32 个字节级 `Select(calldata, offset+i)` 和越界补零 ITE。如果该值继续参与后续 memory / return-data 计算，再在 CFG 终态层把 x86 多条 terminal path 的完整 memory / storage / register state 合并起来，Z3 看到的就不是“某条路径上的局部 observable”，而是“路径 ITE 包起来的一整套终态 Array”。这会把原本的 byte-level 难题放大成路径级 Array 合并难题。

- **根因**：对程序精化而言，真正需要比较的是每条终止路径对外可观察结果，而不是整份机器终态。旧做法相当于先构造：

  ```text
  merged_state = If(cond_0, state_0, If(cond_1, state_1, ...))
  check observable(merged_state)
  ```

  这会强迫 Z3 构造并化简完整终态的 Array ITE。实际上，只要每个输入都落在某条 EVM 终止路径和某条 x86 终止路径上，并且在二者路径条件交集下 observable 相等，就足以证明精化：

  ```text
  coverage:  Or(evm_cond_i) == true, Or(x86_cond_j) == true
  pairwise:  for all i,j. evm_cond_i && x86_cond_j => obs_evm_i == obs_x86_j
  ```

- **解决方式**：引入“终止路径 observation”作为正式检查对象，为 program-level refinement 提供一条不合并完整终态的检查路径。

  1. `RefinementChecker.check_refinement_paths()` 新增 path-observation 检查流程：
     - 先检查 EVM/x86 terminal path 条件是否覆盖全部输入；
     - 对 EVM path 与 x86 path 做两两交集；
     - 对交集 UNSAT 的 path pair 直接跳过；
     - 对 SAT 或 UNKNOWN 的 pair，带着 `path_condition = evm_cond && x86_cond` 调用原来的 return-data / memory / storage / transient-storage 检查；
     - UNKNOWN feasibility 不剪枝，按可能可达处理，保证不因 solver 不确定而欠近似。

  2. `ProgramEquivalenceChecker` 保留旧 merged-result 路径作为默认行为，同时提供 path-observation mode：
     - 默认 `path_observations=False`，继续调用两边 program 的 `to_z3()` merged-result API；
     - 显式 `path_observations=True` 时调用两边 program 的 path API；
     - path-observation 主 refinement 直接使用 `PathObservation` 列表；
     - path-observation 下 `stack_check=None` 时完全不构造 merged state；
     - 只有 debug 用的 `stack_check` 打开时，才请求 `merge_state=True` 作为 fallback。

  3. `EVMProgram` / `X86Program` 增加正式 `to_z3_paths()` API：
     - 返回 `PathSemantics(global_states, observations, merged_state)`；
     - EVM 侧负责执行 EVM CFG 并提取 `offset/length/memory/storage/transient_storage`；
     - x86 侧负责 instruction/block 识别、CFG execution、sequential/no-CFG fallback，并提取对应 observable；
     - `merged_state` 仅在调用方显式要求时生成。

  4. 新增中立结构 `common/path_observation.py`：
     - `PathObservation` 固定字段：`condition, offset, length, memory, base_addr, has_return_data, storage, transient_storage`；
     - `PathSemantics` 表示一次 path-sensitive execution 的结果；
     - `PathObservation` 保持 dict-like `.get()` / `[]` 兼容，避免 `RefinementChecker` 大规模重写。

- **正确性直觉**：旧的 merged-state 检查和新的 path-observation 检查在路径覆盖完整时是等价的。对任意输入，EVM 执行会满足至少一个 `evm_cond_i`，x86 执行会满足至少一个 `x86_cond_j`；这个输入因此落在某个交集 `evm_cond_i && x86_cond_j` 中。若所有可行交集下 observable 都相等，则该输入下两边 observable 相等。反过来，若某个可行交集存在 observable 不等，`check_refinement_paths()` 会在对应 pair 的带条件检查中找到反例。不可行交集跳过是安全的，因为没有输入能同时满足两边路径条件。

- **复杂度变化**：
  - 旧做法：先构造完整终态合并，Array ITE 数量随 terminal path 数增加，后续每个 observable 读取都可能穿透合并后的 memory / storage / register 表达式。
  - 新做法：最坏检查 `m * n` 个 EVM/x86 path pair，但每个 query 只比较一对未合并 terminal observation；不可行 pair 先用轻量 feasibility check 剪掉。
  - 对多路径程序，公式体积从“先构造一个巨大的 merged Array state”变成“按 path pair 局部证明”，通常更适合 Z3 的 incremental 小 query。

- **实测效果**（2026-05-19，单轮 wall-time 对照，`timeout_ms=30000`）：
  - 小程序场景收益不明显，部分还会略慢：`add_raw_stack` 从 `0.031s` 变为 `0.050s`，`mstore_return` 从 `0.057s` 变为 `0.061s`，`three_block_return` 从 `0.101s` 变为 `0.105s`。这些场景路径数少，或者仍启用了 stack check，需要请求 `merged_state` fallback，因此 path-pair 检查的固定开销盖过了省下的合并成本。
  - 简单分支场景有小幅收益：`jumpi_2block_ok_fixed1` 从 `0.233s` 降到 `0.220s`，约 `1.06x`。
  - 固定 ABI size 的真实程序收益更明显：`test_verify_perf_erc20_lite_program_pair` 在 `calldata_size_bytes=68` 时，从旧 merged check 的 `2.623s` 降到 path-observation check 的 `2.002s`，约 `1.31x`。该场景有 `6` 条 EVM terminal path、`7` 条 x86 terminal path，只有 `7/42` 个 path pair 可行，新流程能跳过大量不可行交集，避免先构造完整 merged Array 终态。
  - 全符号 calldata size 仍然不可用：去掉 `calldata_size_bytes=68` 后，两种模式都超时。path-observation check wall time 约 `207.9s`，旧 merged check 约 `232.8s`，虽然略快但仍返回 `TIMEOUT`。这说明当前优化只削掉了外层终态合并的放大项，没有解决全符号 calldata / `CALLDATALOAD` 的核心 SMT 难题。

- **局限性**：
  - 该优化解决的是“外层 CFG 终态合并导致的 Array/ITE 放大”，并不消除 `CALLDATALOAD` 在符号 offset 下的内层 byte-level `Select + ITE` 本质复杂度。它能避免路径合并把 CALLDATALOAD 变得更慢，但不能让全符号 `CALLDATALOAD` 自动变快。
  - 新流程的最坏复杂度是 `m * n` 个 path pair。若两侧 terminal path 很多且 feasibility check 不能剪掉足够多不可行 pair，小 query 的数量也会成为瓶颈。
  - 对单路径或路径很少的程序，新流程可能只有额外调度成本，没有明显公式缩减；这类场景可以考虑后续做 adaptive 选择：多路径且不需要 stack check 时优先 path observation，否则保留 merged check。
  - `stack_check` 打开时仍需要 `merged_state` fallback，此时不能完全避免终态合并成本。

- **记录结论**：program-level refinement 现在拥有“terminal path observation”作为可选精化对象，默认仍保留旧的 merged-result 行为以降低回归风险。该优化可以把验证目标从“大 Array 终态合并后的全局等式”改写为“覆盖完整的 path pair 局部等式”，在保持声音性的同时降低 CFG 多路径场景下的 Z3 公式膨胀风险。它是有价值的结构性优化，但不是全符号 calldata / `CALLDATALOAD` 性能问题的主解法；后续主要性能突破应转向 calldata 建模本身，例如 word-level calldata、byte-select 规范化、或对 ABI selector/size 的路径条件做更强归约。

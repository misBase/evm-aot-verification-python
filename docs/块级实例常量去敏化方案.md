# 块级实例常量去敏化方案（证明实例与上下文实例分离）

> 状态：设计稿（2026-09-30）；2026-10-03 已按 §11 推荐选项（档 2、H2 用 E_c 前提、worklist 拒绝、深度不泛化）在并行调度中实现，开关 `constant_insensitive` / `--constant-insensitive`，默认关（S3 试点前）。行号基于 develop-cutpoint 工作区当天快照（`block_parallel.py` 等文件仍在改动，落地前以符号名为准）。

## 0. 结论

- 把一个实例拆成两个角色：**上下文实例** `c`（关系节点：H0/H2 的目标、发现的产物，带全部栈常量，现状不变）与**证明实例** `k = π(c)`（只保留块真正"值使用"的栈常量）。同一 `k` 的局部定理只证一次，被它所有上下文复用。
- 局部定理复用靠**前提加强**：`R_c = R_k ∧ K_c`，`T_k` 对所有满足 `R_k` 的入口成立，自然对 `R_c` 成立。投影规则 `π` **不进可信基**：丢哪个常量都不影响可靠性，只影响证明难度。
- **H2 必须按上下文检查**：在 `k` 的出口状态上以 `premise_k ∧ E_c` 为前提（`E_c` = 被丢常量在 havoc 入口上的等式），目标集仍是冻结的上下文集合。`k` 永远不作为 H2 目标。
- 深度本步不泛化（绝对深度写死在 stack_geometry / TAG 检查 / live_stack_prefix 里）。
- r29 已尝试实例上的离线测算：CErc20 1863→1216（−35%），Safe 1612→1107（−31%）；按"兄弟≈首个 75%"折算，节点证明墙钟预计省约 20–25%。

## 1. 定义

| 记号 | 含义 |
|---|---|
| `c = (pc, d, m, f, K_c)` | 发现得到的 `BlockSpecialization`，`K_c` = `stack_constants` |
| `S(pc)` | 块的**敏感槽**集合（入口栈顶相对下标），见 §2 |
| `π(c)` | `replace(c, stack_constants=tuple((i,v) for (i,v) in K_c if i in S(pc)))` |
| `D_c = K_c \ K_k` | 被丢掉的常量 |
| `E_c` | `And(evm.peek(i)==v, read_x86_stack_slot(x86,i)==v for (i,v) in D_c)`，在 **k 的 havoc 状态**上求值 |

## 2. 哪些常量可以丢

**可靠性不依赖这一节**（§3.3）。这里只决定"丢了不变难"的常量，目标是：块根本不读、或只搬运不参与计算的槽。

### 2.1 两档规则（均从 IR 算，不看 x86）

- **档 1：窗口外**。窗口 `w(pc)` = 块读到的最深入口槽 + 1。沿 `live_operations(block)` 扫描，`h` 为相对入口的高度变化：
  `need = DUP n → n；SWAP n → n+1；其他 → npop`（`op_stack_effect`，动态 JUMP/JUMPI 的目标也计入 npop），`w = max(w, need − h)`，`h += npush − npop`。保留 `i < w` 的常量。
  交叉核对：CErc20 723/723、Safe 742/742 块上 `w == EVMBlock.min_depth`（Go 的下溢阈值）。实现时两者取 max 并在不等时报诊断即可。
- **档 2：值使用**（推荐默认）。对入口槽做标签传播：DUP 复制标签、SWAP 交换、POP 丢弃；其余操作弹出的标签记为"被使用"。`S(pc)` = 被使用的入口槽。只被搬运（包括被 SWAP 到别处、原样留到出口）的常量丢掉。

**以 JUMP 结尾的返回块**：动态 JUMP/JUMPI 弹出目标，目标槽被"使用"，返回 tag 必然留在 `S(pc)` 中。这是必须的性能约束：若返回 tag 变成符号，`complete_jump_domain` 会把 JUMP 展开到全部 `immediate_set`，路径数爆炸。可靠性上它仍然没问题，只是证明会失败或者很慢。
其他被计算使用的常量（内存偏移、长度等）也保留，因为具体地址是现有专门化收益的来源。

### 2.2 x86 侧

不需要做 x86 读集分析。块边界上活栈全部在规范内存窗口里，x86 块代码（含 host bridge 通过 sp 取参）只读 EVM 操作数对应的槽。如果 x86 读了一个被丢的槽，读到的只是同一个 havoc 符号 `s_i`，结论照样成立，最多让证明变难，并由 §6 的回退接住。

### 2.3 测算（`tmp/window_projection.py`，输入 r29 stage2 已尝试实例，非全量冻结集）

| | 实例 | 档 1 | 档 2 | 全丢（下界） | 档 2 且忽略深度 |
|---|---|---|---|---|---|
| CErc20 | 1863 | 1304 | **1216** | 1052 | 691 |
| Safe | 1612 | 1334 | **1107** | 900 | 635 |

全量冻结集的"全丢"比例（CErc20 4708→2296、Safe 3240→1744）比上表更低，所以上表偏保守。例：CErc20 pc=4236 窗口为 2，16 个上下文投影后按深度只剩 6 个 `k`（全部是 300s 首轮超时的难节点）。

## 3. 可靠性论证

### 3.1 节点证书的语义

对关系节点 `c`：所有满足 `R_c` 的具体 (EVM, x86) 入口对，其段执行要么以终端可观察量相等结束，要么成对到达 `pc'`，且出口对满足 `⋁_{t∈targets(pc')} R_t`。前半句来自局部定理，后半句来自 H2。

### 3.2 两条引理

- **引理 A（havoc 精化）**：若 `k` 与 `c` 的 `(pc, d, m, f)` 相同、`K_k ⊆ K_c`（下标和值都一致），且使用同一 prefix，那么 `havoc(c) ≡ havoc(k) ∧ E_c`。
  依据：`build_havoc(c)` 相对 `build_havoc(k)` 只多做两件事：`Store(Stack, SP−1−i, v)`，以及用 `peek` 重写 x86 栈窗口（`block_relation.py:73-82`）。在 `s_i == v` 下这两步都是恒等写入。其余字段（寄存器、flags、callEngine、memory、assumptions）同名同构。prefix 本来就不含常量（`block_equivalence.py:2344`、`block_parallel.py:99-100`），所以两边符号天然同名。
  **字面量与符号的差别**只是语法层面的：`havoc(c)` 里是字面量（simplify 能折叠），`havoc(k)` 里是符号加等式。语义相同，这条引理由单测直接用 Z3 钉住（§8 T2）。
- **引理 B（关系分解）**：`relation_goals(e,x,c) = relation_goals(e,x,k) ∧ stack_constant_predicate(D_c)`。`relation_goals` 只从 spec 读 `d/m/f/stack_constants`（`block_relation.py:121-167`），其余目标完全相同。

### 3.3 局部定理：前提加强

`T_k` 对所有满足 `R_k` 的入口成立（havoc(k) 覆盖所有满足 `R_k` 的具体状态，这是现有 havoc 完备性论证，与常量无关）。因为 `R_c ⇒ R_k`，`T_k` 对 `c` 直接成立。这里没有用到 `S(pc)` 的任何性质，所以 **π 丢错槽不会导致假绿**，只会让 `T_k` 变难或失败。

### 3.4 H2：必须按上下文

`T_k` 的出口里，被丢的深槽是入口符号 `s_i`（可能被搬到别的位置）。后继上下文往往要求这个槽等于常量。例如 4236 的 `(5, 855)` 是调用者返回 tag，返回块之后的实例要求它等于 855。只凭 `R_k` 的 H2 **证不出**这一点，也不应该证出。

所以对每个 `c ∈ group(k)` 和 `k` 的每个配对出口 `(i, j)`，检查：

```
premise_k ∧ E_c ∧ e_i.cond ∧ x_j.cond ∧ ¬⋁_{t ∈ frozen(pc')} R_t(e_i, x_j)   应为 UNSAT
```

- `premise_k` 用 `node.premise`（包含 host/div 公理），出口用 `T_k` 的 outcomes（与 `outcome_digest` 对应的那一份）。由引理 A，这就是"`c` 的所有入口的出口"的精确描述。
- 深槽能闭合，是因为出口槽就是入口符号 `s_i`，而 `E_c` 给出 `s_i == v`。块没有写窗口外的槽；档 2 下被搬运的槽仍是同一个符号。
- **目标集不变**，仍是冻结的上下文集合。如果把 `k` 注册为 H2 目标，后继发现会丢掉返回 tag，返回块只能以符号目标证明，等价于把本方案的收益换成路径爆炸，而且 discovery 已经在字面量 havoc 上完成。
- 可选优化：不加 `E_c` 前提，而是 `substitute` 把 `s_i` 的四个 limb（`{prefix}_stack_{d-1-i}_z0..z3`）换成常量。这是对全称式做代入，同样可靠，还能让 store forwarding 折叠。只在 H2 出现 unknown 时启用。
- 附加一条 `context_nonempty_c`（`premise_k ∧ E_c` 为 SAT）作为防呆。它不是可靠性必需，只用来防止 `E_c` 构造错误导致 H2 空真。

### 3.5 必须成立的条件（落地清单）

1. `k.pc/d/m/f == c.pc/d/m/f`，且 `set(K_k) ⊆ set(K_c)`。由消费者检查。
2. `k` 与 `c` 走同一个 `build_havoc` 代码路径和 prefix，唯一差别是少写的常量（引理 A，单测守护）。
3. H2 的前提与出口来自 `T_k` 本身这一次执行（同进程、同 `node`），不重新执行 `c`。
4. discovery 不变：仍在 `havoc(c)`（字面量）上跑 EVM 段来提出后继（`block_parallel.py:77-115`）。
5. worklist 模式（`block_program.py`）**不启用**。它从已证节点的出口做发现（`:289-300`），换成 `k` 的出口后 `_discover` 看到的是符号，会丢常量（`:516-517`）。

## 4. 证书消费者

- `BlockTheorem.complete`、`names == required`：**不变**，`theorem.spec == k`。
- `EdgeCertificate`（`block_program.py:26-35`）：新增字段 `assumed: tuple = ()`，值为 `D_c`（默认空，worklist 不受影响）。
- `ParallelProgramCertificate.valid`（`block_parallel.py:186-218`）：每个上下文 `c` 仍对应一个 node dict，新增 `proof_spec` 字段，检查项改为：
  - `theorem.spec == node["proof_spec"]`（原来是 `== node["spec"]`），并满足 §3.5-1 的弱化关系；
  - `node["expected"]` 与 `node["edges"]` 的配对集合相等（原逻辑不变）。同组上下文共用 `k` 的 expected；
  - 每条边满足 `edge.source == c`，`edge.assumed == D_c`，`_edge_ok` 不变（目标 = 冻结集中该 pc 的全部上下文）。
- `ProgramCertificate.valid`：不变（worklist 不启用）。
- 信任边界不变：H2 公式内容由 `prove_instance` 构造，消费者只核对结构，这与现状相同。`assumed` 字段让"H2 用了哪些额外前提"变成可审计的数据。

## 5. 并行调度与结果 pickle

- 任务单元从 spec 改为组 `(k, contexts)`。worker 先 `prove(k)`，再对每个 `c` 做 H2，返回每个 `c` 一个 dict（共享 theorem 对象）。
- `LeaderFirstSchedule`（`:301-347`）改为对 `k` 排队。它现有的 `(pc, m, f)` leader 分组正好对应"不同深度的 `k`"，逻辑不用改。
- 失败回退：`k` 首轮失败且非 sat，按现有规则重试 full budget。full 仍失败，**或得到 sat**（`D_c` 放宽后的反例可能落在任何上下文之外），就把组拆成单元素组 `k := c`，也就是现状。消费者对 `k == c` 天然接受。
- pickle（`_prove_all` 的 `path_of`，`:359-371`）：键从 `repr(spec)` 改为 `repr(k) + digest(contexts)`。加载时要求 `node["proof_spec"] == k`，并且组成员与当前冻结集导出的组完全一致。store 目录名追加投影规则版本号（例如 `pi=v2`），避免规则变更后复用旧的组结果。
- H2 条数不变（本来就是每个上下文各做一遍），省下的只是局部定理。

## 6. 深度为什么本步不泛化

- `stack_geometry` 写死绝对深度：`byte_offset = d*0x20` 是具体值，`R14 = base + offset`（`cutpoint_relation.py:647-678`），目标里有 `SP == IntVal(d)`（`:1028-1045`）。
- TAG 序言的 `minDepth*32 / maxDepth*32+1` 检查依靠具体 offset 静态判死（注释 `:651-655`：符号 offset 与 envelope 方案已经被否决）。
- `live_stack_prefix` 是 `range(d)` 上的逐槽合取（`:680-692`、`:1046-1050`），深度符号化需要带量词或数组级的关系，离开当前 QF 片段。
- prefix 含深度，TAG 的错误码路径（underflow/limit）依赖深度。

剩余规模：档 2 后 CErc20/Safe 为 1216/1107（已尝试子集），全量冻结集的下界是 2296/1744。深度泛化的上限收益见 §2.3 最后一列（约再减半）。它需要"栈顶 w 槽相对寻址 + 不透明调用帧"的新关系，另立专题。

## 8. 测试

正向测试：
- **T1** `sensitive_slots`：返回块（动态 JUMP）保留返回 tag 槽；DUP/SWAP 可达性；只搬运的槽在档 2 被排除；三份 fixture 上 `window == min_depth`。
- **T2 引理 A**：取一个多常量 spec `c` 与 `k = π(c)`，同一 prefix，用 Z3 证 `premise_k ∧ E_c ⇒ Stack_k == Stack_c ∧ stack_mem_k == stack_mem_c`，并证 `havoc_relation(c)` 在 `havoc(k) ∧ E_c` 上成立。
- **T3 端到端**：选一个"内部函数被 ≥2 处调用"的小 fixture（需新造，或从 `muti_block_08` 里挑），`dedup` 开/关都是 VERIFIED，且开启后局部定理数更少。

变异测试（每条都必须让证书被拒或被扣留）：
- **M1** H2 去掉 `E_c`：返回后继需要常量的边不闭合，证书被扣留（sat 或 unknown）。
- **M2** 消费者：`proof_spec` 的 m/f/d 与 `c` 不同、`K_k ⊄ K_c`（值不同）、`theorem.spec != proof_spec`、`edge.assumed != D_c`、组内某个 `c` 少一条边，这些情况全部 `valid() == False`。
- **M3** 把 `k` 混进 H2 目标集：`_edge_ok` 拒绝（targets 不等于冻结集）。
- **M4** 故意用丢掉返回 tag 的坏 π：不允许产生假绿。期望 `k` 失败并拆组回退，最终证书仍然有效。这条验证"π 不可信"。
- **M5** pickle：组成员变化或规则版本变化时不复用旧结果。
- 按 [[feedback_verify_tests_actually_collected]] 核对 collected 数增减。

## 10. 预期收益与风险

收益：局部定理数 −35%（CErc20）/ −31%（Safe）。按兄弟实例占首个 75% 的开销折算，节点阶段墙钟约 −20~25%。难节点收益更大：一个 `k` 的 full budget 重试可以覆盖整组，不必每个上下文各超时一次。

风险：
- **`k` 比 `c` 难**：字面量折叠消失。档 2 只丢未被计算使用的槽，理论上影响很小；兜底是拆组回退，最坏退化为现状加一次失败的 `k` 尝试。
- **H2 变难**：等式前提代替字面量。可以用 §3.4 的 `substitute` 变体缓解。
- **性能收益被 H2 吃掉**：H2 条数不变，但目前没有 H2 占比的实测，S3 需要记录。
- **pickle 兼容**：旧结果目录不复用（规则版本进目录名）。

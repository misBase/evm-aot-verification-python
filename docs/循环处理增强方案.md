# 循环处理增强方案

目标：把当前"有界展开到 max_depth"的循环处理,升级为**对符号 bound 循环可封闭的归纳式验证**,同时保持全自动、fail-closed,不引入任何需要人工按合约干预的环节。

## 1. 问题与现状

### 1.1 问题

真实合约(如 Compound、Safe)含符号 bound 循环——典型如动态 string 的存储读写循环,trip count = ceil(len/32),而 len 从 storage/calldata 读出,是符号值。符号执行在回边处每轮 fork 一次,展开永远无法封闭;提高 `max_depth` 只是多展开几轮、推迟失败。

### 1.2 现状(截至当前复核)

| 环节 | 行为 |
|---|---|
| EVM 侧展开 | `DFSStrategy` + `max_depth`,超深状态在 `evm_ir/cfg_strategies.py` 中**静默跳过**,无计数、无 coverage 证书;当前 executor 另有 `static_loop_headers` + `max_iteration=500` 的异常兜底,但这不是终止路径 coverage 证书 |
| x86 侧展开 | depth 剪枝计数 + `path_coverage_certificate()` fail-closed(`x86_64/cfg_executor.py`) |
| 兜底 | `path_observations` 模式下 `_check_path_coverage`(`verification/equivalence_paths.py`)对两侧做 SMT 覆盖检查,符号 bound 循环必然 SAT → 报 coverage 失败 |
| 可观测面 | 当前 `PathObservation` 的 8 个检查项只覆盖 return metadata、return memory、storage、transient storage;v1 只使用这些已建模 observable,`status/gas/logs/revert_kind` 归入后续 v2/gas 阶段,不作为 P0/P2 前置 |

即:当前对符号 bound 循环**不会假绿,但也证不过去**。另有一个已知盲点:`to_z3` merged 模式下 EVM 侧被剪路径静默消失,无证书兜底(见 §7 P0)。

## 2. 方法定位:translation validation 谱系与 Alive2 对比

### 2.1 三条技术路线

编译正确性验证有三条经典路线,本方案属于第二条,并借第三条(CompCert)的证明骨架把循环从有界升级为无界:

**(a) 编译器验证(CompCert,Leroy 2006/2009)。** 在 Coq 中一次性证明编译器本身正确,对所有输入程序生效。正确性表述为 **forward simulation**:存在关系 ~,源程序每走一步,目标程序走一步(lock-step)、多步(plus)或零步(stuttering,配测度递减防止无限空转),且 ~ 保持;再由目标机确定性得到 backward simulation(真正的精化)。代价是数年级的人工证明投入,且编译器每次改动都要重证。

**(b) Translation validation(Pnueli et al. 1998;Necula, PLDI 2000)。** 不证编译器,证**每一次编译的产物**:给定源程序与编译输出,自动推断两者程序点之间的对应(cutpoint)与状态关系,再逐段检查关系保持。编译器保持黑盒,验证全自动、按次进行。Necula 2000 把这条路线做到了带优化的真实编译器上——本项目正是这一形态:对每个合约的 (EVM IR, x86) 对做验证,go-hpc-evm 保持黑盒(仅在 Tier 2 引理与 profile 处做一次性白盒投入)。

**(c) 有界 translation validation(Alive2,Lopes et al., PLDI 2021)。** 把 src/tgt 两个函数整体编码进 SMT 查精化,循环只展开常数轮——对循环是有界结论。

本方案的定位:**形态是 (b),循环处的证明义务用 (a) 的 simulation diagram 表述**——§4 的三条查询(Base/归纳步/出口)就是 lock-step simulation diagram 在循环头 cutpoint 上的 Z3 实例化。EVM 一条指令对应 x86 一段模板代码,属于 "plus" 图;我们只在 cutpoint(循环头、块边界)处陈述关系 R,段内由有界符号执行吞掉,这是 translation validation 的标准 cutpoint 化简。两侧语义均确定(host 非确定性折叠进 UF),forward 方向即足够。

### 2.2 与 Alive2 的对比

Alive2 是最接近的工程参照,但关键前提不同,差异大多对本项目有利:

| 维度 | Alive2(LLVM) | 本项目(EVM AOT) |
|---|---|---|
| 变换结构保持性 | 无:优化任意重构 CFG(循环旋转/向量化/块合并),src/tgt 无结构对应,只能整函数黑盒比较 | 有:逐指令模板直译,循环回边 1:1,可用 simulation |
| 循环处理 | 被迫有界展开(常数轮),结论有界 | v1 在 no-OOG/no-stack-limit envelope 内做锁步/单侧归纳,**trip count 无界完整证明**;有界展开仅作降级 |
| UB/非确定性 | undef/poison/UB 占编码复杂度大头,精化非对称(tgt 可更 defined) | EVM 无 UB,语义全函数式;非确定性(CALL 结果、SHA3)折叠为两侧共享 UF |
| 可观测面 | 返回值、最终内存、UB 域 | v1 覆盖当前 checker 已有 observable(return metadata、return memory、storage、transient storage);logs、revert_kind、完整 status 与 **gas** 留到 v2/gas 阶段 |
| 循环终止 | 无天然论证 | v1 不证明 gas/OOG 分支,而是显式采用 §4.3 的 no-OOG/no-stack-limit cutpoint assumption;gas 单调递减与 OOG 对齐留到 v2/gas 阶段 |
| 语言形态 | src/tgt 同为 LLVM IR,一套编码器用两次 | 跨语言:栈机 ↔ 寄存器机,两套编码器 + 状态映射(即 §4.1 的 R,骨架来自编译器自身的栈布局约定) |
| 位宽压力 | 常见 ≤64 bit | 256 bit(4 limb);已有对策:holiman 分段建模、UF 折叠、div 桥接 |

一句话:**Alive2 展开循环是因为它别无选择;本项目的编译器结构保持,所以有更好的选择**。真正值得从 Alive2 借鉴的是两点工程纪律:诚实报告(timeout/不完整必须显式暴露,对应本方案的 prove-or-honestly-degrade 与 coverage 证书)和精化查询的组织方式。若未来管线在 AOT 之后追加 LLVM 级优化,那一段与 Alive2 的问题域相同,可直接复用 Alive2 本身。

## 3. 循环分类

验证目标(go-hpc-evm 逐指令模板直译,无循环重构/展开/向量化)决定了循环宇宙可精确二分:

| | Tier 1:EVM 源级循环 | Tier 2:x86-only 内生循环 |
|---|---|---|
| 来源 | 合约源码(Solidity/Yul)编译产物 | codegen 模板(`impl_amd64.go`) |
| 两侧形态 | 都有循环,JUMPI 回边 ↔ Jcc 回边 1:1 | 仅 x86 有循环;EVM 语义是一步闭式 Array 操作 |
| 归纳命题 | 关系式:"两侧保持同步" | 单侧:"循环净效果 = EVM 闭式结果" |
| 不变式来源 | 固定通用模板(现有耦合关系),零合成 | 少量手写模板,一次性、全合约复用 |
| 实例 | string 拷贝、数组遍历 | CALLDATACOPY/CODECOPY/RETURNDATACOPY/MCOPY 的拷贝循环 |

不存在第三类(EVM 有环而 x86 展开):该编译器不做 unrolling。

Tier 2 的循环清单(按 `$GOPATH/src/github.com/bcds/go-hpc-evm/evm/aot/impl_amd64.go` 回边统计,共 **7 条**):

```text
compileMakeDataCopy         1 条 (服务 CALLDATACOPY/CODECOPY)
compileEVMRETURNDATACOPY    1 条
compileEVMMCOPYFromLow      2 条 (字循环 + 尾循环)
compileEVMMCOPYFromHigh     3 条 (反向字循环 + SHRStart 对齐移位循环 + 尾循环)
```

其中 `compileEVMMCOPYFromHigh` 的 `SHRStart` 不是 memcpy 形状,而是把已读入 `tmp` 的 qword 右移到尾部起点的寄存器循环;P3 引理必须单独覆盖这一段,不能被 §5.1 的纯内存模板吞掉。

清单封闭性**不靠人工清点**,由 §6 的结构守卫强制。

### 3.1 Tier 1 前提的实证(2026-07-02,CErc20 + Safe fixture)

Tier 1 依赖的每条前提都已在真实 fixture 与编译器源码上核实:

**跳转全部静态化,无 dispatcher。** IR 生成期 `resolveSymbolicJumps`(`evm_ir.go`)把跳转目标解析为静态形式。两个 fixture 的 JUMP/JUMPI 形态统计:

```text
CErc20.json: 723 blocks | static_single=640  resolved_multi=83  dynamic_unresolved=0
Safe.json  : 742 blocks | static_single=659  resolved_multi=83  dynamic_unresolved=0
```

codegen 三种形态(`impl_amd64.go` compileEVMJUMP/JUMPI):静态单目标 → **直接 JMP/JNE**;多目标(resolved_multi,主要是函数返回跳)→ **CMPQ+JEQ 比较链**(边仍显式);完全未解析 → 进中央 jumpCode dispatcher。**第三种在两个 fixture 中出现 0 次**;若出现,§6 守卫直接 fail(dispatcher 不建模)。

**真循环极少,且"往回跳"≠循环。** 按块序统计"往回跳"有 256 个(CErc20),但支配分析(natural loop:边 u→h 且 h 支配 u)显示其中**真循环回边仅 18 条**(约 8/9 个循环头,按统计口径略有差异,含多 latch 共享头);Safe 仅 **4 条**。其余 238 个是 Solidity 内部函数的**调用/返回边**(共享子例程位于前部块)——它们每条路径上返回地址具体,不产生无界展开,不需要归纳,现有展开即可处理。**因此 P1 配对器必须做支配分析识别 natural loop,严禁用朴素"目标地址在前"判定**——否则会把函数调用误当循环。

**循环头局部栈深静态可知,但不能只覆盖局部窗口。** IR block 携带 StackDepth/MinDepth/MaxDepth;注意其为**相对当前 stackBasePoint 的深度**(codegen 在 JUMP/JUMPI 处以 `StackDepth*stackBytesSize` 动态调整栈基)。这个静态深度可用于限定循环体局部触碰范围,但 Solidity 内部函数中的循环还会在退出后读到 caller-frame 中的返回地址和局部变量;这些槽不在当前 stackBasePoint 之上。若 R 只钉住局部窗口,归纳步按 §4.3 havoc 后会把 caller-frame havoc 成互不相等,③ 出口继续执行到函数返回时必然伪 SAT → 降级。因此 R 必须覆盖后续可能被读到的 live 栈前缀(见 §4.1)。

**执行器可从任意 cutpoint 启动。** x86 侧已有先例(单指令等价性检查从截断 core 执行);EVM 侧 `SymbolicExecutor` 接受 blocks 列表,从任意块构造初始 GlobalState 是工程问题,无原理障碍。

## 4. Tier 1:锁步关系式归纳

### 4.1 耦合关系 R

R 是"两侧状态同步"的谓词,骨架来自现有 等价性检查的状态映射,但不能只照搬最终态 observable checker。循环 cutpoint 位于程序中间,尤其可能位于 Solidity 内部函数内部,所以 R 必须覆盖后续会被读到的 caller-frame 栈槽。

```text
R ≜  逻辑 sp / callEngine stack pointer / stack byte offset 一致
   ∧ x86 当前 R14 block stack base 与 EVM stackBasePoint 的平移关系一致
   ∧ live 栈前缀一致:
        对后续可能被读取的每个 EVM 栈槽 i,
        EVM Stack[i] = x86 STACK 域中对应的 4-limb Uint256
        (第一版保守取从栈底到当前 SP 的 live prefix;后续可用 liveness 缩窄)
   ∧ memory 平移一致:
        对每个 EVM memory offset a,
        EVM Memory[a] = x86 evm_mem[R15 + a]
   ∧ return metadata / storage / transient storage 等当前 checker 已建模 observable 相等
   ∧ pc 位于配对的循环头
```

这里的栈地址采用当前 R14 block stack base 与 Go stack pointer 的 limb 映射:逻辑栈顶在 `R14 + (sp_limb - 4) * 8`,次栈顶在 `R14 + (sp_limb - 8) * 8`,依此类推;不得写成简单的同向正偏移公式。循环头静态深度 `k` 只用于界定循环体局部读写范围和 frame 影响范围,**不是** R 的覆盖范围。

`status/gas/logs/revert_kind` 等完整链上 observable 不属于 v1 的 R 合取;v2/gas 阶段先补 EVM 侧 gas/OOG 与相关 observable 建模后,再把它们加入 R。

R 不含任何"循环在算什么"的功能信息。live 栈前缀可以用有限槽位展开实现;隐含前提是同一循环头的绝对栈深可按有限深度类枚举,归纳查询按深度类分别实例化。无递归/无调用环的 Solidity 产物满足该条件;若存在导致栈深无界的调用环,配对阶段未必失败,但再次到达同一循环头时可能落入新的深度类,导致当前 R 实例在 ②(b) 处失配并降级。若后续改为符号深度,可用与 §5.2 同款的 lambda/witness 编码保持 QF-friendly 查询。

### 4.2 三条有界查询

把"任意轮迭代后仍等价"按归纳法拆成三条**无环、Z3 直接可解**的查询:

```text
① Base   : 从入口(或上游 cutpoint)符号执行到两侧循环头,证明 R 成立。
② 归纳步 : 假设两侧位于循环头且 R(s_evm, s_x86) 成立(s_* 为 havoc 后的任意符号状态),
           两侧各执行一轮循环体(有界路径枚举),证明:
           (a) EVM 级控制分支逐对一致:EVM JUMPI/loop-exit 走回边 ⟺ x86 对应 Jcc 走回边;
               x86 模板内部实现分支(holiman 分段、溢出检查等)属于 plus-simulation 段内分支,
               由有界枚举吞掉,不要求与 EVM 分支一一配对
           (b) 都走回边 ⇒ 回到循环头时 R 保持
           (c) 都走出口 ⇒ 出口处 R 保持
           (d) 体内合法终止路径 ⇒ 当场证明当前 checker 已有终止可观测量等价
               (return metadata/return memory/storage/transient storage);
               x86 TAG OOG/栈错误分支由 §4.3 cutpoint assumption 压成不可达,
               status/gas/logs/revert_kind 留到 v2/gas 阶段
③ 出口   : 从"出口处 R 成立"继续符号执行到下一 cutpoint 或终止,普通有界查询。
```

归纳论证:第 0 次到达循环头 R 成立(①);第 n 次成立则第 n+1 次成立(②b),且两侧永远同时决定继续/退出(②a)——任意轮数下同步,退出后同步到底(②c+③)。**符号 bound 被归纳直接吞掉**。②d 对 v1 可建模的体内合法终止路径仍是必需分支:这类路径不经过回边/出口,漏掉即健全性缺口;gas/OOG 与 TAG 栈错误路径由 §4.3 的显式前提排除,留到 v2/gas。

### 4.3 havoc 纪律(实现契约)

归纳步必须**主动 havoc 一切 R 未钉住的状态**:x86 scratch 寄存器、CPU flags、两侧路径条件。禁止复用从入口符号执行携带路径条件的状态——那会把归纳静默退化成有界证明(教训同 path-assumption 全局泄漏事故)。

但 R 钉住的状态不能被 havoc 成两侧互不相关值:live 栈前缀、`R15` 平移后的 EVM memory、storage/transient storage、必要的 callEngine side-channel(sp/stack base/return data metadata 等当前 checker 已建模状态)必须保持耦合。havoc 的错误方向是安全的:havoc 过头只产生伪 SAT(降级),不会假绿。准则:**宁滥 havoc,勿漏 havoc;但先把 R 写够强**。

v1 还必须在每个 cutpoint 显式加入 no-OOG/no-stack-limit assumption:循环头的 `gas_remaining` 大于单轮循环体加出口段的静态消耗上界,总栈长处在不会触发栈下溢与 `maxStack` 超限的范围内。原因是 x86 每个块入口 TAG 都有 `makeStaticUseGas` OOG、栈下溢、栈超限三类错误分支;全程序 develop 模式用具体大 gas 与合法栈区间把它们静态压死,而归纳步 havoc 后若不补这个前提,这些分支会被符号激活,EVM 侧又没有对应 gas/栈错误路径,②(a)/②(d) 会稳定伪 SAT。这个 assumption 是把现有 no-OOG/no-stack-limit 抽象显式化,不是新增信任;Base 处只核对第 0 次到达 cutpoint 时 envelope 成立,归纳步则把它作为 havoc 后状态的新鲜前提,不声称它会在无界轮次中由循环自身保持。v1 的完整证明结论必须携带 no-OOG/no-stack-limit envelope 标注。

全局无损 assumption(如 CALLDATALOAD hi-192==0)允许作为②的前提,但必须是路径无关的全局先验。

### 4.4 嵌套、多出口与多 latch

- 嵌套循环:所有循环头同时设为 cutpoint,cut 后所有段无环,统一走三条查询,无需"由内向外"分层。
- 多出口(break/continue):②(a)(c) 按出口边逐对处理,结构不变。
- 多 latch(实证中常见,如 CErc20 一个循环头对 4–6 个 latch):循环头仍是唯一 cutpoint,②(b) 对每条 latch 分别证明,骨架不变。
- 不可归约 CFG(手写内联汇编):配对失败,走 §6 降级。

## 5. Tier 2:单侧归纳(codegen 拷贝循环)

### 5.1 不变式模板(快照相对形式)

对 memcpy 形状的循环,Inv 相对**循环前内存快照 mem₀** 表述,但 Tier 2 不能只建纯内存等式。真实模板中还存在索引寄存器、`src/dst/size` 指针寄存器以及 MCOPY 尾部 `tmp` 右移寄存器状态:

```text
Inv(i) ≜  mem = F(i)                          (等式形式,见 5.2)
        ∧ index/size/src/dst/tmp 等活跃寄存器满足模板对应关系
        ∧ 0 ≤ i ≤ len
        ∧ 尚未读取的源区间 = mem₀ 原值
```

注意:**不能写"源数据未被破坏"**——MCOPY 重叠场景下源区间必然被部分覆写,FromLow/FromHigh 分方向正是保证"尚未读的部分完好"。已读部分被覆写是合法的;Inv 的分区方向随 FromLow/FromHigh 相反。

`compileEVMMCOPYFromHigh` 是三段串联复合引理:反向 8-byte 字循环、`SHRStart` qword 对齐移位循环、尾 byte 循环。`SHRStart` 的不变式核心是 `tmp = tmp0 >> (8*i)` 与剩余移位计数的寄存器关系;它不修改 memory,因此不能套用纯 `mem = F(i)` 模板。

### 5.2 等式编码(规避量词)

"前 i 个字已拷完"不用 ∀j<i 量词,改用参数化闭式:

```text
F(i) = Lambda(a, If(dst ≤ a < dst + 32*i, 闭式源数据[a - dst + off], mem₀[a]))
```

归纳步变成证 `一轮循环体(F(i)) = F(i+1)`,数组外延等价由 Z3 内部处理,查询保持在 QF-friendly 片段。

### 5.3 三条查询与引理化

```text
① Base   : 循环入口处 Inv(0)(索引清零;F(0) = mem₀ 平凡成立)
② 归纳步 : Inv(i) ∧ i < len ⇒ 一轮后 Inv(i+1)     (i 符号,任意 len 封闭)
③ 出口   : Inv(i) ∧ 退出条件 ⇒ 当前段达到该段目标状态;
           串联所有段的出口状态后,mem = F(len) = EVM 闭式结果
           另单独覆盖 len = 0(循环整体跳过,直接 Inv(0) + 出口)
```

7 条回边各证一次(参数 len/dst/off 保持符号化),产出 7 条**模板正确性引理**。之后所有合约验证遇到这些循环时:模板匹配 → 引用引理 → 用 EVM 闭式语义替换循环,不再展开。哲学与 `mul_uf` 一致:对合约黑盒(全自动),对编译器白盒(一次性投入);引理绑定编译器版本,codegen 变更时模板匹配失败 → fail-closed。

## 6. 结构守卫与降级管线

核心守卫(放在 x86 CFG 构建后):

```text
0. 前提检查:IR parser 必须解析并保留 `immediate_set`,用它区分
   resolved_multi 与真正 dynamic_unresolved。IR 中出现 dynamic_unresolved 的
   JUMP/JUMPI(将编译为 jumpCode dispatcher)⇒ 验证失败
   (dispatcher 不建模,fail-closed)。
1. 两侧分别做支配分析,识别 natural loop(边 u→h 且 h 支配 u)。
   注意:"目标地址在前"不是循环——真实合约中多数按序回跳是 Solidity
   函数调用/返回边(CErc20:256 个按序回跳中仅 18 条真循环),误判会把
   子例程调用当循环处理。
2. x86 侧每条 natural-loop 回边,必须满足其一,否则验证失败:
   (i)  与某条 EVM natural-loop 回边完成 Tier 1 配对(循环头支配结构
        + 静态跳转目标校验,配不上不猜)
   (ii) 命中 Tier 2 已证引理的模板(指令序列匹配,fail-closed 同 MUL slice parser)
```

该守卫同时防御"编译器升级悄悄新增循环"。整体管线是 **prove-or-honestly-degrade**:

```text
1. 默认有界展开 + coverage 证书(现状) ── 无循环/具体 bound 循环直接过
2. coverage 失败且反例落在回边 → 尝试 Tier 1 / Tier 2 归纳
3. 归纳步 unsat → v1 给出 no-OOG/no-stack-limit envelope 内的完整证明,
   trip count 任意长度封闭,但报告必须保留 envelope 标注
4. 归纳步 SAT/unknown → 降级:有界展开 + 自动长度 assumption(如 len ≤ 64),
   结论显式标注"bounded + assumption",不冒充完整证明
```

关键语义:**归纳步 SAT ≠ 找到 bug**。R/Inv 太弱时归纳步给伪反例,管线不能把它当反例报告;可信反例只能来自降级后的有界模式(bound 内真 bug 必现)。归纳失败的正确输出是"inconclusive → 降级",这保证任何一格都不假绿。

## 8. 边界与限制

- 归纳完备性依赖 R/Inv 够强;跨回边存活的 scratch 值(栈机 codegen 下预期不存在)会导致伪 SAT → 降级,不会漏检。
- R 若不覆盖 caller-frame 中后续会读到的 live 栈槽,Compound string 类函数内循环会因出口后函数返回读取 caller-frame 而系统性伪 SAT → 降级;本方案第一版默认比较 live 栈前缀就是为避免该验收用例退化。
- Tier 2 引理与编译器版本绑定,`impl_amd64.go` 模板变更需重证(模板匹配失败会强制暴露)。
- 含 dynamic_unresolved 跳转(jumpCode dispatcher)的合约整体拒绝——实证中 Solidity 产物全部可静态解析,该限制目前不约束任何目标合约。
- 降级格子中超出 bound 且不满足 assumption 的行为不被覆盖——但在报告中显式声明,非盲区。
- host 调用(SHA3/CALL 等)在循环体内时仍按现有 UF/bridge 机制处理,归纳框架不改变其语义信任模型;但 P2 必须显式校验循环体内 EVM/x86 bridge site 配对,不能只依赖整程序地址序枚举。
- v1 暂不证明 gas、OOG、logs、revert_kind 与完整 status observable;后续 v2/gas 阶段需要先补 EVM 侧 gas/OOG 语义,再扩展 `PathObservation`/checker 并启用 §4.1 中对应 R 合取。

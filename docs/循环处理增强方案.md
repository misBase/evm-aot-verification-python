# 循环处理增强方案

## 0. 方案概述

### 0.1 一句话

把当前"有界展开到 `max_depth`"的循环处理,升级为**对符号 bound 循环可封闭的证书式验证**:循环单独完成归纳/闭式证明,主验证器在 cutpoint 处消费证书并把循环折叠成一条 summary edge,不再把无界循环展开到 `max_depth`。全流程保持自动、fail-closed,不引入需要人工按合约干预的环节。

### 0.2 核心思想

**(1) cutpoint 归纳取代展开。** 在 CFG 上选一组程序点(本方案取循环头),使切开后剩余的图无环;在每个 cutpoint 上陈述耦合关系 `R`,证明"任意 cutpoint 到任意 cutpoint 的无环段保持 `R`"。无界性被归纳吞掉,而不是被展开吞掉。

**(2) 循环宇宙的两层分类。** 目标编译器逐指令模板直译、不做 unrolling/向量化,循环因此可精确二分:EVM 源级循环(两侧都有环,需**关系式**证书)与 codegen 内生循环(仅 x86 有环,可用**单侧闭式** summary)。两者的证明形态与信任边界完全不同,不可混用。

**(3) pre-prove, fold, or honestly degrade。** 先证后折叠;证不出来就如实降级为 inconclusive,绝不用"归纳步 SAT"冒充反例,也绝不让任一格子静默通过。

### 0.3 整体管线

```text
  ┌─ 0. 静态守卫 ───────────────────────────────────────────┐

  └────────────────────────┬────────────────────────────────┘
                           ↓
  ┌─ 1. Tier 2 预处理 ─────────────────────────────────────┐
  │  模板命中 + 引理/codegen 指纹有效 → 注册单侧闭式 summary │
  │  未命中 → fail-closed 或显式 bounded 降级                │
  └────────────────────────┬────────────────────────────────┘
                           ↓
  ┌─ 2. Tier 1 证书生成 ───────────────────────────────────┐
  │  循环头设为 cutpoint,只执行无环段:                      │
  │  ① Base → ② 归纳步(逐深度类) → ③ 出口(逐出口)        │
```

### 0.4 关键设计决策一览

| 决策点 | 结论 | 依据 / 取舍 | 详见 |
|---|---|---|---|
| 循环处理方式 | cutpoint 归纳,不靠提高 `max_depth` | 提高 depth 只是推迟失败,对符号 bound 永远无法封闭 | §4.1 |
| 三条查询的实现 | 归约到**同一个**"段执行 + 路径矩阵验证"流程,只是参数不同 | 三套独立实现必然漂移;共用一套后 fail-closed 语义只需守一处 | §4.3 |
| 循环分类 | Tier 1 关系式证书 / Tier 2 单侧闭式 summary | 编译器结构保持使二分精确;两者信任边界不同 | §3.1 |
| gas 的位置 | cutpoint `R` 里(三档都要)**且** terminal observable(两档) | gas 是决定控制流的内部状态,不是纯 observable | §4.5.4 |
| status 的位置 | terminal observable;cutpoint 处只作**结构前提**(两侧均 running),五处覆盖 | 写进 `R` 是过强约束,除制造降级无收益 | §4.5.6 |
| no-OOG/no-stack-limit envelope | **取消** | EVM 侧 gas/OOG/status 已建模,错误终态改由 ②(d) 配对证明 | §4.2 |
| 定理适用域 | 域约束不是简化假设,必须**域内进、域内出** | 一轮扩容跨出域外,下一轮就在域外复用定理 | §4.4 ② |
| Base 的 coverage 门 | **非对称**:EVM 侧必须完整,x86 侧容忍深度剪枝 | 两侧漏路径的后果不同:一个不健全,一个 fail-closed | §4.2 |
| OOG 路径膨胀 | 先分别生成 `oog_evm`/`oog_x86`,**证等价后**才桥接 | 直接共享判定会把待证命题假设掉,掩盖静态 gas 常量编错 | §4.8 |
| `GasCheck.OFF` 档归纳 | 应用域内有 reachable host-gas 操作 ⇒ 一律 inconclusive | OFF 不建模 host gas,OOG 阈值判 `S>G` 而非 `S>G−H` | §7.3 |
| 深度类 | 绝对栈深有限枚举 + 两条完备性义务 | 符号深度是换机制,归入 cutpoint 泛化 | §4.5.6 |
| 终止性 | gas 递减作 ranking function + 六项外部前提**进证书** | 单轮递减推不出有限退出 | §4.4 ②(e) |
| `lastGasCost` | 两侧相等 **且** 各自 = `memoryGasCost(MSize)` | 仅相等是健全性最低要求;派生不变式避免 havoc 过近似 | §4.5.3 |
| 表示层闭包 | side-channel 属性 ↔ CALLENGINE limb 镜像必须进 `R` | 实测:不加时 `R` 接受"属性对、limb 陈旧"的状态 | §4.5.5 |
| 调用/返回伪回边 | 识别是**达成率优化**,非健全性机制 | 误排除 fail-safe;长期正解是 cutpoint 泛化 | §6 |

### 0.5 收益边界与当前结论强度

**收益边界:本方案解决封闭性,不解决可扩展性。** CErc20 有 723 个 EVM block,而 context-insensitive natural-loop 候选只有 9 个、其中按形态疑似真实循环的仅 4 个小自环;其余按块序回跳的边是 Solidity 内部函数的调用/返回,每条路径上返回地址具体、不产生无界展开。大合约的主导成本来自内部函数调用链而非回边(§3.3)。**不要把循环归纳当作性能手段**——那是 `docs/cutpoint泛化方案.md` 的方向。

**当前结论强度。** 早先记录的两项阻塞已兑现:`R` 的镜像闭包已补(实测 6/6 镜像字段拒绝陈旧 limb,修复前是 5/5 接受),主验证器已能在 paired cutpoint 消费证书(`fold_loops`,§4.7)。

**但机制齐全不等于覆盖率。** 两份真实合约的 13 对配对循环里,**6 对连结构预检都过不去**(出口口径不对称),通过的 7 对中已证 3 对、1 对撞规模墙、3 对未测;端到端折叠链路从未在真实合约上跑通。详见 **§9.0**——读完成度时以那一节为准,不要只看 §9 表格里的"已落地"。

**仍需在结论里如实带上的边界有四条:**

1. **配对仍是顺序配对,只是多了一道独立兜底。** 循环配对与出口配对都按顺序进行,允许同 latch 数的错误置换;现在有 TAG 序言的 `(static_gas, min_depth)` 指纹交叉验证(§6)在证明之前把置换挡掉,验收 12 的反向哨兵也已建立。但这是**兜底**,不是"配对本身正确"——指纹的判别力依赖"同一合约内三元组两两不同"这个**实测观察**(三份合约 19 对成立),不是定理。
2. **三个开关都默认关闭。** `loop_guard`、`fold_loops`、`enable_oog_bridge` 均需显式开启。默认路径的 VERIFIED **不含**循环结构检查,报告消息会就此显式声明,但读结论时必须看这一行。
3. **验收基准依赖手动运行,不进常规回归**(§9.2)。验收基准 1 已通过(CErc20 string 循环归纳成功,约 283 s),但它是 `skipif(not RUN_LOOP_INDUCTION_ACCEPTANCE)`、连 `-m slow` 都跑不到。它曾经长期红着而无人发现——**"§9 无未落地条目 + 全量绿"并不蕴含"验收基准成立"**。

4. **OOG 桥接把路径膨胀从 10× 压到 8×,没压回 envelope 级别**(§9.1)。取消 envelope 让预过滤后的配对矩阵从 8 对涨到 80 对;桥接以 12 条查询、约 0.3 s 剪掉 16 对。原因是它只在**循环头**的 gas guard 上分区,而膨胀主体来自块内其它 TAG guard——要压回原量级需把桥接推广到每个块入口。

## 1. 问题与目标

真实合约(如 Compound、Safe)含符号 bound 循环——典型如动态 string 的存储读写循环,trip count = `ceil(len/32)`,而 `len` 从 storage/calldata 读出,是符号值。符号执行在回边处每轮 fork 一次,展开永远无法封闭;提高 `max_depth` 只是多展开几轮、推迟失败。

当前对符号 bound 循环**不会假绿,但也证不过去**:两侧执行器都记录 depth/flush-depth 剪枝并由 `path_coverage_certificate()` 对 incomplete 显式 fail-closed(`evm_ir/cfg_executor.py`、`x86_64/cfg_executor.py`)。

目标是把这个"证不过去"变成"证得过去",且不牺牲任何 fail-closed 性质。

前提条件已就绪:**EVM 侧 gas、OOG 与 status 语义已落地**(见 `docs/Gas一致性验证设计.md`)。gas 是决定控制流的内部状态而非仅比较用的 observable,OOG 是真实分叉,`GasCheck` 分 `OFF`/`FIXED_BUDGET`/`FULL` 三档;EVM 侧 TAG 守卫三分支已镜像 x86(终止状态次序 `OUT_OF_GAS` → `STACK_UNDERFLOW` → `STACK_REACHED_LIMIT`),错误码见 `evm_ir/status_code.py`。这使得早期方案依赖的"no-OOG/no-stack-limit envelope"前提不再必要(§4.2)。

一处尚未纳入的可观测量:`common/path_observation.py` 的 `OBSERVATION_KEYS` 共 10 项(`condition / offset / length / memory / base_addr / has_return_data / storage / transient_storage / status_code / gas`),**logs 不在其中**(§7.2)。

## 2. 方法定位

### 2.1 三条技术路线

编译正确性验证有三条经典路线,本方案属于第二条,并借第三条(CompCert)的证明骨架把循环从有界升级为无界:

**(a) 编译器验证(CompCert,Leroy 2006/2009)。** 在 Coq 中一次性证明编译器本身正确,对所有输入程序生效。正确性表述为 **forward simulation**:存在关系 `~`,源程序每走一步,目标程序走一步(lock-step)、多步(plus)或零步(stuttering,配测度递减防止无限空转),且 `~` 保持;再由目标机确定性得到 backward simulation。代价是数年级的人工证明投入,且编译器每次改动都要重证。

**(b) Translation validation(Pnueli et al. 1998;Necula, PLDI 2000)。** 不证编译器,证**每一次编译的产物**:给定源程序与编译输出,自动推断两者程序点之间的对应(cutpoint)与状态关系,再逐段检查关系保持。编译器保持黑盒,验证全自动、按次进行。本项目正是这一形态:对每个合约的 (EVM IR, x86) 对做验证,go-hpc-evm 保持黑盒(仅在 Tier 2 引理与 profile 处做一次性白盒投入)。

**(c) 有界 translation validation(Alive2,Lopes et al., PLDI 2021)。** 把 src/tgt 两个函数整体编码进 SMT 查精化,循环只展开常数轮——对循环是有界结论。

本方案的定位:**形态是 (b),循环处的证明义务用 (a) 的 simulation diagram 表述**——§4.4 的三条查询就是 lock-step simulation diagram 在循环头 cutpoint 上的 Z3 实例化。EVM 一条指令对应 x86 一段模板代码,属于 "plus" 图;只在 cutpoint 处陈述关系 `R`,段内由有界符号执行吞掉。两侧语义均确定(host 非确定性折叠进 UF),forward 方向即足够。

**证书折叠不消解无界义务。** 折叠只是把已证义务从主证明中抽成一条可复用边。循环语义是 `Body⁰ ∪ Body¹ ∪ …` 的不动点;这一"任意 n"义务仍必须由 Tier 1 归纳或 Tier 2 闭式引理完成。区别只在于:证明完成后,主验证器消费证书,而不是再次展开循环。

**gas 递减为 latch 提供 ranking function。** simulation diagram 的 stuttering 分支需要一个良基测度防止无限空转。gas 单调递减正是候选测度。但要强调:**gas 只是循环 latch 的 ranking function,不等于单独补齐了整个 simulation 的终止论证**——完整结论依赖 §4.4 ②(e) 列出的六项前提。

### 2.2 与 Alive2 的对比

| 维度 | Alive2(LLVM) | 本项目(EVM AOT) |
|---|---|---|
| 变换结构保持性 | 无:优化任意重构 CFG(循环旋转/向量化/块合并),src/tgt 无结构对应,只能整函数黑盒比较 | 有:逐指令模板直译,循环回边 1:1,可用 simulation |
| 循环处理 | 被迫有界展开(常数轮),结论有界 | 锁步/单侧归纳,trip count 无界;有界展开仅作降级 |
| UB/非确定性 | undef/poison/UB 占编码复杂度大头,精化非对称 | EVM 无 UB,语义全函数式;非确定性(CALL 结果、SHA3)折叠为两侧共享 UF |
| 可观测面 | 返回值、最终内存、UB 域 | return metadata、return memory、storage、transient storage,status 与 gas 已纳入;logs 等链上 observable 仍在范围外 |
| 循环终止 | 无天然论证 | gas 递减是 latch 的 ranking function;完整终止结论依赖六项前提(§4.4 ②(e)) |
| 语言形态 | src/tgt 同为 LLVM IR,一套编码器用两次 | 跨语言:栈机 ↔ 寄存器机,两套编码器 + 状态映射(即 `R`) |
| 位宽压力 | 常见 ≤ 64 bit | 256 bit(4 limb);已有对策:holiman 分段建模、UF 折叠、div 桥接 |

一句话:**Alive2 展开循环是因为它别无选择;本项目的编译器结构保持,所以有更好的选择**。值得从 Alive2 借鉴的是两点工程纪律:诚实报告(timeout/不完整必须显式暴露)和精化查询的组织方式。

## 3. 循环分类与前提实证

### 3.1 Tier 1 / Tier 2 二分

验证目标(go-hpc-evm 逐指令模板直译,无循环重构/展开/向量化)决定了循环宇宙可精确二分:

| | Tier 1:EVM 源级循环 | Tier 2:x86-only 内生循环 |
|---|---|---|
| 来源 | 合约源码(Solidity/Yul)编译产物 | codegen 模板(`impl_amd64.go`) |
| 两侧形态 | 都有循环,JUMPI 回边 ↔ Jcc 回边 1:1 | 仅 x86 有循环;EVM 语义是一步闭式 Array 操作 |
| 归纳命题 | 关系式:"两侧保持同步" | 单侧:"循环净效果 = EVM 闭式结果" |
| 不变式来源 | 通用模板(现有耦合关系)为主 | 少量手写模板,一次性、全合约复用 |
| 实例 | string 拷贝、数组遍历 | CALLDATACOPY/CODECOPY/RETURNDATACOPY/MCOPY 的拷贝循环 |
| 证书形态 | 关系式,必须由关系式主验证器在 paired cutpoint 消费 | 精确闭式状态变换,可用单侧 x86 summary runtime |

不存在第三类(EVM 有环而 x86 展开):该编译器不做 unrolling。

判别依据是 x86 循环头是否带 **TAG 序言**(`makeStaticUseGas` 的 gas 检查开头:`mov rax,[r13+0x70]` → `cmp rax, IMM` → `jb`,中间可能有 nop 对齐)。带序言的是 EVM 块边界即 Tier 1 候选,不带的是 codegen 内生循环即 Tier 2 候选(`x86_64/loop_analysis.is_evm_tag_header`)。

### 3.2 Tier 2 循环清单

按 `$GOPATH/src/github.com/bcds/go-hpc-evm/evm/aot/impl_amd64.go` 回边统计,共 **7 条**:

```text
compileMakeDataCopy         1 条 (服务 CALLDATACOPY/CODECOPY)
compileEVMRETURNDATACOPY    1 条
compileEVMMCOPYFromLow      2 条 (字循环 + 尾循环)
compileEVMMCOPYFromHigh     3 条 (反向字循环 + SHRStart 对齐移位循环 + 尾循环)
```

其中 `compileEVMMCOPYFromHigh` 的 `SHRStart` 不是 memcpy 形状,而是把已读入 `tmp` 的 qword 右移到尾部起点的寄存器循环;引理必须单独覆盖这一段,不能被 §5.1 的纯内存模板吞掉。

清单封闭性**不靠人工清点**,由 §6 的结构守卫强制。

### 3.3 前提实证

> 下列数据在当前 develop 上实测取得,复现命令见 §8 脚注。**术语是中性的**:统计只支持 "context-insensitive natural-loop 候选" 这一层结论;"疑似真实循环"与"疑似 call/return 伪环"是按**形态**(latch 数、body 规模)作出的推断,不是已证的语义分类。除非另有 call/return 语义识别证据,本文不使用"真回边""伪环"这类断言式命名。

**跳转全部静态化,无 dispatcher。** IR 生成期 `resolveSymbolicJumps`(`evm_ir.go`)把跳转目标解析为静态形式。两个 fixture 的 JUMP/JUMPI 形态统计**存在两个口径**,引用时必须说明用的是哪个:

| fixture | blocks | raw 口径(含终止指令后的死代码尾跳) | 活控制流口径(守卫实际使用) |
|---|---|---|---|
| CErc20.json | 723 | static 640 / multi 83 / **dynamic 0** | static 542 / multi 83 / **dynamic 0** |
| Safe.json | 742 | static 659 / multi 83 / **dynamic 0** | static 557 / multi 83 / **dynamic 0** |

raw 口径由 `classify_raw_jump_ops` 统计**所有** JUMP/JUMPI 操作;活口径由 `build_evm_cfg` 只计入每块第一个控制流操作(其后视为死代码)。守卫用活口径,两者的差就是终止指令后的 IR 导出尾部 JUMP。

codegen 三种形态(`impl_amd64.go` compileEVMJUMP/JUMPI):静态单目标 → **直接 JMP/JNE**;多目标(resolved_multi,主要是函数返回跳)→ **CMPQ+JEQ 比较链**(边仍显式);完全未解析 → 进中央 jumpCode dispatcher。**第三种在两个 fixture 中出现 0 次**;若出现,§6 守卫直接 fail。

**natural-loop 候选的实测分布。**

| fixture | EVM 候选 / 回边 | x86 候选(Tier 1 / Tier 2) | 配对结果 |
|---|---|---|---|
| CErc20 | 9 / 18 | 48(9 / 39) | 9 pairs,unpaired_evm 0 |
| Safe | 4 / 4 | 38(4 / 34) | 4 pairs,unpaired_evm 0 |

CErc20 的 9 个候选形态(`header / latch 数 / body 块数`):

```text
按形态疑似真实循环:  0x739 /1/1    0xb39 /1/1    0x36aa/1/2    0x3731/1/2
按形态疑似 call/return: 0x7c7 /1/21   0x32b7/6/8    0x333e/2/9
                        0x35e7/1/5    0x3643/4/17
```

Safe 的 4 个候选全部单 latch、body ≤ 2,未出现疑似 call/return 形态。**是否出现取决于合约,不是普遍规律。**

由此得到三条对设计的约束:

1. **"目标地址在前"不是循环。** 按块序统计 CErc20 的"往回跳"有 256 个,而 context-insensitive 支配分析只给出 9 个候选。朴素的地址序判定会把大量函数调用误当循环。
2. **上下文不敏感的支配分析也不足以区分循环与函数调用。** 多 latch(6 条、4 条)或大 body(21、17 块)的候选,形态上更像多个 caller 的返回边汇聚。当前守卫**不做**这种排除,9 个候选全部进入 Tier 1 配对(见 §6 对其定位的说明)。
3. **收益边界。** 主导成本来自内部函数调用链而非回边——这是 §0.5 那条结论的数据来源。

**循环头局部栈深静态可知,但不能只覆盖局部窗口。** IR block 携带 StackDepth/MinDepth/MaxDepth;注意其为**相对当前 stackBasePoint 的深度**(codegen 在 JUMP/JUMPI 处以 `StackDepth*stackBytesSize` 动态调整栈基)。Solidity 内部函数中的循环还会在退出后读到 caller-frame 中的返回地址和局部变量,这些槽不在当前 stackBasePoint 之上。若 `R` 只钉住局部窗口,归纳步 havoc 后会把 caller-frame havoc 成互不相等,③ 出口继续执行到函数返回时必然伪 SAT → 降级。因此 `R` 必须覆盖后续可能被读到的 live 栈前缀(§4.5)。

**执行器可从任意 cutpoint 启动。** x86 侧已有先例(单指令等价性检查从截断 core 执行);EVM 侧 `SymbolicExecutor` 接受 blocks 列表与 `stop_pcs`,从任意块构造初始 GlobalState 已实现。

## 4. Tier 1:锁步关系式归纳

### 4.1 总述:命题、归纳拆解与实现骨架

#### 要证的命题

设配对的循环头是 `(h_evm, h_x86)`。要证的是一个**无界命题**:

> 对任意轮数 n:若第 n 次到达循环头时 `R(s_evm, s_x86)` 成立,则第 n+1 次到达时 `R` 仍成立;且两侧永远同时决定继续或退出;且轮数有限。

#### 归纳拆解

把循环头设为 cutpoint,切开后所有段无环,无界命题化为三条**有界、Z3 直接可解**的查询:

```text
        真实入口                     ① Base:入口 ⇒ 到达 h 时 R 成立
           │
           ↓
    ┌──► [ h ] ──────┐               ② 归纳步:h(havoc)⇒ 一轮后
    │      │         │                   ├ 回边:R 保持
    │      │         │                   ├ 出口:R 保持
    └──────┘         │                   ├ 体内终止:observable 等价
      回边           ↓                   └ 每条 latch:gas 严格递减
                  出口 ──► …          ③ 出口:出口处 R ⇒ 后缀 observable 等价
```

#### 统一的实现骨架

三条查询**不是三套独立机制**,而是同一个两阶段流程的三组参数。这是本章最重要的结构性事实——三套独立实现必然漂移,而 fail-closed 语义只要有一处没守住就是缺口:

```text
阶段 A  段执行      从段起点符号执行,在 stop 集合处截断
                    产出:路径列表,每条带 path condition + 截断态,
                          并标记 latch / exit / terminal
                    ↓
阶段 B  路径矩阵验证 对 (EVM 路径 × x86 路径) 的每一对,先判"该不该共现":
                    不该共现 ⇒ 证明它们互斥(决策对齐)
                    该共现   ⇒ 证明该对上的义务成立
                    产出:proved 或 inconclusive —— 绝不产出反例
```

三条查询的差别只在五个参数:

| | 段起点 | stop 集合 | 兼容规则(该共现) | 证明义务 | 对齐标签 |
|---|---|---|---|---|---|
| **① Base** | 真实入口(非 havoc) | `{h}` | 两侧都到达 `h` | 到达状态满足 `R` + 域约束 | `①-align` |
| **② 归纳步** | `h`(havoc 态) | `{h} ∪ exits` | `latch↔latch`、`terminal↔terminal`、`exit↔exit` 且出口配对匹配 | latch/exit:`R` 保持 + 域约束闭合 + 不变式重建;terminal:终止 observable 等价 | `②(a)` |
| **③ 出口** | 某个 exit(havoc 态) | `{h, exit}` | `terminal↔terminal`;非终止按位置配对 | terminal:observable 等价;再入:`R` 保持 | `③-align` |

#### 模块职责

| 层 | 落点 | 职责 |
|---|---|---|
| 段执行 | `run_evm_segment` / `run_x86_segment` | 从起点跑到 stop,产路径列表 + coverage 证书 |
| 路径矩阵 | `Tier1LoopInduction._verify_path_matrix` | 五阶段验证,**三条查询共用这一个函数** |
| 三条查询 | `check_base_query` / `check_inductive_step` / `check_exit_query` | 提供上表五列参数 |
| 关系 `R` | `CutpointRelationSchema` | havoc 绑定与证明义务**成对**生成,分量集合强制一致 |
| 结构预检 | `SegmentStructuralValidator` | 段内静态可达块的语义前提校验 |
| 编排与缓存 | `prove_loop_certificate` | ① → 逐深度类 { ② → ③ } → 证书;theorem/application 两级缓存 |

#### 本章结论强度

三条查询全部通过只给出"两侧锁步同步"。终止性另需 ②(e) 的六项前提(§4.4);整体健全性还依赖 §7.1 列出的两项尚未成立的性质。**同步已证 ≠ 终止已证**,两者在结果对象里也分开报告。

### 4.2 段执行:从 cutpoint 出发的有界执行

#### 契约

输入 `(blocks, 起始状态, 段起点, stop 集合, max_depth)`,输出 `(路径列表, coverage 缺陷, 段说明)`。执行器在 stop 集合处截断:到达 stop 的**非入口**状态不再展开,收进截断态集合。判别用的是"状态对象不是入口状态",不能用 `depth > 0`——fallthrough 后继不增 depth,直落进 cutpoint 的状态会带着 `depth=0` 漏过截断、穿透 cutpoint 继续执行。

#### 路径三分类

```text
latch    截断于段起点自身(回边回到 h)         kind = "latch"
exit     截断于 stop 集合的其它成员             kind = "exit"
terminal 自然终止(STOP/RETURN/REVERT/错误终态) kind = "terminal"
```

每条路径携带 `condition`(path condition 合取)与 `state`(截断/终止时的 `SMTState`)。`latch` 与 `exit` 的区分就是 `截断地址 == 段起点`。

#### TAG 错误终止路径照常进入路径列表

OOG / 栈下溢 / 栈超限 / gas uint overflow 在 x86 侧表现为"写状态码到 `[r13+0xe0]` 后 ret"的 stub。envelope 取消前它们被整段丢弃;现在照常收进 `terminal` 类,由 ②(d) 与 EVM 侧对应终态**配对证明**,只额外记一条 note 标注该路径的性质供报告使用。

#### coverage 缺陷的处理是分场景的

| 场景 | EVM 侧 | x86 侧 |
|---|---|---|
| ② 归纳步 / ③ 出口 | 缺陷 ⇒ inconclusive | 缺陷 ⇒ inconclusive |
| ① Base | **必须完整** | **可容忍深度剪枝**(降级为 note) |

Base 的非对称是有意设计,理由必须写清楚,否则后人会"顺手对齐"成两侧都严格、白白拒掉可证的循环:

- **EVM 侧**漏掉一条会到达循环头的路径 ⇒ 该次首次到达的 `R` 义务凭空消失 ⇒ 组合不健全,必须严格;
- **x86 侧**被剪的路径若本会到达,它的输入不被 `Or(x86 到达条件)` 覆盖,于是"EVM 到达 ⇒ x86 到达"的对齐义务**必然失败**(fail-closed);被剪的非到达路径(合约其它函数区域、Tier-2 拷贝循环)与 Base 无关。

#### 段内静态预检

归纳步从 havoc 状态出发,段内某些指令的语义前提与全程序模式不同。按**"段入口到任一 stop 的静态可达块"**扫描——不是只扫循环体,那会漏掉经未登记边到达、但仍在本次段执行范围内的块。拒绝三类:

| 拒绝对象 | 理由 | 放宽条件 |
|---|---|---|
| 段内可达 `GAS` opcode | 读的是 cutpoint 上的符号 gas | 需先确认 `compileEVMGAS` 的 `Blk.StaticGas - Immediate` 在符号 gas 下与 EVM 侧逐字对齐 |
| `MSize` 未进 `R` 时的 `MSIZE` | 两侧 MSize 互不相关 ⇒ 伪 SAT | `R` 含 `memory_size` 分量时放行(当前已放行) |
| x86 "真实 gas 值物化"块 | 读 `[r13+0x70]` **且**写栈**且**不写回 gas ⇒ 是 GAS 的 codegen,与普通 TAG 静态检查(读完就比较、不写栈)不同 | — |

外加两条结构预检:两侧出口数必须相等;EVM 循环头块必须存在。任一不过 ⇒ inconclusive,不进入求解。

### 4.3 路径矩阵验证:三条查询共用的算法

五个阶段。任何一步失败都产出 inconclusive,**没有一处产出反例**:

```text
输入:evm_paths, x86_paths, assumptions, compatible_fn, goals_fn, alignment_tag
base := And(assumptions)

阶段 1  可行性预过滤
        对每条路径查 SAT(base ∧ path.condition)
        UNSAT   ⇒ 已证不可达,剪掉(等价于 reachability 剪枝)
        unknown ⇒ 保守保留(可能可行)
        任一侧被剪空 ⇒ inconclusive

阶段 2  逐对遍历 (ep, xp)
        compatible_fn(ep, xp) 为假 ⇒ 阶段 3;为真 ⇒ 阶段 4

阶段 3  决策对齐(不该共现的对必须互斥)
        证明 base ∧ ep.cond ∧ xp.cond 为 UNSAT
        证不出 ⇒ inconclusive:"branch decisions may diverge"

阶段 4  joint-sat(该共现的对是否真的共现)
        查 SAT(base ∧ ep.cond ∧ xp.cond)
        UNSAT   ⇒ 该对不可共现(vacuous),跳过、不计 partner
        SAT     ⇒ 双方 partner 计数 +1
        unknown ⇒ 保守履行义务,但不计 partner

阶段 5  证明义务
        goals_fn(ep, xp) 产出的条件在该对上成立
        证不出 ⇒ inconclusive(SAT 与 unknown 同等对待)

出口守卫  空洞守卫
        预过滤保留下来的路径中,任一条 partner 计数为 0 ⇒ inconclusive
```

**为什么必须有空洞守卫。** 阶段 4 的 UNSAT 跳过本身是必要的——不可共现的对没有义务可证。但如果某条路径与**所有**对侧路径都不可共现,那它一条义务都没证过,而阶段 1 已经确认它自身可行。这种"看起来全过、实则什么都没验"的空洞必须显式拒绝。unknown 同样设防。

**查询极性不是一刀切的 UNSAT。** 阶段 3、5 要 UNSAT(不存在反例);阶段 1、4 是**可行性查询**,要的是 SAT 或 unknown 这种"可能可行"的答案。把两类混写成"所有查询必须 UNSAT",按字面实现会拒绝所有存在真实可行路径的循环。正确表述:证明失败公式、决策失配公式与 coverage-gap 公式均为 UNSAT;可行性查询获得其预期结果;任何关键查询不得 unknown 或超时。

**`inconclusive` 的全部触发点。** 统一在此列出,新增触发点时对照补齐:

| 触发点 | 位置 |
|---|---|
| 段 coverage 缺陷(②③ 两侧、① 的 EVM 侧) | 段执行 |
| 一侧无路径 / 全被预过滤剪空 | 阶段 1 |
| 决策可能分叉 | 阶段 3 |
| `R` 或 observable 不保持 | 阶段 5 |
| 空洞(无可共现伙伴) | 出口守卫 |
| 段内可达 `GAS` / 未支持的 `MSIZE` / gas 物化块 | 段内预检 |
| 出口数不等、循环头块缺失 | 结构预检 |
| 深度类超出 schema 建模范围 | havoc 构造 |
| 到达时栈深是符号量 | Base 深度类提取 |
| 出口数过滤错误 stub 后不等 | ③ 的逐出口编排 |
| Base 通过但深度类为空 | 证书组装(vacuity) |

**归纳步 SAT ≠ 找到 bug。** `R` 太弱时阶段 5 给出的是伪反例。可信反例只能来自降级后的有界模式(§6)。

### 4.4 三条查询的具体构造

#### ① Base

```text
1. 起始状态是真实初始状态(非 havoc):两侧共享同一 SMTState 的符号
   calldata/storage,栈从空开始。到达时的窗口内容由两侧各自执行建立,
   R 因此是真正的证明义务,而不是 by construction 的耦合。
2. 两侧从各自入口执行,stop = {循环头}。
   x86 侧默认开 reachability check —— Base 跑的是真实入口的整程序前缀,
   selector 分派等具体死分支不剪会路径爆炸。
3. coverage 门:EVM 严格 / x86 容忍(§4.2)。
4. 取到达路径:kind != terminal ∧ location == 循环头。
   EVM 侧无到达 ⇒ inconclusive(该入口条件下循环头不可达)。
5. 深度类提取:对每条到达路径求 simplify(SP).as_long();
   取不出具体值(符号栈深)⇒ inconclusive。
6. 到达对齐:逐条证 ep.cond ⇒ Or(x86 到达条件),再逐条证反向。
   用逐条蕴含而非整体等价,失败时能定位到具体是哪条路径。
7. 路径矩阵验证,义务 = R 在到达状态成立 + 域约束成立。
```

产出 `depth_classes`,供 ②③ 按类实例化。**Base 通过但深度类为空必须拒绝**——那意味着循环头从此入口不可达,此时报成功是 vacuous。

#### ② 归纳步

```text
1. 段内静态预检(§4.2),不过 ⇒ inconclusive。
2. build_cut_state() 造 havoc 状态(§4.5.2),两侧各取一份 copy。
3. 两侧从循环头执行一轮,stop = {循环头} ∪ 出口集合。
4. 段 coverage 有缺陷 ⇒ inconclusive(归纳前提不成立)。
5. 前提 = havoc 注入的域约束 + 不变式前提。
6. 兼容规则:latch↔latch、terminal↔terminal、
   exit↔exit 且 exit_pairing[ep.location] == xp.location。
7. 义务按路径类型分派:
     terminal ⇒ ②(d) 终止 observable 等价
     latch    ⇒ ②(b) R 保持 + 域约束闭合 + 不变式重建
     exit     ⇒ ②(c) 同上
8. 路径矩阵验证,其阶段 3 即 ②(a) 决策一致。
9. ②(e):在同一批 latch 路径上收集终止证据。
10. 深度转移封闭:每条 latch 回到循环头时 SP 仍等于本深度类。
```

**②(a) 只覆盖 EVM 级分支。** 回边与出口边的决策必须逐对一致;x86 模板内部的实现分支(holiman 分段、溢出检查)属于 plus-simulation 的段内分支,由有界枚举吞掉,不构成决策失配。

**出口配对是顺序的。** `exit_pairing = dict(zip(evm_exits, x86_exits))` ——与 §6 的循环配对同源,同属"配不上不猜、但配错也不报警"的形态,其 fail-safe 性质同样依赖消费端按精确程序点验证(§7.1)。

**域约束必须在回边/出口处闭合:域内进、域内出。** havoc 注入了 `MSize ≤ 4 MiB` 与 32 字节对齐,定理只在该域内成立。若一轮循环体扩容后跨出域外,下一轮就在域外复用了只在域内成立的定理;③ 也只从域内的 havoc 状态验证了一个并不覆盖实际出口的后缀 —— 假绿。所以把域约束做成归纳的一部分,加进 ②(b)/(c) 的证明义务。**两侧都要证**:`R` 的 `memory_size` 分量保证两侧 MSize 相等,但那是 `R` 的**结论**不是前提,不能靠它省掉一侧。

**不变式的前提与义务必须成对出现。** 只当前提是白嫖(定理凭空变强),只当义务是无谓降级。cutpoint 处作为归纳前提注入,latch/exit/再入处作为义务重新证明。

##### ②(d):终止 observable 与错误终态的归类

终止 observable 为:return metadata、return memory(用整 memory 的 R15 平移相等表达,强于逐字节区间比较)、storage、transient storage、**status code**,以及 `FIXED_BUDGET`/`FULL` 档下的 **gas**。

**OOG / 栈下溢 / 栈超限 / gas uint overflow 是 terminal outcome,不是循环出口。** 它们既不回到循环头也不走正常出口,因此归入 ②(d),**不能**与普通出口边一起按地址配对。早期方案把 x86 的 TAG 错误 stub 从可配对出口里剔除,那是 EVM 侧没有对照物时的权宜;现在 `evm_ir/cfg_executor.py` 的 TAG 守卫已忠实镜像三分支、`evm_ir/status_code.py` 有完整错误码(`OUT_OF_GAS=12`、`GAS_UINT_OVERFLOW=13`、`STACK_UNDERFLOW=14`、`STACK_REACHED_LIMIT=15`),这些路径应当配对证明。

**status 只能作候选分桶键,不能替代 observable 检查。** 按 status 分桶后,每个桶内仍须证明:两侧路径条件双向覆盖、status 相同、storage / transient / return data 一致,以及启用 gas 比较时的 gas 一致。既有范式就是这样——`verification/equivalence_paths.py` 的 `_check_path_pair_status_and_state_observables_with_solver` 先证 status,**再**继续证其余 observable,从不用 status 顶替。

##### ②(e):终止义务的实现与条件化

实现是一组反例查询:对每条 latch 路径,证明

```text
UNSAT( assumptions ∧ path.condition ∧ ¬ ULT(gas_out, gas_in) )
```

`gas_in` 取 cutpoint 上 havoc 出来的符号 gas(**不是具体值**),`gas_out` 取该 latch 路径末态的 gas。全部 latch arm 都严格递减,才算这一条成立。

**但单轮递减不足以推出有限退出。** 完整结论是条件定理,依赖六项前提;实现把"本处已证的"与"依赖别处兑现的"分开记录,后者带 `discharged` 标志:

| 外部前提 | 由谁兑现 | 本处状态 |
|---|---|---|
| `segment_coverage_completeness` | `run_evm_segment` / `run_x86_segment` 的 coverage 证书 | 段无缺陷时兑现 |
| `no_unidentified_inner_loop` | §6 结构守卫(段内每条 x86 回边要么 Tier-1 配对、要么命中已证 Tier-2 引理) | **未兑现**——本查询看不到全局守卫结论 |
| `all_sccs_cut_or_certified` | 外层 cutpoint 证明图 | **未兑现** |
| `no_infinite_x86_stuttering` | x86 段执行器深度有界且 coverage 缺陷 fail-closed,非终止 stutter 会表现为证书不完整 | 段无缺陷时兑现 |
| `sat_unknown_coverage_fail_closed` | `_verify_path_matrix` 把 SAT/unknown/coverage gap 一律转 inconclusive | 恒兑现 |

第六项"无位向量回绕"是**结构性论证而非 SMT 查询**,如实标注来源:TAG 守卫在减法**之前**按 `ULT(gas, static_gas)` 分叉,而 `consume_static` 是纯减法、不钳零,故不会下溢回绕(`docs/Gas一致性验证设计.md` §5)。

**未兑现的前提不能算数。** `discharged` 默认 False,证书的 `proved` 强制检查。把这些前提写成一串说明性字符串、再让 `proved` 忽略它们,等于把六项中的四项悄悄降格成注释——终止结论会在前提未落实时照样签发。

##### 深度类转移封闭的实现

归纳步是按单个深度类实例化的,因此"转移封闭"就是:每条 latch 回到循环头时 SP 仍等于该深度类的值。落在集合外的深度记入 `escaping_depths`——那意味着存在**未登记**的深度类、枚举不完整,调用方必须降级或补证该类,不得当作已覆盖。

#### ③ 出口

```text
1. 按深度类造 havoc 状态,栈基字节偏移取具体的 k*0x20。
2. 从出口点执行,stop = {循环头, 出口点} —— 既拦再入(回到循环头),
   也拦回到该出口 cutpoint。
3. 前提中复用 ②(c) 已在出口处建立的不变式。
4. 兼容规则:terminal↔terminal;非终止按位置配对(头↔头、出口↔出口)。
5. 义务:terminal ⇒ observable 等价;再入 ⇒ R 保持。
6. EVM 侧遇到不支持的跳转 ⇒ inconclusive(而不是异常退出)。
```

**为什么第 3 步不能省。** ②(c) 已经证明了出口处不变式成立,③ 不把它作为前提就等于丢掉一段已证信息——不是不健全,但会让本可证明的循环无谓 inconclusive。

**havoc 覆盖整栈而不只是循环窗口。** caller-frame 的返回地址等被 havoc 成两侧共享符号;EVM 侧 `resolved_multi` 返回跳靠执行器的 `immediate_set` 分叉(每叉带 `value == target` 约束),与 x86 的 `CMPQ+JEQ` 比较链自然对齐。

**③ 必须逐出口跑。** ② 虽证明了每个出口处 `R` 保持,但出口**之后**的 suffix 彼此不同;只验第一个出口,其余出口后的 status / storage / 返回值差异会被整条漏掉。出口数在两侧过滤错误 stub 后不相等时,**不得 zip 截断**——那会静默丢掉多出来的出口却仍签发证书。任一出口失败 ⇒ 整体 inconclusive,不是"其它出口还好"。

#### 归纳论证

第 0 次到达循环头 `R` 成立(①);第 n 次成立则第 n+1 次成立(②b),且两侧永远同时决定继续/退出(②a)——任意轮数下同步,退出后同步到底(②c + ③);②(e) 在六项前提下给出有限轮次。**符号 bound 被归纳直接吞掉。** ②(d) 是必需分支:体内终止路径不经过回边/出口,漏掉即健全性缺口。

### 4.5 耦合关系 R

#### 4.5.1 分量表

`R` 是"两侧状态同步"的谓词,骨架来自现有等价性检查的状态映射,但不能只照搬最终态 observable checker——循环 cutpoint 位于程序中间,尤其可能位于 Solidity 内部函数内部,所以 `R` 必须覆盖后续会被读到的 caller-frame 栈槽。

分量由 `CutpointRelationSchema._COMPONENTS` **单点定义**:`build_havoc` 必须绑定其中每一项,`component_goals` 必须为每一项产出义务,`_assert_component_symmetry` 在每次求义务时校验两者一致——**分散手工拼合取正是历史上三处遗漏的成因**。加分量只能改 `_COMPONENTS`,不能在别处手工补 havoc。

| # | 分量 | 内容 | 漏掉的后果 |
|---|---|---|---|
| 1 | `stack_geometry` | 逻辑 sp / stack byte offset / R14 与 stack base 的平移关系 / R15 = memory base | 栈窗口错位,后续所有栈比较失效 |
| 2 | `live_stack_prefix` | 对后续可能读取的每个 EVM 栈槽 i,`Stack[i]` = x86 STACK 域对应 4-limb Uint256 | 出口后读 caller-frame ⇒ 系统性伪 SAT → 降级 |
| 3 | `memory` | 对每个 EVM offset a,`Memory[a]` = `evm_mem[R15 + a]` | 内存内容脱钩 |
| 4 | `memory_size` | EVM `MSize` = `callengine_memory_size_bytes`(`[R13+0x18]`) | `MSIZE` 读出不相关值;段预检据此拒绝 MSIZE |
| 5 | `memory_gas` | 两侧 `lastGasCost` 相等 **且** 各自 = `memoryGasCost(MSize)` | 下一次内存扩展扣费不同 ⇒ gas 保持失败(§4.5.3) |
| 6 | `gas` | EVM `Gas` = `callengine_gas_remaining` | 两侧 OOG 分叉无法对齐,归纳不闭合(§4.5.4) |
| 7 | `host_gas_seq` | 每个 `HOST_GAS_SEQ_KINDS` opcode 的调用序号相等 | **假绿**:定理钉死在第 0 次调用(§4.5.3) |
| 8 | `return_data_source` | 内容 Array + pointer + size 三者相等 | **假绿**:被当只读环境后跨轮演化脱管(§4.5.3) |
| 9 | `storage` | Storage Array 相等 | 状态脱钩 |
| 10 | `transient_storage` | TransientStorage Array 相等 | 同上 |
| 11 | `return_metadata` | return offset / length 相等 | 终止比较失去锚点 |
| 12 | `environment` | 真正只读的语义环境(**刻意剔除 `return_data`**) | — |
| 13 | `callengine_environment` | callEngine 只读字段,外加跨视图链接(`callengine_input_size_bytes = calldatasize`、`callengine_callvalue = Extract(63,0,callvalue)` 及高 192 位为 0) | 只做同名字段相等会允许两个 side channel 一起漂移 |

栈地址采用当前 R14 block stack base 与 Go stack pointer 的 limb 映射:逻辑栈顶在 `R14 + (sp_limb - 4) * 8`,次栈顶在 `R14 + (sp_limb - 8) * 8`,依此类推;**不得写成简单的同向正偏移公式**。循环头静态深度 `k` 只用于界定循环体局部读写范围,**不是** `R` 的覆盖范围;第一版保守取从栈底到当前 SP 的 live prefix。

> **分量名齐全 ≠ `R` 闭合。** `_assert_component_symmetry` 比较的是**分量名称集合**,发现不了分量**内部**漏约束。§4.5.5 给出一类已实测确认的内部缺口。

#### 4.5.2 havoc 的构造与定理适用域

归纳步必须**主动 havoc 一切 `R` 未钉住的状态**:x86 scratch 寄存器、CPU flags、两侧路径条件。禁止复用从入口符号执行携带路径条件的状态——那会把归纳静默退化成有界证明。

构造从 `create_initial_state(num_inputs=0)` 起,逐分量绑定。每个 callEngine 字段都必须**同时**写属性与 `[R13+offset]` limb(x86 侧读该字段走 side-channel 快路径直接取属性,limb 是宽度不符时回退内存读用的镜像;两者分叉即陈旧值假绿):

| 分量 | havoc 构造 |
|---|---|
| `stack_geometry` | 字节偏移取**具体值** `k*0x20`(绝对深度类);超出 `max_stack_byte_offset` ⇒ 抛建模范围错误,由调用方降级而非放宽。R14 = stack base + 偏移,R15 = memory base |
| `live_stack_prefix` | push `k` 个符号 Uint256,并映射进 x86 STACK 域同一批值 |
| `memory` | 一个快照 Array `mem₀`;EVM 侧直接用它,x86 侧用 `Lambda(a, mem₀[a - R15])` 平移视图 |
| `memory_size` | 自由符号 + **两条域约束**:`≤ 4 MiB`、32 字节对齐 |
| `memory_gas` | **不独立 havoc**,派生为 `memoryGasCost(mem_size)`(见 §4.5.3) |
| `gas` | 两侧共享同一新鲜符号 |
| `host_gas_seq` | 每个 opcode 一个**任意符号**(§4.5.3:绝不是 0) |
| `return_data_source` | 内容 Array、size、pointer 全部符号化(size 绝不沿用初始的具体 0) |
| `storage` / `transient_storage` / `return_metadata` / `environment` / `callengine_environment` | 由初始状态的共享 Array/字段天然耦合,无需重写;但**仍要登记为已绑定**,否则对称性断言会把它们当遗漏 |

配置开关(`host_gas_uf_enabled`、`abstract_calldataload_words`、`assume_calldata_offset_no_overflow`)必须与调用方的档位一致并透传:归纳步若回到默认值,定理就会在**另一套语义**下证出,再被应用到 Base 的语义上——假绿。它们同样进定理缓存键。

**havoc 的错误方向是安全的,但只对自由符号成立。** havoc 过头只产生伪 SAT(降级),准则是"宁滥 havoc,勿漏 havoc;但先把 `R` 写够强"。**例外**:把一个跨轮次演化的状态量 havoc 成**具体常量**不是过近似而是欠近似,会把定理钉死在初始轮,属假绿方向。三个已知易错点:`host_gas_seq` 缺键默认 0、`return_data_size_bytes=0` 初值、memory size / `lastGasCost` 沿用初值。

**域约束是定理的适用域,不是免费简化。** `MSize ≤ 4 MiB` 与 32 字节对齐界定了定理成立的范围,因此:

- Base 与每次 certificate application 必须在**实际到达状态**上证明它们;
- ②(b)/(c) 必须在回边/出口处证明它们仍成立(域内进、域内出,§4.4 ②)。

**共享符号的适用边界。** 在**通用 theorem**(havoc 后的 caller-independent 命题)中,用一个新鲜符号同时赋给两侧、令 `gas_evm = gas_x86` by construction 是合法的——那正是"假设 `R` 成立"的编码方式。但 **Base 与每一次 certificate application 必须对实际到达状态重新证明该等式**,不得继续 by construction;否则证书会把待证义务偷换成前提,x86 侧静态 gas 常量编错这类 codegen bug 就会逃过检查。

判据适用于 `R` 的**每一个**合取:**凡是 by construction 耦合的量,都必须在 `R` 里有一条对应的证明义务**;只耦合不列义务,等于把它移出了验证范围。§4.5.5 的镜像缺口正是这条判据下的漏网之鱼。

#### 4.5.3 三处易漏分量的假绿机理

`host_gas_seq`、`memory_gas`、`return_data_source` 是同一类错误:**跨轮次演化的状态量被误当成只读环境**。三者都必须四处齐全——进 `R`、进 havoc、进 Base/application/latch/exit 的证明义务、进证书指纹;**缺一处,该量就悄悄退出了验证范围**。

**(a) host-gas 调用序号:havoc 不能重置为 0。**

`HOST_GAS_SEQ_KINDS` 里的指令(SLOAD/SSTORE/BALANCE/EXTCODE*/CALL 四件套/CREATE 系)把**调用序号**作为 UF 的末位实参(`state/host_gas.host_gas_uf`),序号取自 `SMTState.host_gas_seq` 并由 `next_host_gas_seq` 递增,随 `state.copy()` 分叉、在合流点按 If-chain 合并。它是**跨轮次演化的状态量**,不是常量。

这处错误会**假绿**而不是降级:

> 若 cutpoint 把两侧计数器都置 0(或暗中赋成同一个值),而 certificate application 不证明实际计数器相等,则归纳步证明的只是"从第 0 次 host 调用开始的一轮"。第 n 轮到达时真实序号是 n,`host_gas_sload(key, 0)` 与 `host_gas_sload(key, n)` 在 Z3 里是不同的值,定理不能合法应用。更糟的是,两侧真实序号若不相等(x86 侧多一次调用),这个差异恰好被"两侧都重置为 0"掩盖,UF 照样相消。

要求:`R` 含逐 opcode 的序号相等;通用 theorem 用任意共享符号;Base、每次 certificate application、latch 与 exit 都证明实际序号关系;该关系进入证书参数与缓存指纹。序号语义随 `HOST_GAS_SEQ_KINDS` 的增删而变,按旧集合证出的证书不能被新集合复用。

**(b) `lastGasCost`:MSize 相等推不出下一轮扣费相等。**

内存扩展费用是 `newTotal − lastGasCost`,不是 `newTotal` 本身(`state/evm_gas_state.memory_expansion_fee`):

```text
expands      = rounded > mem_size_bytes
fee          = If(expands, new_total − last_gas_cost, 0)
new_mem_size = If(expands, rounded, mem_size_bytes)
new_last_gas = If(expands, new_total, last_gas_cost)
```

`MSize`(`[R13+0x18]`)与 `lastGasCost`(`[R13+0x20]`)是**两个独立字段**。两侧 `MSize` 相等而 `lastGasCost` 不等时,下一次内存操作扣的 gas 就不同 ⇒ ②(b) 的 gas 保持失败。

由上面的公式还可见:只要初始满足 `lastGasCost = memoryGasCost(MSize)`,该等式就被两条分支同时保持(扩展支两者同步更新,非扩展支两者都不变),因此它是一条**不变式**。本方案把它一并纳入:`memory_gas` 分量同时要求两侧相等**与**各自等于 `memoryGasCost(MSize)`,havoc 据此派生而非独立自由。仅做两侧相等是健全性的**最低要求**;补上派生不变式才能避免"下一轮扣费任意"的过近似造成无谓降级。

**(c) return data 是可变分量,不能算作只读环境。**

两侧的 `_update_return_data_source`(x86:`x86_64/go_function_semantics.py`;EVM:`evm_ir/semantics._update_call_return_data_source`)在**每次会刷新 returndata 的 host 调用后**重写 `return_data`(Lambda 覆盖前 size 字节)以及 pointer / size。会刷新它的是 **CALL 四件套 + CREATE / CREATE2** 六个 opcode(`compiler.go` 的 host 表里只有这六个标 `returns: true`)。因此循环体内含这些指令时,return data 跨轮次演化——把它和 calldata/code 一起归为"只读环境"是错的。`_READONLY_ENVIRONMENT_FIELDS` 因此**刻意从 `SMTState.ENVIRONMENT_FIELDS` 中剔除 `return_data`**,由独立的 `return_data_source` 分量连同 pointer/size 一起承载。

两个已修的建模缺陷(两侧共同的错误,不是循环归纳引入的,但会被 `R` 放大成假绿):

1. **长度曾被钉成 `retSize`**。`retSize` 是调用方给的**输出缓冲区**长度,而 RETURNDATASIZE 读的是被调用方**实际返回**的长度 `len(res)`;自动拷贝只搬 `min(retSize, len(res))` 字节。两侧一起钉成 `retSize`,真实返回长度就整个落在量化域外,一个混淆这两个量的 codegen 缺陷会被共同错误掩盖。现改用同名 UF(`common/uninterpreted.*_return_size`),取值相同故照常相消,错误实现则因取值不同被抓住。
2. **CREATE / CREATE2 曾完全不刷新 returndata**。真实执行中成功的 CREATE 让 host 返回 nil、engine 把长度刷成 0,revert 时则是 reason data——**保留调用前的旧值是不可能的真实状态**。两侧一起保留会让"错误保留旧 returndata"的编译产物被判等价。现同样用 UF 刷新:不把 size 钉成 0,那样只覆盖成功路径、会把 revert 路径排除在量化域外。

**一个已知边界(降级方向,非假绿)**:两侧 host UF 的内存实参处在**不同坐标系**——EVM 侧传 offset-space 的 `evm_memory.Memory`,x86 侧传 absolute-space 的 `x86_memory.evm_mem`。内存为空时两者都是零数组、平移后相同,UF 照常相消;但内存**已有写入**且 `R15 ≠ 0` 时,它们只满足平移关系,UF 可以取不同值 ⇒ 含 CALL 族的循环会无谓 inconclusive。这是既有模式(`call_semantics` 等全部如此),彻底修法是把两侧统一到 offset-space,涉及所有既有 host UF 的实参,影响面远超本方案。边界已固化在 `tests/unit/test_go_function_semantics.py::test_return_data_uf_needs_matching_memory_coordinate_systems`。

#### 4.5.4 gas 的双重身份

`docs/Gas一致性验证设计.md` §2 明确:gas 是**决定控制流的内部状态**(OOG 阈值),不是只在比较时才需要的 observable。这带来一个必须分清的区分:

| 用途 | 位置 | 适用档位 |
|---|---|---|
| **内部控制流关系** `gas_evm = gas_x86` | cutpoint 上的 `R` 合取 | **三档都要**——没有它,两侧的 OOG 分叉无法对齐,归纳不闭合 |
| **terminal gas 比较** | ②(d) 终止 observable | 仅 `FIXED_BUDGET` / `FULL` |

把两者混同会得到错误结论:在 `OFF` 档下写"比较 gas"与 `GasCheck.OFF` 的定义冲突;反过来,在三档都省掉 cutpoint 上的 gas 关系,则控制流对不齐。

与 `GasCheck` 三档的交互:

| 档位 | cutpoint 上的 gas | terminal gas | 循环语义 |
|---|---|---|---|
| `OFF` | 仍须 havoc 成两侧共享符号 | 不比较 | 应用域含 host-gas 操作 ⇒ inconclusive(§7.3) |
| `FIXED_BUDGET` | 共享符号 | 比较 | gas 进 `R`,OOG 配对证明 |
| `FULL` | 共享符号 | 比较 | 同上,且对所有初始 gas 量化 |

全局无损 assumption(如 CALLDATALOAD hi-192 == 0)允许作为 ② 的前提,但必须是路径无关的全局先验,且与 calldata 语义开关一起进入定理指纹。

#### 4.5.5 表示层闭包:side-channel 属性 ↔ CALLENGINE limb 镜像

`build_havoc` 对每个 callEngine 字段**同时**写属性与 `[R13+off]` limb(§4.5.2),其自带注释已指出:**两者分叉即陈旧值假绿**。

但只同步 havoc 侧是不够的。`component_goals` 的 13 条义务**全部只比较属性**,`_assert_component_symmetry` 又只比对分量名称集合,于是:

- havoc 状态里 属性 == limb(by construction);
- Base / application 对实际到达状态重证 `R` 时只证属性 ⇒ 允许 limb 陈旧;
- 定理在同步状态上证明,却被应用到不同步状态 ⇒ **定理被用到证明域之外**。

实测(单侧篡改 x86 的 limb、属性不动,求 `R` 全合取 ∧ `limb ≠ 属性` 是否可满足):

```text
gas_remaining      R accepts stale limb: sat
return_data_size   R accepts stale limb: sat
memory_size        R accepts stale limb: sat
last_gas_cost      R accepts stale limb: sat
stack_byte_offset  R accepts stale limb: sat
```

**5/5 全部 sat** —— `R` 当前不闭合。

**设计要求:每个经 `_sync_callengine` 维护的字段,其"属性 = 对应 `[R13+off]` limb"必须作为证明义务进入 `R` 与定理适用域**,并与其余分量同样贯穿 havoc / Base / application / latch / exit / 指纹。这条与 §4.5.2 的判据同源。

修复路径(实现状态见 §9):为每个镜像字段补一条 `limb == 属性` 合取(可新增 `callengine_mirror` 分量,或并入各自分量),并加逐字段单侧篡改测试(§8 验收 11)。这会改变 `fingerprint` 使现有证书失效——**那是正确行为**,旧证书本就在不闭合的 `R` 下签发。

#### 4.5.6 两个位置决策

**status:不进 `R`,改作 cutpoint 结构前提。**

status 的主位置是 **terminal relation**(②(d))。把 `error_code = callengine_status_code` 放进中间 cutpoint 的 `R` 是过强约束,除了制造无谓降级没有收益——cutpoint 处两侧都还在 running。

但"都还在 running"这件事本身不能靠 `create_initial_state` 的初值 by construction 成立。设计要求:**"两侧均处于 running(未终止)"作为一条 cutpoint 结构前提**,覆盖**五处**——

```text
① Base 到达循环头时
② 每次 certificate application
③ latch 再应用(回边回到循环头时)
④ 正常 exit 边上
⑤ ③ 出口段进入下一 cutpoint 时
```

并进入**定理适用域**(与域约束同机制)与**缓存指纹**。只写"Base 和 application"不够:status 不进 `R` 之后,剩下的三处仍可能靠初始值偷换。

同类的还有两个**结构前提**(不是状态等式):cutpoint 位于块边界,故 `pending_errors` / `pending_constraints` 应核对为空。

**深度类:绝对栈深有限枚举 + 两条完备性义务。**

live 栈前缀用有限槽位展开实现,隐含前提是同一循环头的绝对栈深可按有限深度类枚举,归纳查询按深度类分别实例化。

仅规定"遇到未登记的新深度类就 fail-closed"**不足以证明枚举完整**——那挡不住"永远遇不到、但确实存在"的 class。完备性必须拆成两条可证义务:

```text
(i) Base 覆盖所有首次到达:任何到达该循环头的路径,其深度类都在已登记集合内
    实现:Base 段的 coverage 证书保证枚举了全部到达路径(§4.4 ①)
(ii) 转移封闭:每个已登记 class 的 latch 与再入,只转移到已登记集合内的 class
    实现:归纳步逐 latch 检查 SP 仍等于本深度类(§4.4 ②)
```

两条都证明后,深度类集合才是该循环头的归纳不变式。无递归/无调用环的 Solidity 产物预期满足;存在导致栈深无界的调用环时,(i) 或 (ii) 会失败 → 降级。**符号深度类不在本方案范围内**(§7.3)。

### 4.6 特殊结构:嵌套、多出口与多 latch

- **嵌套循环**:所有循环头同时设为 cutpoint,cut 后所有段无环,统一走三条查询,无需"由内向外"分层。
- **多出口(break/continue)**:②(a)(c) 按出口边逐对处理,结构不变;③ 逐出口跑。
- **多 latch**:循环头仍是唯一 cutpoint,②(b)(e) 对每条 latch 分别证明;疑似 call/return 形态的多个 caller edge 不应当成多 latch(§6)。
- **不可归约 CFG**(手写内联汇编):配对失败,走 §6 降级。

### 4.7 证书:数据结构、缓存与消费

#### 两层拆分

`Tier1LoopTheorem` 只证明 caller-independent 的命题:`R ⇒ 一轮决策对齐 / 回边保持 / 出口保持 / gas 递减`。`Tier1LoopCertificate` 在其上绑定 caller assumptions、arrival path condition、depth class 与 Base/application 证明。两者分别缓存。

```text
Tier1LoopCertificate ≜
    EVM/x86 循环头与结构指纹
  ∧ 回边/latch 集合与已配对出口集合
  ∧ 适用的绝对栈深 classes,及其"首次到达覆盖 + 转移封闭"两条证明结论(§4.5.6)
  ∧ 耦合关系 R 的版本/参数(含 host-gas 序号、lastGasCost、return data、镜像闭包关系)
  ∧ GasCheck 档位、host-gas scope、调用方前提、已证 gas 下界(若有)
  ∧ Base、每个 depth class 的归纳步、每个出口义务的证明结果
  ∧ 终止证据(§4.4 ②(e) 的五条外部前提 + 递减查询 + 无回绕依据 + 查询极性)
  ∧ host/bridge 配对结果
  ∧ 模板/codegen/profile 指纹(变更后自动失效)
```

其中 Base 与 application 处的各项 equality 都是**重新证明的结论**,不是 by construction 的前提(§4.5.2),且都要在 latch 与 exit 处证明保持。**证书的 `proved` 严于查询的 `proved`**:它强制要求终止证据与深度类完备性齐备,不让"同步已证"冒充"终止已证"。

#### 编排主流程

```text
prove_loop_certificate:
  1. ① Base(深度类未知,stack_depth 只是占位)
        失败 ⇒ 返回;产出空深度类 ⇒ 拒绝(vacuous)
  2. 组装 theorem key:两侧程序指纹 + 循环头 + 出口集合 + R 指纹
        + GasCheck 档位 + calldata 语义开关 + extra_invariant 身份
        + summary_config 指纹 + aot_profile 指纹
  3. for depth in depth_classes:
        theorem = cache.theorem(key(depth)) 或跑 ② 归纳步
            建模范围错误 ⇒ 记 reason 并 continue(降级,不 fail-hard)
            只缓存成立的定理
        certificate = cache.application(app_key) 或跑 ③(逐出口)并组装
            只缓存成立的证书
  4. 汇总:任一深度类失败 ⇒ 整体不 proved
```

#### 缓存键的构成要求

| key | 必含 | 理由 |
|---|---|---|
| theorem key | 两侧程序指纹、循环头、出口集合、深度类、`R` 指纹、GasCheck 档位、host-gas UF 开关、calldata 语义开关、不变式身份、summary/profile 指纹 | 这些都改变**命题内容**;不同档位下 ②/②(d)/③ 证的不是同一件事 |
| application key | theorem key + 规范化 caller assumptions + 入口条件 + **是否要求终止证据** | 同一 cache 先以"不要求"、再以"要求"调用时,key 相同就会取回宽松证书,绕过未兑现的终止前提 |

两条实现纪律:

- **只缓存成立的定理。** `timeout`/`max_depth` 不在 key 里,把 inconclusive 也缓存起来,调用方换更大预算重试时会直接取回旧的失败结果——降级被固化成永久失败。
- **进过缓存键的可调用对象必须被缓存持有。** 对匿名可调用回退到含地址的 repr,对象被 GC 后地址复用会让语义不同的新闭包撞上旧键。

#### 折叠形态与消费接口

```text
Entry
  │
  ├─ 无环前缀 → 非循环 Terminal → 普通 observable 等价性检查
  │
  └─ Base → paired loop cutpoint
                  │
                  └─ Tier1LoopCertificate(任意轮数)
                              │
                              ├─ 配对出口 → 下一 cutpoint
                              └─ 体内终止(含 OOG/栈错误)→ observable 等价性检查
```

主验证器命中已证 cutpoint 时不再进入回边,而是按序执行四步:

```text
1. 核对程序点(EVM pc 与 x86 addr 必须同时匹配证书记录的那一对)
2. 核对栈深 class 与证书指纹
3. 证明当前状态满足 R + 域约束 + 结构前提(running、pending 队列为空)
4. 引用证书,以每个配对出口为后继继续
```

第 1 步是 §6 那条 fail-safe 论证的支点:错配的证书因程序点对不上而永远不会被消费,回边退回展开 → 降级。**该消费端尚未落地**(§9),所以这条性质目前只是预期。

Tier 1 证书是**关系式证书**,不是可分别应用到单侧状态的函数 summary:它证明 `R(s_evm,s_x86)` 对任意轮数保持,并不给出精确的 `s' = F^n(s)`。因此不得让两个单侧 executor 各自无约束地跳到出口;折叠必须由关系式主验证器在 paired cutpoint 上执行。Tier 2 拥有精确闭式状态变换,才可以继续使用单侧 x86 summary runtime。

最终成功条件是所有证明义务的合取,不允许任何证书用一个 `True` 覆盖其它失败:

```text
VERIFIED ⇔
    全部非循环 terminal paths 的 observable 等价成功
  ∧ 全部可达 Tier 1 loops 有有效证书且已在主证明中消费
  ∧ 全部 Tier 2 loops 命中已证闭式 summary
  ∧ 所有 root-to-terminal/cutpoint 边都有 coverage 依据
  ∧ 无 unpaired/unresolved/non-loop coverage gap
```

### 4.8 路径规模控制:OOG 谓词先证后桥接

取消 envelope 的直接代价是路径规模。cutpoint havoc 后 gas 是符号量,每个块入口的 OOG 分支不再被 `simplify` 折死,全部存活。

**上界不构成 havoc 后的剪枝手段。** `state/host_gas.HOST_GAS_UPPER_BOUNDS` 只给**部分 opcode**写出了外部人工审计所得的上界,**CALL 四件套 / CREATE / CREATE2 仍是无上界 UF**(Gas 设计 §7.2)。而且即使有上界,havoc 后手上只有 `gas = 任意符号` 与 `host_cost ≤ B`,这推不出 `gas ≥ host_cost + static_gas`,OOG 分支依然可满足。**上界只在同时存在足够强的 gas 下界时才剪枝**——而具体大预算恰恰是 cutpoint havoc 取消掉的东西。

**本方案采用的机制:先证 OOG 谓词等价,再作分区桥接。**

严禁表述成"两侧共享 OOG 判定"——直接让两侧用同一个 Boolean 就把待证命题假设掉了:x86 静态 gas 常量编错导致 `oog_evm = gas < 10` 而 `oog_x86 = gas < 11`,这类 codegen bug 会被完全掩盖。强制顺序:

```text
1. 分别生成 oog_evm 与 oog_x86(各自侧的真实谓词)
2. 证明 R ∧ path_precondition ⇒ (oog_evm ↔ oog_x86)
3. 仅当该查询 UNSAT,才把等价结论作为桥接,用单个分区变量减少后续枚举
4. SAT / unknown / 超时 ⇒ 一律失败或降级
```

这与 `common/div_bridge.py` 的纪律同构(先证实参恒等,再注入恒真等式),差别只在桥接的是控制流谓词而非数据等式。桥接后按 status 分桶组织枚举,但 status 只是分桶键,每桶内仍须证全部 observable(§4.4 ②(d))。

**两种机制不可混为一谈。** 循环体内的 EVM 复杂指令(DIV/MOD/SDIV/SMOD/SIGNEXTEND/ADDMOD)在 x86 侧是分段实现,归纳步的路径矩阵会变成 EVM 路径数 × x86 路径数的笛卡尔积。项目里有两种看起来相似、实则信任边界完全不同的机制:

| | `common/div_bridge.py` | `x86_64/summaries/mul.py` + `mul_proof.py` |
|---|---|---|
| 作用时机 | 表达式**已生成**、path pair **已选定**之后 | 符号执行期 |
| 做什么 | 配对两侧除法子表达式,先证实参恒等,再注入恒真的结果相等提示 | 严格模板匹配 → 对每个命中 slice 做 glue proof → 应用 summary 替换该段 |
| 对路径数的影响 | **无**——不替换指令段,不减少枚举 | **减少**——整段被闭式状态变换取代 |
| 定位 | 纯求解提速 hint(soundness 中性) | 可信摘要,fail-closed |

因此"减少归纳步路径矩阵"的正确路径是后者。但为 `SIGNEXTEND`/`ADDMOD` 等建 matcher + per-hit proof **不在本方案范围内**(§7.3);它们目前都没有 summary,不能因为与 DIV/MUL 并列讨论就视为已有可复用机制。两条纪律仍适用:单指令等价测试**不能**替代 summary 命中点证明——前者证的是"这段语义正确",后者证的是"这一处确实是那段"。

## 5. Tier 2:单侧归纳(codegen 拷贝循环)

Tier 2 的循环只出现在 x86 侧,EVM 语义是一步闭式 Array 操作,因此不需要关系式归纳,只需证明"循环净效果 = EVM 闭式结果"。整体分三期,三期共用**同一份**闭式语义定义:

```text
引理证明期(一次性,全合约复用)
    对 §3.2 的 7 条回边各证一次 Inv 的 ①②③(§5.1–5.3)
    ↓
发现期(每合约一次)
    在 x86 CFG 上做模板匹配,产出 (入口, 模板名, 参数) 的 summary 列表
    ↓
执行期(每次符号执行)
    命中入口 → 证明前提 → 用闭式状态变换替换整段(§5.4)
```

### 5.1 不变式模板(快照相对形式)

对 memcpy 形状的循环,`Inv` 相对**循环前内存快照 mem₀** 表述,但不能只建纯内存等式。真实模板中还存在索引寄存器、`src/dst/size` 指针寄存器以及 MCOPY 尾部 `tmp` 右移寄存器状态:

```text
Inv(i) ≜  mem = F(i)                          (等式形式,见 5.2)
        ∧ index/size/src/dst/tmp 等活跃寄存器满足模板对应关系
        ∧ 0 ≤ i ≤ len
        ∧ 尚未读取的源区间 = mem₀ 原值
```

注意:**不能写"源数据未被破坏"**——MCOPY 重叠场景下源区间必然被部分覆写。FromLow 的完整分派条件是 `dst ≤ src ∨ size ≤ 8`:前一分支靠升序方向保证尚未读取的源区间完好;后一分支即使 `dst > src`,也会在任何写入前一次性载入唯一 qword,因此反向重叠仍安全。FromHigh 的条件是 `src < dst ∧ size > 8`。已读部分被覆写是合法的;`Inv` 的分区方向随 FromLow/FromHigh 相反。

`compileEVMMCOPYFromHigh` 是三段串联复合引理:反向 8-byte 字循环、`SHRStart` qword 对齐移位循环、尾 byte 循环。`SHRStart` 的不变式核心是 `tmp = tmp0 >> (8*i)` 与剩余移位计数的寄存器关系;它不修改 memory,因此不能套用纯 `mem = F(i)` 模板。

### 5.2 等式编码(规避量词)

"前 i 个字已拷完"不用 `∀j<i` 量词,改用参数化闭式:

```text
F(i) = Lambda(a, If(dst ≤ a < dst + 32*i, 闭式源数据[a - dst + off], mem₀[a]))
```

归纳步变成证 `一轮循环体(F(i)) = F(i+1)`,数组外延等价由 Z3 内部处理,查询保持在 QF-friendly 片段。

### 5.3 三条查询与引理化

```text
① Base   : 循环入口处 Inv(0)(索引清零;F(0) = mem₀ 平凡成立)
② 归纳步 : Inv(i) ∧ i < len ⇒ 一轮后 Inv(i+1)     (i 符号,任意 len 封闭)
③ 出口   : Inv(i) ∧ 退出条件 ⇒ 当前段达到该段目标状态;
           串联所有段的出口状态后,mem = F(len) = EVM 闭式结果
           另单独覆盖 len = 0(循环整体跳过)
```

7 条回边各证一次(参数 len/dst/off 保持符号化)。**注意引理数与回边数不是一一对应**:基础引理可被多条回边复用(如 byte-tail 同时服务 FromLow 与 FromHigh 的尾循环),FromHigh 还需要串联三段的构造级复合证明。守卫要核对的是**回边 → 证明入口的覆盖映射**,不是数量相等。

### 5.4 发现期与执行期:summary 替换

#### 调用链

```text
发现期  discover_copy_loop_summaries(x86 blocks)
          对每个非 TAG-序言的 natural loop 头做模板匹配
          产出 payload:(入口地址, 模板名, src/dst/size 来源, 闭式参数)
          模板名 ∈ {returndata-byte-copy, makedata-byte-copy,
                    mcopy-low-word, mcopy-high-word}
          cluster 型模板(mcopy-*)发现失败 ⇒ 报错而非静默跳过
        ↓
守卫期  make_tier2_matcher(blocks_by_addr)
          §6 守卫用它判断"这条 x86 回边是否命中已证引理";
          未命中的 Tier 2 候选进 unpaired_x86 ⇒ 守卫失败
        ↓
执行期  符号执行到达 summary 入口:
          1. 用当前 path condition 证明该模板的前提
             证不出(SAT/unknown)⇒ SummaryPreconditionError
          2. 应用闭式状态变换,跳过整段循环
          3. 失败策略 fallback ⇒ 回退到逐指令执行原循环
```

`fallback` 是**健全的降级**:逐指令执行原循环的语义与不启用 summary 完全一致,失去的只是折叠收益。

#### 三条纪律

**闭式语义单点定义。** 引理与 runtime summary 必须引用同一份(`x86_64/tier2_semantics.py`)——各写一份迟早漂移,届时 runtime 折叠的行为与引理证明的行为就不是一回事。分派条件同理:FromLow 的 `dst ≤ src ∨ size ≤ 8` 单点定义在 `mcopy_low_dispatch_premise`(复合路径的反向重叠支额外要求 `copied == 0`,因为 `size ≤ 8` 时 word 循环的 `jl` 一轮不跑就跳 tail)。引理只证 `dst ≤ src` 而 runtime 按真实分派条件放行,就会折叠一段引理从未证明过的行为。

**prove-or-reject,且不得自行补前提。** summary **不得**往 `SMTState.assumptions` 里添加尚未证明的 no-wrap/方向/长度前提,否则证明域会被静默缩小。`assumed_premises` 记录器守住这一半纪律,测试断言它恒为空。

**gas 中立性是折叠安全的地基。** 四条 opcode 的 gas 全部在循环**之外**由 `checkMemoryAndCalcDynamicGas*` 前言扣完,循环体内一条 gas 指令都没有,所以跳过循环体不会让两侧账本分叉。这是对当前 codegen 的**观察而非定理**,必须由端到端哨兵固化(`tests/integration/test_copy_loop_gas_parity.py`):将来若有 gas 被挪进循环体,该测试会立刻红。

#### 单入口检查(证书折叠的前置条件)

必须拒绝"外部边绕过 summary 入口进入 covered 区"的情形,否则"折叠一定生效"的保证不成立。未命中入口的块会被原样逐指令执行(语义与不启用 summary 一致,故非健全性问题),但这项检查必须先于 Tier 1 证书折叠落地(§8)。

引理绑定编译器版本,codegen 变更时模板匹配失败 → fail-closed。哲学与 `mul_uf` 一致:对合约黑盒,对编译器白盒。

## 6. 结构守卫与降级管线

核心守卫(放在 x86 CFG 构建后):

```text
0. 前提检查:IR parser 必须解析并保留 `immediate_set`,用它区分 resolved_multi
   与真正 dynamic_unresolved。IR 中出现 dynamic_unresolved 的 JUMP/JUMPI
   (将编译为 jumpCode dispatcher)⇒ 验证失败(dispatcher 不建模,fail-closed)。
1. 两侧分别做支配分析,识别 natural loop(边 u→h 且 h 支配 u)。
   "目标地址在前"不是循环。
2. x86 侧每条 natural-loop 回边,必须满足其一,否则验证失败:
   (i)  与某条 EVM natural-loop 回边完成 Tier 1 配对
   (ii) 命中 Tier 2 已证引理的模板(指令序列匹配,fail-closed)
```

该守卫同时防御"编译器升级悄悄新增循环",且必须在完整路径枚举**之前**运行——它的输出决定哪些循环头是 cutpoint、哪些 Tier 2 summary 可在执行时启用。

**配对方式与其 fail-safe 性质的当前状态。** 现行配对按 header 排序后逐位比对 latch 数(数量不等 ⇒ 全部不配对;逐位 latch 数不等 ⇒ 该位不配对),因此**同 latch 数的错误置换可以直接进入 pairs**。②的出口配对(§4.4)是同一形态。其安全性论证是:

> 预期在 Base / application / 消费端**全部按精确程序点验证**后为 fail-safe——错配的证书永远不会被消费(实际执行不会同时到达那对程序点),回边退回展开 → 降级。

但**主消费端尚未落地**,该性质目前只是预期、未经实证(§7.1)。验收基准 12 是它的哨兵。

**调用/返回形态候选的处置。** §3.3 显示 CErc20 有 5 个按形态疑似 call/return 的候选,当前一并进入 Tier 1 配对。对它们的识别与排除定位为**达成率优化,不是健全性机制**:

- 收益:避免对函数调用边徒劳跑归纳(每个都是分钟级 Z3 开销),避免守卫因它们失败而拒绝整个合约;
- 误排除方向是 fail-safe 的:被排除的边照常展开执行,若其中真有符号 bound 循环,depth-pruning 的 coverage 证书会 fail-closed 抓住;
- 排除只作用于 loop-backedge 检测,**执行 CFG 不删除任何边**;
- 长期正解不是"排除",而是 cutpoint 泛化——这些候选的本质就是函数调用(`docs/cutpoint泛化方案.md`)。

管线是 **pre-prove, fold, or honestly degrade**:

```text
0. 静态守卫:两侧 CFG/natural-loop 分析,unresolved 跳转检查,
   Tier 1 配对,Tier 2 模板发现。

1. Tier 2 预处理:模板命中 + 引理/codegen 指纹有效 → 注册单侧闭式 summary;
   命中失败 → fail-closed 或显式 bounded 降级,不在完整模式中展开符号 copy loop。

2. Tier 1 证书生成:把所有循环头设为 cutpoint,只执行无环前缀来证明 Base、
   发现并证明 depth classes 的两条完备性义务;对每个可达 pair 证明归纳步
   与全部出口,生成 Tier1LoopCertificate。

3. 主证明折叠:在 paired cutpoint 消费证书,不进入回边;
   x86 executor 在 Tier 2 入口应用闭式 summary;
   最终只对折叠后的无环 proof skeleton 枚举 terminal/cutpoint paths。

4. 等价与 coverage 合取:检查全部非循环 terminal observables;
   核对所有循环边都由已消费证书/summary 覆盖;两类义务同时成功才 VERIFIED。

5. 降级:任一证书 SAT/unknown/超时/结构失配 → inconclusive;
   只有调用方显式允许时,才用有界展开 + 显式长度 assumption,
   结论标注"bounded proof + caller-provided assumption",不冒充完整证明。
```

允许一次低 depth 的 discovery pass 作为调度优化,但它不得成为"先完整跑到全局 `max_depth`,再决定是否证循环"的前置条件;即使使用 discovery,循环头也必须是 stop cutpoint。

**归纳步 SAT ≠ 找到 bug**(§4.3)。可信反例只能来自降级后的有界模式。

**证书/summary 的适用前提必须 prove-or-reject。** 前提须由当前 path condition + 调用方全局先验证明;查询为 SAT 或 unknown 时必须拒绝或进入显式 bounded 降级。

## 7. 边界、非目标与结论强度

### 7.1 结论强度

**方案证明什么。** 对每个通过全部义务的合约 (EVM IR, x86) 对:所有非循环 terminal path 的 observable 等价;所有可达 Tier 1 循环在任意轮数下两侧保持同步、同时决定继续/退出、并在满足六项前提时有限退出;所有 Tier 2 拷贝循环的净效果等于 EVM 闭式语义。

**方案不证明什么。**

- **logs 不在证明范围内。** `OBSERVATION_KEYS` 十项中没有 logs;status 与 gas 已纳入,revert 以 `status_code` + return memory 体现。声称"可观测面已补齐"是过强的。
- **终止结论是条件定理**,依赖 §4.4 ②(e) 的六项前提,且这些前提必须作为证据进入证书。
- **host gas 公式与 `HOST_GAS_UPPER_BOUNDS` 都是外部人工审计所得的 assume,不是定理**;CALL 四件套 / CREATE / CREATE2 仍是无上界 UF。
- 降级格子中超出 bound 且不满足 assumption 的行为不被覆盖,但在报告中显式声明,非盲区。

**已兑现的两项**(早先版本把它们列为阻塞):`R` 的镜像闭包已进证明义务与指纹,实测 6/6 镜像字段拒绝陈旧 limb;主验证器已能消费证书并按精确程序点 + 深度类核对截断态(§4.7)。

**仍未实证的一项:** 顺序配对的 fail-safe 性质(§6、§4.4 ②)。循环配对与出口配对都按顺序进行,允许同 latch 数置换。消费端的程序点核对理论上使错配证书无法被消费,但**验收 12 的反向哨兵尚未建立**——在它建立前,这条只是论证,不是被测过的性质。

### 7.2 已知边界(均为降级方向)

- **`OFF` 档在归纳模式下默认 inconclusive**(证书应用域内存在 reachable host-gas 操作时)。
- 归纳完备性依赖 `R`/`Inv` 够强;跨回边存活的 scratch 值会导致伪 SAT → 降级,不会漏检。
- `R` 若不覆盖 caller-frame 中后续会读到的 live 栈槽,函数内循环会因出口后读 caller-frame 而系统性伪 SAT → 降级。
- 两侧 host UF 的内存实参坐标系不同,含 CALL 族的循环在内存非空且 `R15 ≠ 0` 时会无谓 inconclusive(§4.5.3)。
- 深度类超出 schema 建模范围(如栈字节偏移 > `0x4000`)时降级,而不是放宽边界。
- 段内可达 `GAS` opcode 一律拒绝;放宽需先确认 `compileEVMGAS` 在符号 gas 下与 EVM 侧逐字对齐(§4.2)。
- Tier 2 引理与编译器版本绑定,`impl_amd64.go` 模板变更需重证(模板匹配失败会强制暴露)。
- 含 dynamic_unresolved 跳转的合约整体拒绝——实证中 Solidity 产物全部可静态解析。
- host 调用(SHA3/CALL 等)在循环体内时仍按现有 UF/bridge 机制处理;必须显式校验循环体内 EVM/x86 bridge site 配对,不能只依赖整程序地址序枚举。
- Tier 1/Tier 2 证书缓存键必须包含 EVM IR、x86 指令片段、AOT profile、`R`/`Inv` 版本与 `GasCheck` 档位;任一指纹变化必须重证(§4.7)。
- 主验证折叠后仍必须证明不经该循环的分支、体内终止分支与出口 suffix;loop certificate 不对其它 terminal paths 给出全局免检权。

**`R` 的完整性是逐条枚举出来的,不存在"其余状态默认对齐"。** 每个跨轮次演化的状态量都必须同时进 `R`、进 havoc、进 Base/application/latch/exit 的证明义务、进证书指纹——四处缺一,该量就悄悄退出了验证范围。按 `SMTState` 字段表逐项过之后,确认三类字段**刻意不进 `R`**,理由各不相同,新增字段时应对照分类:

| 类别 | 字段 | 处理 |
|---|---|---|
| bridge 传参暂存 | `callengine_stack_pointer_limbs`、`builtin_func_index`、`go_func_index`、`return_address` | 不是窗口状态,由 bridge 配对校验覆盖 |
| 配置标志 | `host_gas_uf_enabled`、`abstract_calldataload_words`、`assume_calldata_offset_no_overflow` | 进**证书指纹**,不是 `R` 合取 |
| 待消费队列 | `pending_errors`、`pending_constraints` | cutpoint 在块边界,应核对为空;这是**结构前提**而非状态等式(§4.5.6) |

### 7.3 非目标与重启判据

以下方向**明确不在本方案范围内**。每条给出重启判据,以免被当作永久否决:

| 非目标 | 理由 | 重启判据 |
|---|---|---|
| **段内复杂指令 summary**(SIGNEXTEND/ADDMOD 等的严格 matcher + per-hit proof) | 一次性白盒投入不小,且尚未确认这些指令真的出现在目标合约的循环体内 | 先做一次"目标合约循环体内复杂指令普查";普查确认出现且 §4.8 的桥接不足以控制路径规模时启动 |
| **caller gas 下界 → 区间化 theorem application** | 依赖"下界从哪来"这个尚未设计的环节;没有下界时上界无法剪枝 | 出现能提供可信 gas 下界的调用场景(如 `FIXED_BUDGET` 下的分段预算)时重估 |
| **`GasCheck.OFF` 档的专用归纳路径** | OFF 不建模 host gas,OOG 阈值判 `S > G` 而非 `S > G−H`,探索的是错误路径集;共享符号 cutpoint gas 补不上这个缺口。默认 inconclusive 已保证不假绿 | 出现"必须在 OFF 档拿完整结论"的实际场景时重估;条件性结论只能由显式 legacy/conditional 模式产出并携带完整前提标注 |
| **符号深度类** | 与"函数级 cutpoint 的符号 frame 参数化"是同一个机制问题,单独做等于做一半 | 随 cutpoint 泛化一并设计;若届时仍需 QF-friendly 查询,可用与 §5.2 同款的 lambda 编码 |
| **cutpoint 泛化(函数级 cutpoint)** | 独立一期工作,要求把有限深度类枚举换成符号 frame 参数化与闭包证明 | 见 `docs/cutpoint泛化方案.md`(探索阶段,四个问题待设计) |

验收基准:

1. Compound name/symbol getter 与 initialize 的 string 循环(Tier 1),CALLDATACOPY/RETURNDATACOPY/MCOPY 符号长度用例(Tier 2),均在不提高全局 `max_depth` 的前提下得到完整证明。
2. 主路径统计证明已识别 Tier 1 回边没有被重复展开。
3. 人为修改一条非循环 return/memory/storage 路径时,即使所有循环证书成功,顶层也必须失败。
4. 人为注入不可配对回边、破坏 Tier 2 模板或删除必要守卫时,必须 fail-closed。
5. 人为让 x86 侧静态 gas 常量与 EVM 侧差 1,OOG 谓词等价查询必须 SAT(即桥接拒绝),不得被"共享判定"掩盖。
6. **host-gas 序号反向用例**:循环体内含 SLOAD,人为让 x86 侧比 EVM 侧多一次 host 调用(序号偏移 1),证书必须失败。若把 cutpoint 序号重置为 0,该用例会假绿——它正是这条缺口的哨兵。
7. **`lastGasCost` 反向用例**:构造两侧 `MSize` 相等而 `lastGasCost` 不等的到达状态,certificate application 必须拒绝。
8. **return data 反向用例**:构造循环**之前**执行过 CALL 的用例,人为令两侧 return-data size 或内容不同,certificate application 必须失败。若 cutpoint 沿用 `create_initial_state` 的 size=0 初值,该用例会假绿。
9. 报告保留 `GasCheck` 档位、证书指纹、depth classes、命中 cutpoints、降级前提。
10. 守卫统计在 CErc20/Safe 上复现 §3.3 的实测分布(两个口径的跳转分类、候选数与形态分布、Tier 1/Tier 2 分层数)。
11. **CALLENGINE 镜像反向用例**:逐字段单侧篡改 limb(属性不动),`R` 必须拒绝——这是 §4.5.5 的哨兵,用例须覆盖 `_sync_callengine` 维护的全部字段而非固定几个。
12. **配对置换反向用例**:人为交换两个同 latch 数的 pair,折叠必须拒绝。这是 §6 那条 fail-safe 论证的哨兵。
13. **status 结构前提反向用例**:构造一侧已终止、另一侧仍 running 的到达状态,§4.5.6 的五处覆盖点各自必须拒绝。
14. **域约束闭合反向用例**:构造一轮循环体把 `MSize` 扩到域外(> 4 MiB)的场景,②(b) 必须拒绝而不是让定理在域外被复用。

### 9.0 真实合约上的循环覆盖率(先看这一节)

机制齐全 ≠ 能用。下面是在两份真实合约的**全部 13 对配对循环**上的实测,它决定这套方案当前实际能覆盖多少。

**第一道门:结构预检**(`Tier1LoopInduction._structural_rejections`)

| | 配对循环 | 通过 | 被拒 |
|---|---|---|---|
| CErc20 | 9 | 5(`0x739` `0x333e` `0x35e7` `0x36aa` `0x3731`) | 4 |
| Safe | 4 | 2(`0xc3b` `0x27f1`) | 2 |

**6 对(46%)被拒,原因全部是 `exit count mismatch`**,根因是两侧对"出口"的定义不对称:

- x86 侧把 TAG 错误 stub 当作 CFG 后继块 ⇒ 计入出口;
- EVM 侧的 TAG 错误是 terminal 状态 ⇒ 不计入出口。

`__init__` 本应过滤掉 x86 的错误 stub,但 `_TERMINAL_ERROR_STATUSES` 只含四个 TAG 守卫错误(`out_of_gas` 12 / `gas_uint_overflow` 13 / `stack_underflow` 14 / `stack_reached_limit` 15),而 AOT profile 里 **3–17 都是错误终止**。实测漏掉的是 `invalid_jump`(8):Safe `0x10bb` 的 x86 侧出口里就有一个 `mov [r13+0xe0], 8` 的 stub,于是出口计数多一。

另一类是 `JUMP immediate_set` 多目标跳转:`0xb39` 的 EVM header 有 21 个跳转目标、展开成 20 个出口,x86 侧比较链给 19 个——**两侧计数口径本就不同**,不是漏过滤能解决的。

**「补全过滤集合」这条路已实测否决。** 直觉上把 `_TERMINAL_ERROR_STATUSES` 从 4 个错误码扩到全部 terminal status 就能对上,实测是**净负**:

| 过滤集合 | 出口数匹配的配对(共 13) |
|---|---|
| 现行 4 个 TAG 守卫错误码 | **7** |
| 全部错误终止(12 个) | 6 |
| 全部 terminal(排除 bridge) | 6 |

`0x10bb` 确实被救回(3→2 ✓),但 `0x333e`(8✓→7✗)与 `0x35e7`(3✓→2✗)被弄坏——**某些写了 status 码的 x86 块是真实的循环出口而非 terminal stub**,"写 status + ret" 不是 terminal outcome 的充分判据。而且多数不匹配的差距根本不是一两个(`0x7c7` 34 vs 32、`0xb39` 20 vs 15、`0x3643` 27 vs 20)。

**方向应当是按语义配对出口,而不是按数量相等 + 顺序 zip。** 现行 `exit_pairing = dict(zip(sorted(evm_exits), sorted(x86_exits)))` 要求两侧数量相等,这个前提在多目标跳转下本就不成立。可用的锚点已经有了:`docs/cutpoint泛化方案.md` §3 实测的 TAG 序言指纹能把 EVM pc 与 x86 地址逐块对齐(CErc20 723/723、Safe 742/742),用它给出口做**语义配对**,比数量匹配可靠得多。这是一项独立设计,不在当前范围内。

复现:`tmp/probe_filter.py`。

**第二道门:归纳步**(通过预检的 7 对,单查询预算 60 s)

| 循环 | body | depth | 结果 | 墙钟 | 查询数 |
|---|---|---|---|---|---|
| CErc20 `0x739` | 1 | 3 | **proved** | 136.4 s | 278 |
| CErc20 `0x36aa` | 2 | 2 | **proved** | 2.9 s | 60 |
| CErc20 `0x3731` | 2 | 3 | **proved** | 4.5 s | 243 |
| CErc20 `0x35e7` | 5 | 1 | 14 min 未完成 | — | — |
| CErc20 `0x333e` | 9 | 2 | 未测 | — | — |
| Safe `0xc3b` / `0x27f1` | 2 | 4 / 3 | 未测 | — | — |

**结论:符号 trip count 确实被归纳吞掉了**——`0x739` 是带 SLOAD host 调用的动态 string 存储循环,136 s 证过,不需要提高 `max_depth`。但可用范围目前限于**循环体 ≤ 2 块、单 latch、出口两侧对得上**的循环;body=5 就撞上规模墙(段执行的路径矩阵是 8 × 111 量级,见 §9.1)。

**第三层:端到端从未在真实合约上跑通。** `fold_loops` 的完整链路(① Base → ② 逐深度类 → ③ 逐出口 → 证书组装 → 主验证器消费)只在最小合成程序上验证过(`tests/integration/test_loop_folding_integration.py`);上表证的都是**单独的归纳步 ②**。

**复现**:`tmp/survey_loops.py`(遍历两份 fixture 的全部配对循环,`--structural-only` 只跑第一道门)。

### 9.1 §4.8 桥接的路径规模数据

在 CErc20 循环 `0x739`(EVM)/ `0x107a2`(x86)的归纳步上实测。**注意前提:这些数字是在归纳步当前 `inconclusive` 的状态下取得的**(见 §9.2),端到端那一组因此严重低估收益。

**端到端**(`check_inductive_step()`,3 次重复):

| | 桥接关 | 桥接开 |
|---|---|---|
| 结论 | inconclusive | inconclusive(**一致**) |
| solver 查询数 | 126 | 138(+1 桥接等价 +11 极性) |
| 墙钟中位 | 12.2 s | 13.0 s |
| `pairs_pruned` | 0 | 0 |

端到端目前是**净成本**:矩阵在第二对就因义务不成立而当场返回,还没走到有剪枝机会的地方。

**全矩阵普查**(绕开早退,数整个矩阵有多少对被桥接证明不可共现):

| 阶段 | 矩阵规模 |
|---|---|
| raw,envelope 时代(两侧错误终止路径整个不入列表) | 2 × 80 = **160** |
| raw,取消 envelope | 8 × 111 = **888**(5.6×) |
| 可行性预过滤后,envelope 等效 | 2 × 4 = **8** |
| 可行性预过滤后,取消 envelope | 8 × 10 = **80**(**10×**) |
| 预过滤后 + OOG 桥接 | **64**(**8×**) |

桥接自身开销 **12 条查询 / 约 0.3 s**(1 条等价 + 11 条极性,极性判不出的为 0),剪掉 **16/80 = 20%** 的配对。

**这个收益没有把规模压回 envelope 级别,原因是清楚的**:本次桥接只在**循环头**的 TAG gas guard 上分区(阈值 50),只有 1 条 x86 路径与 1 条 EVM 路径被判为 must-OOG;膨胀的主体来自**块内其它 TAG guard**(各自不同阈值)产生的错误终止路径,它们在头部谓词下极性为 False、不被剪。要压回 envelope 量级,需要把桥接推广到**每个块入口**的 gas guard,而不只是循环头——这是 §4.8 的后续方向,不在当前范围内。

### 9.2 验收基准 1:通过,以及它曾经如何静默失效

`tests/integration/test_loop_induction_cerc20.py`(验收基准 1:CErc20 string 循环 EVM `0x739` / x86 `0x107a2` 的完整归纳证明)**通过,用时约 283 s**。

它一度是红的,失败在 ②(c) 出口 R,根因有两个,都值得记下来:

**(a) 域约束的字段混淆——EVM 侧的检查从未真正生效。** `_domain_predicate` 两侧都读 `callengine_memory_size_bytes`,但那是 callEngine 的镜像字段,**EVM 语义从不写它**(EVM 侧的语义字段是 `evm_memory.MSize`)。于是 `predicate(evm_state)` 读到的永远是 havoc 原值,而域约束在 havoc 里已被 `add_assumption`,该义务因此**恒真**——实测出口边上 EVM 侧域目标 `simplify` 成 `True`。名义上"两侧都证",实际只证了 x86 一侧,§4.4 ② 那句"不能靠 R 的 `memory_size` 分量省掉一侧"被字段混淆悄悄绕过。现已按侧取正确字段。

**(b) 深 ITE 让 `memory_gas`/`gas` 两条义务 `unknown`。** 解法是 `_proved_ite_polarities`:先证 `premises ∧ c` 不可满足(即 `premises ⊢ ¬c`),再把该字面量注入后续查询。注入的是完整前提的**逻辑后承**,`A ⊨ e ⟹ A ≡ A ∧ e`,是恒等变换而非新假设;判不出(sat/unknown/超预算)就不加。这与 `common/div_bridge.py` 的"先证实参恒等再注入等式"是同一条纪律。**`memory_gas` 的双条件(两侧相等 + 各自 = `memoryGasCost(MSize)`)完整保留,R 没有被削弱。**

**流程问题:默认 skip 的验收测试会静默腐化。** 该测试是 `skipif(not RUN_LOOP_INDUCTION_ACCEPTANCE)`,连 `-m slow` 都跑不到,全量回归里根本不包含它。上述 (a) 是一个**长期存在**的缺陷,而它同时还带着一条 envelope 取消后就恒假的过时断言——两者都是在一次手动运行中才暴露的。验收基准若不进常规回归,"§9 无未落地条目 + 全量绿"并不蕴含"验收基准成立"。
